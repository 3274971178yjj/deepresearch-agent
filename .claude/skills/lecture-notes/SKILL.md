# 带读讲义写作规范（DeepResearch Agent 版）

本 skill 面向 `learn-notes/` 下的系列讲义。学习者是在准备校招面试的 NPU 学生,
目标是**读懂简历里写的每个技术点、能应对面试追问**,而不是运行训练。

## 一、交付要求(先看这条)

- **讲义写入 `learn-notes/` 下的 md 文件**,文件名形如 `0X-主题.md`(编号与"第 X 讲"一致)。
- **不要在对话框里长篇讲解**。对话框只用于答疑、批改、讨论;成体系的内容一律落文件。
- 写作前先读上一讲,确保**开头承接、末尾预告**、内容不重复。
- 写完后**必须**跑链接验证脚本(见第五节),再向用户交付。

## 二、必备格式骨架

标题与引言:

```markdown
# 0X · 主题名【带读讲义 · 第 X 讲】

> 本讲义属于"带读模式"系列:每讲 = 大白话 → 带读代码 → 对照样例 → 跟读复述。先读 [01_项目全貌&学习路线](01_项目全貌&学习路线.md) 建立前序认知,再读本讲义。
> 本讲目标:**说得出……、背得出……、讲得清……**。
> 使用方式:VS Code 打开项目文件夹 → 本 md 按 `Ctrl+Shift+V` 预览 → 点击蓝色链接直接跳代码。行号已与当前代码核对。
```

正文步骤(按此顺序,可按讲次需要裁剪):

| 章节 | 内容要求 |
|---|---|
| `## 📖 阅读导航` | 🔴必读(带分钟估计 + 为什么必读) / 🟡选读 / ⚪可跳过。**放正文最前面** |
| `## 第 0 步 · Python 语法工具包(第 N 包)` | 表格:语法 / 例子 / 人话。**只列本讲新出现的语法** |
| `## 第 1 步 · 大白话:……` | 先讲动机与问题,再给方案。不先上代码 |
| `## 第 2 步 · 带读代码` | 关键代码原文 + 逐段**【人话翻译】** |
| 后续步骤 | 对照样例 / 对照数字 / 把规则落到具体例子 |
| `## 第 X 步 · 跟读复述` | 填空题式提问,**替代闭卷测验**(见第四节) |
| `## 面试速记卡` | 表格:问 / 答。**每讲必须有**;题目按第七节第 6 条的五类 Claim 归类,答案遵守第七节第 5 条的内部名词预算 |
| 末尾 | `**下一讲预告:第 X+1 讲 · 主题**——一句话钩子。` |

## 三、写作原则

1. **只讲简历技术点和项目重点**,不做无关扩展;不贴大段可运行代码。
2. **讲动机 > 讲实现**。每个设计都要能回答:为什么这么做?不这么做会怎样?
3. **Python 基础一般**:新语法进"语法工具包";`【人话翻译】`要用生活化类比,不要用术语解释术语。
4. **明确区分"真实现"与"占位/规划"**,这是本项目面试最高频的失分点(见第七节第 1 条)。
5. **篇幅 30–45 KB**。低于 25 KB 会被认为"讲得太浅"。
6. 关键代码**放出来逐行讲**,但只放直接相关的那一段,长函数可拆成"先看这段/再看这段"。
7. 术语第一次出现时给通俗解释;能用表格对比的就用表格。

## 四、学习者背景(影响写法)

- NPU 学生,校招面试导向,Python 基础一般。
- **明确拒绝过闭卷代码测验** → 一律用**带读 + 跟读复述**(给提示、填空式),不要设计需要默写的题。
- 偏好中文、可点击的行号链接、以及"这段代码为什么这么写"的讲解。
- 每讲末尾的跟读复述**用填空/提示**,不给标准答案让人背。

## 五、代码链接规范(历史踩坑点)

**格式**:`[文件名](../相对路径#L起始-L结束)`

- 从 `learn-notes/` 出发,**必须带 `../` 前缀**(漏掉会导致链接点不开——已踩过两次)。
- 跨多个文件的链接不要歧义:同名文件(如两个 `README.md`)在正文中写清来源目录。
- **行号必须与当前代码核对**,代码改动后链接会失效。

**代码锚点的统一写法**(全系列统一,新写/改写一律照此):

```markdown
👉 **本地阅读代码**:[orchestrator.py:519-537 _should_replan()(失败率>50% 触发重规划)](../src/orchestrator/orchestrator.py#L519-L537)
```

- 链接文字用**短标签** `文件名:起始-结束 函数名()`,不要写整条长路径(太长的可点区域不好扫)。
- 同一处引用多个符号,用 ` · ` 分隔成多条链接,不要塞进一个括号里。
- ❌ **禁止写法**:`👉【本地阅读代码:路径 :: 函数名(第N行)】`——纯文本包裹,函数名点不开。
- 指向**目录**的链接无效(check_links.py 只校验文件)。要指目录内容时,挑一个代表文件来链,并在正文里说明该目录还有哪些文件。

- 写完**必跑**:

```bash
python .claude/skills/lecture-notes/check_links.py learn-notes/0X-主题.md
```

脚本会验证文件存在、行号在范围内,并打印每行内容供核对"链接指向的内容"与正文是否一致。
输出 `✅ 所有链接都能点开` 才算完成;有失效链接先修再交付。

## 七、事实与证据纪律(本项目最重要的一节)

讲义里每句话都要能被源码接住。以下七条是硬约束,和第三节的写作原则同级。

### 1. 源码与文档冲突时,以实现为准,**并把差异显式写出来**

本项目 README 与代码有多处出入(已核实)。典型:

| README 说 | 代码实际 |
|---|---|
| M6 是"GRPO 强化学习" | `engine.py` 第 7 步是 **注释掉的伪代码**,无任何训练代码 |
| 对抗"3 轮 / ≥8.0 / Δ<0.3" | `loop.py` 的**函数默认值**是这样,但 `configs/default.yaml` 覆盖为 **10 / 9.5 / 0.2** |
| Red 五维含"时效性" | `Dimension` 枚举五维是 fact_check / hallucination / logical / source_credibility / coverage,**没有时效性** |
| Blue"4 种修复 ADD/DELETE/MODIFY/VERIFY" | `FixType` 只有 **3 种**:IN_PLACE / SUPPLEMENTARY(值叫 `search`) / REMOVAL |
| L1"cosine<0.6 丢弃、>0.95 保留" | 0.6/0.8/0.95 是 **budget 占用率**触发阈值;L1 的 cosine 阈值实际是自适应的 **0.25/0.20/0.15** |
| L3"精保留原文" | L3 是 **LLM 层级摘要**(逐文档摘要 → 聚合摘要) |
| 结构与文件(`verl/`、`docs/`、`configs/tool_config/`、`.env.example`) | 这些路径**都不存在**(真实是 `configs/tools/`、`.env.template`) |

写讲义遇到这类冲突,**以代码为准**,并写清"README 这么写、代码这么写"。
不要为了叙事顺畅而挑一个说法。仓库里没有文档说明某事时,如实写"仓库里没有明确写 X",再给推断并标明是推断。

### 2. 数字必须标证据档位

| 档位 | 含义 | 讲义写法 |
|---|---|---|
| **实测** | 跑出来的日志 / 报告 / 评测结果 | 直写数字 + 出处(哪个文件哪一行) |
| **阶段结果** | 中间产物(题数、条数、次数) | 写清"在哪个环节" |
| **技术验证** | 能跑通、现象符合预期,但没测规模 | 只写"验证了 X 能跑通",不写收益 |
| **估算 / 推断** | 算出来的、推的 | 必须写"按 X 推算是 Y" |

**性能收益没有测量时不下结论。** 不写"显存降低 40%""速度提升 3 倍"这类没有出处的数。
简历里出现的 `85%→95%` 这类数字,**仓库中查无出处**,必须在讲义里标为"待确认 / 无仓库证据"。

### 3. 源码边界:只讲存在的路径,异步要追到注册点

- 异常、恢复、清理、降级:**只讲代码里确实写了的**。源码没有的容错路径不要补
  ("它会自动重试"要么有代码,要么标为分析)。
- 工具、Agent、后端的**注册链**要追到证据:`src/tools/__init__.py` 的导出列表、
  `runner.py` 的工具工厂、`configs/default.yaml` 的 `backend_mapping` 都是这类证据。
- 追不到运行时的真实目标就**停在已证实的接口边界**,不要猜。

### 4. 标记约定(与 🔴/🟡/⚪ 导航并列,用途不重叠)

```text
待确认   —— 源码里没有证据,不要当结论讲
推断     —— 由证据算出来的,要说明推法
分析     —— 设计动机类判断(源码不会写"为什么"),标明这是分析
```

### 5. 面试口播用通用表达,实现名下沉

「面试速记卡」「面试 30 秒版」是**要念给面试官听的**,不是给自己看的。

- 正文可以出现 `OrchestratorState`、`FixType`、`backend_mapping` 这类项目内部名,
  **但口播里最多 2 次**,且每次紧跟一句通用翻译(如"九状态状态机,即任务生命周期的显式建模")。
- 口播优先用通用工程说法:多智能体异步编排、DAG 拓扑并发、语义去重与冲突消解、
  对抗式自我修订、分层上下文压缩、多云模型路由——面试官听得懂的是**能力**,不是你的私有枚举名。
- 私有函数名、私有枚举、打点名、内部代号:**正文里给源码链接就够了**,口播里不出现。

### 6. 面试题先归类,再按风险信号追问

写「面试速记卡」和问题库时,每道题先归到五类之一,再决定追问方向:

| Claim 类型 | 追问重点 |
|---|---|
| Ownership | 个人范围、亲自实现的部分、关键决策、团队分工 |
| Metric | baseline、分母、周期、数据来源、口径、个人归因 |
| Technical | 技术在项目里的输入输出、具体作用、选择原因、trade-off |
| Architecture | 组件、数据流、边界、替代方案、故障处理、扩展限制 |
| Result | 是否真交付、谁在用、怎么衡量、个人动作 vs 团队结果 |

**优先追这些风险信号**(出现在自己的答案里就是失分点):用"负责 / 优化 / 提升 / 支持"
却没有对象 + 动作 + 证据;报了百分比却说不清统计口径;用"主导 / 架构 / Owner"却划不清
个人边界;只讲 happy path、讲不了失败与回滚;背得出术语定义却说不出它在项目里的作用;
答案与简历原文或前文自相矛盾。

**不给缺乏校准依据的精确总分**(如"你这项 7/10")。

### 7. 发现"讲不清"时,只给三条诚实路径

某个技术点用户讲不清(或简历写得比实际掌握强)时,**不要替他补话**。只给三条路:
① 补真实事实;② 补相关知识(并指明该读哪一段源码);③ 降低简历 / 口播表述强度。
不生成"听起来很对的空话答案"。
