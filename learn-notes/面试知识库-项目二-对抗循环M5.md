## 1 · 先看全景：verdict.py 在 M5 里的位置

### 1.1 这个文件是「数据契约层 + 纯数学层」

[verdict.py](../src/adversarial/verdict.py) **一共 287 行，没有一个 `async`，没有一次 LLM 调用，没有一行 IO。**

这不是偶然，是分层：

```
        ┌──────────────── AdversarialLoop.run() ────────────────┐
        │  loop.py:92  for round_idx in 1..max_rounds            │
        │                                                         │
        │   ①Red.attack() ──► RedVerdict ──┐                      │
        │        red_agent.py:270           │                     │
        │                                   │ ← verdict.py 定义   │
        │   ②震荡检测 set[Issue] 交集 ◄──────┤   的三种数据结构    │
        │        loop.py:104                │                     │
        │                                   │                     │
        │   ③Blue.defend() ◄────────────────┘                     │
        │        blue_agent.py:180 ──► list[FixOperation]         │
        │                                   │                     │
        │   ④delta = compute_delta(...) ◄───┘                     │
        │        loop.py:131                                      │
        │   ⑤_check_convergence()   loop.py:161                    │
        └─────────────────────────────────────────────────────────┘
```

**四个纯函数各自插在闭环的一个关节上**（全部实测调用点，`scripts/measure_m5_verdict.py` §6）：

| 方法 | 上线代码里的调用点 | 调用点数 | 干什么 |
|---|---|---|---|
| `compute_overall` | [red_agent.py:334](../src/adversarial/red_agent.py#L334) | **1** | 五维 → 一个综合分 |
| `compute_delta` | [loop.py:131](../src/adversarial/loop.py#L131) | **1** | 轮间变化量 → 收敛判据 |
| `compute_priority` | [blue_agent.py:206](../src/adversarial/blue_agent.py#L206) | **1** | 决定先修哪个 |
| `to_json` / `from_json` | **（无）** | **0 / 0** | 号称「持久化审计」，**从未被调用** |

> **面试可以讲的定位**："`verdict.py` 是 M5 的**数据契约层 + 纯函数层**——它把『什么是问题』『怎么打分』『先修哪个』全部收拢到一处，且不含任何模型调用和 IO。**所以它可以完全离线单测**，这和张量/模型代码要起 GPU 才能验是两种工程风格。"

### 1.2 ⚠️ 先说清楚：这里有两套「五维」，别混

这是**答 M5 时最容易翻车的概念混淆**：

| | M5 循环内的五维 | 评测层的五指标 |
|---|---|---|
| 定义处 | [verdict.py:45-51](../src/adversarial/verdict.py#L45-L51) `Dimension` | [rule_based.py:26-303](../evaluation/metrics/rule_based.py#L26-L303) |
| 五个名字 | `fact_check` / `hallucination` / `logical` / `source_credibility` / `coverage` | `factual_accuracy` / `logical_consistency` / `citation_coverage` / `bias` / `comprehensiveness` |
| 谁来打分 | **Red Agent（LLM）** 输出 | **纯正则/子串**规则 |
| 用途 | 驱动**循环内**的收敛与修复排序 | 离线评测报告质量 |
| 权重 | 0.30/0.25/0.20/0.15/0.10 | 见 [rule_based.py:268-274](../evaluation/metrics/rule_based.py#L268-L274) |

**两套体系没有代码上的耦合。** 面试如果问「这两套指标什么关系」，正确回答是：

> "**它们是两个不同层面的东西。** 循环内的五维是 Red Agent 这个模型对报告的主观评分，用来驱动迭代和修复排序；离线评测层的五个指标是纯规则统计，用来给最终报告打一个可复现的分。**前者求快、求方向对；后者求稳定、求可复现。** 我没有把两者对齐——这是个可以改进的点：理想情况下应该验证『循环内分数提升』和『离线指标提升』是否同向，**但那样需要跑对照实验，我没有做。**"

**最后一句必须说**，否则就是在暗示两套指标互相验证过。

## 2 · 三个枚举 = 对抗循环的受控词表

### 2.1 `Severity` —— [verdict.py:31-35](../src/adversarial/verdict.py#L31-L35)

| 成员 | 值 | `SEVERITY_WEIGHTS` | 语义 |
|---|---|---|---|
| `CRITICAL` | `"critical"` | 10.0 | 事实性错误、核心幻觉 |
| `MAJOR` | `"major"` | 5.0 | 显著不一致、重要遗漏 |
| `MINOR` | `"minor"` | 1.0 | 措辞偏差、次要来源问题 |

**10 : 5 : 1 的比例（不是 3:2:1）是刻意的**——它让「严重度」在优先级公式里变成**硬门槛**（见 §4.3）。

⚠️ **这是从 LLM 输出解析来的字段。** [Issue.from_dict:90](../src/adversarial/verdict.py#L90) 写的是 `Severity(data.get("severity", "minor"))`——`.get` 的默认值**只在键缺失时生效**；键存在但值非法会直接抛。实测：

```
Issue.from_dict(severity='blocker') → ValueError: 'blocker' is not a valid Severity
```

**算 bug 吗？** 我的判断：**算设计脆弱，不算 bug。** 因为 `Issue.from_dict` 的唯一调用链是 `RedVerdict.from_dict` ← `VerdictEngine.from_json`，**而 `from_json` 零调用**——所以这条路径在**当前代码里根本走不到**。写出去的 JSON 用的必然是 `.value`，round-trip 安全。

> **面试话术（展示边界意识）**："我在两个地方对 LLM 输出做了防御——[red_agent.py:320-332](../src/adversarial/red_agent.py#L320-L332) 的 try/except 兜底，和 [verdict.py:226](../src/adversarial/verdict.py#L226) 的数值 clamp。**但 `from_dict` 这条路径我没设防，因为我判断它只服务于序列化 round-trip，不是 LLM 输入面。** 知道自己哪里没设防、以及为什么不需要，比到处 try/except 更能说明边界在哪。"

### 2.2 `FixType` —— [verdict.py:38-42](../src/adversarial/verdict.py#L38-L42) ⚠️ 名字和值是错位的

| 枚举成员名 | 值 | 语义错位 | 干什么 |
|---|---|---|---|
| `IN_PLACE` | `"in_place"` | 否 | 原地修正：数字/日期/人名直接替换 |
| `SUPPLEMENTARY` | **`"search"`** | ✅ **错位** | 补充检索：无出处的论断 → 触发新搜索 |
| `REMOVAL` | `"removal"` | 否 | 整段移除：高置信幻觉段落直接删 |

**实测确认的后果：**

```
Issue.from_dict(fix_type='supplementary')  → ValueError: 'supplementary' is not a valid FixType
Issue.from_dict(fix_type='search')         → FixType.SUPPLEMENTARY   ✅
```

**为什么故意这么设计？** 因为序列化出去的值是**给 LLM 看的**：`"fix_type": "search"` 比 `"supplementary"` 对模型更直观。同理 `Dimension.FACTUAL = "fact_check"`（[verdict.py:47](../src/adversarial/verdict.py#L47)）也是错位的，值对齐的是 prompt 模板的语义。

**这是一个可以讲出深度的设计决策：**

> "我的枚举**值面向序列化的读者（LLM 和人类看 JSON），名面向代码的读者（语义）**。两者最优解不同，我选了对齐序列化。代价是**代码里写 `FixType.SUPPLEMENTARY`、日志里打印 `search`，grep 代码时对不上**。如果重做，我会加一个 `_VALUE_ALIASES` 映射同时接受两种写法，让反序列化更宽容。"

### 2.3 `Dimension` —— [verdict.py:45-51](../src/adversarial/verdict.py#L45-L51)

就是 §1.2 那张表的左列。五个维度同时是 `DIMENSION_WEIGHTS` 的键空间，也是 `compute_overall` / `compute_delta` / `compute_priority` 三个函数的共同定义域。

## 3 · 三个 dataclass = 一轮循环的完整数据切片

### 3.1 `Issue` —— 一条问题（[:58-111](../src/adversarial/verdict.py#L58-L111)）

六个字段（[:70-75](../src/adversarial/verdict.py#L70-L75)），**全流程不改一个字段**：

| 字段 | 作用 | 谁填 |
|---|---|---|
| `severity` | 严重级别 | Red Agent |
| `dimension` | 属于哪个攻击维度 | Red Agent |
| `description` | 自然语言描述 —— **传给 Blue Agent 的「作战指令」** | Red Agent |
| `location` | 报告中的位置 | Red Agent（可能为空） |
| `fix_type` | 建议怎么修 | Red Agent |
| `evidence` | 支撑证据片段 | Red Agent |

**一份 `Issue` 从「Red 发现」→「算法排序」→「Blue 修复」→「震荡检测集合」→「存档」全程是同一个对象。** 单一数据源、无中间态转换——这是好设计，值得主动讲。

#### 3.1.1 ⭐ `__hash__` **必须手写**，这不是可选优化

[:98-111](../src/adversarial/verdict.py#L98-L111)：

```python
def __hash__(self) -> int:
    """用于 resolved_issues 集合去重：基于核心字段生成确定性 hash。"""
    return hash((self.severity, self.dimension, self.description, self.location, self.fix_type))
```

**关键机制（实测验证，`outputs/m5_verdict_metrics.json` §1）：**

`@dataclass` 的默认行为是：`eq=True`（默认）+ `frozen=False`（默认）→ **`__hash__` 被置成 `None`，这个类变成不可哈希**。这是 Python 的刻意设计：可变对象且可比较 → 哈希不稳定 → 禁止当字典键。

```
只写 __eq__ 的 dataclass:  __hash__ = None  →  unhashable type
真正的 Issue:              __hash__ = <function Issue.__hash__>  →  可入 set ✅
```

而 [loop.py:88](../src/adversarial/loop.py#L88) 正是：

```python
resolved_issues: set[Issue] = set()
```

> 🚨 **所以：如果这里不手写 `__hash__`，`loop.py:88` 会在运行时直接 `TypeError: unhashable type: 'Issue'`。**

**面试话术：**
> "`Issue` 要放进 `set` 做跨轮去重，但 `@dataclass` 在 `eq=True, frozen=False` 时会把 `__hash__` 置为 `None`——**所以我显式实现了 `__hash__`，不是为了性能，是为了让这个类能被哈希。**"

**这是本文里最值得讲的一个 Python 机制点**，因为大多数人只知道"dataclass 方便"，不知道它**默认让类不可哈希**。

#### 3.1.2 ⭐ 相等性**刻意排除** `evidence`

看字段列表：`severity / dimension / description / location / fix_type` 五个——**`evidence` 被排除在外。**

实测：

```
a = Issue(MAJOR, FACTUAL, "数字错了", "para3", IN_PLACE, "来源A原文")
b = Issue(MAJOR, FACTUAL, "数字错了", "para3", IN_PLACE, "完全不同的证据")
a == b  →  True        # evidence 不同但判等
{a, b}  →  去重后剩 1 条
```

**这是故意的、且正确的。** 理由：`evidence` 是「支撑这个判断的原文摘录」，**同一个问题在不同轮次可能摘到不同片段**（报告改了、检索结果变了）。如果算进相等性，同一个问题会被判成两个不同问题，跨轮去重直接失效。

> **一句话**：**`evidence` 是论据，不是问题的身份。** 身份 = 谁在哪个维度上、对哪个位置、提了什么性质的错。

#### 3.1.3 🚨 但这套机制让「震荡检测」几乎失效（**修正 02 讲义的乐观评价**）

`description` 是 **LLM 生成的自由文本**。而震荡检测（[loop.py:104](../src/adversarial/loop.py#L104)）要求：

```python
reappeared = resolved_issues.intersection(set(verdict.issues))
```

**集合求交集 = 要求逐字完全一致。** 实测：

```
i1 = Issue(MAJOR, FACTUAL, "2024年市场规模应引用IDC数据", "para2")
i2 = Issue(MAJOR, FACTUAL, "市场规模数字缺少 IDC 来源引用", "para2")
i1 == i2  →  False      # 同一个问题、同义改写 → 判不等 → 从交集里漏掉
```

**两轮描述同一问题的措辞几乎不可能逐字复现**（LLM 采样本身有随机性）。所以：

> **震荡检测的实际检出率远低于设计意图。** 它是一段**结构正确、但在真实数据上几乎不会触发**的代码。

⚠️ **【对 [02-核心模块细节笔记.md](02-核心模块细节笔记.md) 第 3.3 节的修正】**：02 讲义把震荡检测评价为「这一条里最有说服力的设计，要主动讲」。**这句话现在危险了**——如果面试官顺着问「你怎么判断两轮是同一个问题？」，照 02 那样答会当场卡住。

**正确的讲法（承认取舍，而不是吹）**：

> "震荡检测的逻辑是：把已经成功修复过的问题存进一个集合，下一轮攻击如果又报出同一个问题，就判定为震荡、立刻停止——**因为说明修改在互相抵消，继续跑是浪费预算**。
>
> **但我对这套去重的实际灵敏度是清楚的**：相等性判断包含自然语言描述字段，而模型两轮之间的措辞很难逐字复现，所以**真实的检测率远低于它该有的水平**。
>
> **正确做法是用 `(dimension, location, severity)` 三元组做键、忽略描述文本，或者干脆上语义相似度匹配。** 我当时的取舍是**宁可漏报也不要误报**——因为误报会在报告还有救的时候强制中止整个循环，代价比多跑几轮更高。**这个取舍我认为方向是对的，但我知道它的检出率上限。**"

**为什么"宁可漏报"能站住**：[loop.py:111-115](../src/adversarial/loop.py#L111-L115) 一旦判定震荡就 `break`，**直接放弃后续所有轮次**。误报的代价（提前中止、带病交付）确实高于漏报（多跑几轮，被 `max_rounds` 兜住）。

### 3.2 `RedVerdict` —— 一次攻击的完整结果（[:114-147](../src/adversarial/verdict.py#L114-L147)）

```python
dimension_scores: dict[Dimension, float] = field(default_factory=dict)
overall_score: float = 0.0
issues: list[Issue] = field(default_factory=list)
raw_feedback: str = ""
```

**四个值得讲的点：**

**① `field(default_factory=dict)` 是必须的，不能写 `= {}`。**
dataclass 的默认值在**类定义时求值一次**，所有实例会共享同一个可变对象 → 一个实例 `append` 污染全部实例。**Python 基本功，必答。**（同一个坑在 [04 第 0 步](04-规划器与JSON解析.md) 的语法工具包和 [03 第 0 步](03-编排引擎.md) 里都出现过。）

**② `raw_feedback`（[:127](../src/adversarial/verdict.py#L127)）是「给未来的自己留证据」。**
存的是五个维度 prompt 的**原始模型输出**（拼接见 [red_agent.py:316](../src/adversarial/red_agent.py#L316)）。

> **设计原则**："解析结果和原始文本我都留。**解析是有损的**——如果我的正则漏掉了模型输出里的某条 issue，光看结构化数据永远不知道。**留 raw 是可审计性的底线。**"

**③ `to_dict` 里的 `{k.value: v ...}`（[:131](../src/adversarial/verdict.py#L131)）是枚举↔JSON 的桥。**
JSON 的键必须是字符串，而 `dict[Dimension, float]` 的键是枚举对象。`json.dumps` 对枚举键会直接失败，**所以这一步不是顺手，是必需。**

**④ `from_dict` 里的 `Dimension(k)`（[:141](../src/adversarial/verdict.py#L141)）是反向的脆弱点。**
实测 `RedVerdict.from_dict({"dimension_scores": {"mind_reading": 5.0}})` → `ValueError: 'mind_reading' is not a valid Dimension`。**无 try、无降级、一个未知键就让整份存档读不出来。**（同 §2.1 的边界论证。）

### 3.3 `FixOperation` —— 一次修复的记录（[:150-171](../src/adversarial/verdict.py#L150-L171)）

issue: Issue          # 修的是哪个问题（组合，非继承）

**`issue` 字段是「组合」关系的体现**：持有 `Issue` 对象建立关联，而不是把 severity/dimension 再抄一遍。**好处是「一条问题 → 它的所有修复尝试」可以直接从对象图里查。**

## 4 · `VerdictEngine` = 一个**没有实例**的类 + 四个纯函数

[:178](../src/adversarial/verdict.py#L178)。它的方法签名全是 `@classmethod` / `@staticmethod`，**没有 `__init__`**。

**这个类的真实身份是「命名空间 + 一张配置表」。** 用 class 而不是模块级函数，是因为：① 命名空间隔离（`VerdictEngine.DIMENSION_WEIGHTS` 比全局名清晰）；② **权重表和用它的公式物理放在一起**——权重的语义只有配合公式才能理解。

> **被问「为什么用 class 而不是模块函数」**："**它不是对象，是命名空间。** 用 classmethod 而非实例方法，是因为**这个引擎无状态**：同样输入永远同样输出。"

### 4.1 `compute_overall` —— 五维加权平均（[:210-230](../src/adversarial/verdict.py#L210-L230)）

```python
if not dimension_scores:
    return 0.0
total = 0.0
weight_sum = 0.0
for dim, score in dimension_scores.items():
    w = cls.DIMENSION_WEIGHTS.get(dim, 0.0)
    total += w * max(0.0, min(10.0, score))   # ← clamp
    weight_sum += w                            # ← 只累加【真实存在】的维度
if weight_sum == 0.0:
    return 0.0
return total / weight_sum                      # ← 重新归一化
```

**实测（`m5_verdict_metrics.json` §3）：**

| 输入 | 输出 | 说明 |
|---|---|---|
| 五维全 8.0 | **8.0** | 基准 |
| 只给前三维都 8.0 | **8.0** | ✅ **缺失维度不扣分，重新归一化** |
| 只给 `FACTUAL=10, COVERAGE=0` | **7.5** | `(0.30×10 + 0.10×0) / 0.40` |
| `{}`（空） | **0.0** | 防零除 |
| `FACTUAL=99`（越界） | **10.0** | clamp 生效 |

**⭐ 最重要的一处设计：`weight_sum` 只累加实际出现的维度。**

把它和**同一个项目里的另一个加权分函数**对照——评测层的 [rule_based.py `composite_score`](../evaluation/metrics/rule_based.py)：

| | 缺失维度取值 | 权重是否计入 | 后果 |
|---|---|---|---|
| 评测层 `composite_score` | **0.0** | ✅ 计入 | 少给一个指标 → **固定扣分**。实测封顶 **0.75** |
| M5 `compute_overall` | 不参与 | ❌ 不计入 | 少给一个维度 → **重新归一化**，实测仍 **8.0** |

> **面试话术（这一段含金量最高）**："我在项目里有两个加权平均函数，**故意的口径相反**。评测层的那个是『缺失即 0 分』，因为**评测语义是：你答不出这个指标，就是没做到**——这也正是我在审计里发现一个封顶 bug 的来源。而对抗循环这个是『重新归一化』，因为**它的语义是：在能观测到的维度上有多好**，缺维度属于数据不完整，不是质量差。
>
> **同一个词『加权平均』，在两种业务语义下正确的实现是相反的。**"

**另外两处：**

**① `max(0.0, min(10.0, score))` clamp 住 LLM 越界输出。** LLM 常返回 0-100 分制或负数，不 clamp 会让综合分荒谬。

> 这是"**对 LLM 输出不信任**"的具体落地：**结构上不信任**（解析有 fallback），**数值上也不信任**（这里 clamp）。

**② `if weight_sum == 0.0: return 0.0` 防零除。** 传入一个键完全不认识的字典时，`w` 全 0，返回 0.0 而不是 `ZeroDivisionError`。**防御性写法正确。**

### 4.2 `compute_delta` —— 收敛判据（[:232-258](../src/adversarial/verdict.py#L232-L258)）

```python
all_dims = set(prev.keys()) | set(curr.keys())     # ← 并集
sq_sum = 0.0
for dim in all_dims:
    p = max(0.0, min(10.0, prev.get(dim, 0.0)))    # ← 缺的补 0
    c = max(0.0, min(10.0, curr.get(dim, 0.0)))
    sq_sum += (c - p) ** 2
return math.sqrt(sq_sum)                            # ← 欧氏距离
```

**五维空间的欧氏距离。** 比「平均绝对差」好在**对「变化集中在少数维度」更敏感**：

| 情形 | 绝对差之和 | 欧氏距离 |
|---|---|---|
| 只有 FACTUAL 掉 2 分 | 2.0 | **2.0** |
| 五维各掉 0.4 分 | 2.0 | **0.894** |

**绝对差之和无法区分，欧氏距离能。** 而「某个维度崩了」恰恰是最该停止循环的信号（Blue 修一处、引入一处严重事实错误）。

#### ⚠️ 实测出的量纲问题

```
每维 +0.1（共5维） → delta = 0.2236      ← 已经超过阈值 0.2
每维 +0.2（共5维） → delta = 0.4472
理论最大（全0→全10）→ delta = 22.3607
阈值 0.2 占理论最大值 **0.89%**   →  等价于「五维平均每维变化 0.0894 分」
```

**阈值 `0.2`（`configs/default.yaml:174`）极紧。** 五维平均每维变 0.1 分，delta 就 0.2236 > 0.2，判为「还在变，继续修」。

> **⚠️ 待确认（与 [02 第 3.3 节](02-核心模块细节笔记.md) 的「待确认」呼应，这里给出实测答案）**：02 讲义推测「变化量收敛这个条件实际上很难触发」。**实测确认了量纲比例（0.89%），但停止原因无法从产物反推**——见 §5.4。所以准确说法是：**「delta 收敛」要求两轮几乎无变化（每维 <0.09 分），只在报告基本定型时才可能触发；但它在 5 次实测里到底触发了没有，我不知道，因为轮次记录没落盘。**

#### ⭐ 一个容易答错的点：`delta` 比的是「哪两轮」

[loop.py:128-132](../src/adversarial/loop.py#L128-L132)：

```python
delta = 0.0
if prev_scores is not None:
    delta = VerdictEngine.compute_delta(prev_scores, verdict.dimension_scores)
prev_scores = copy.deepcopy(verdict.dimension_scores)
```

**两个输入都是「Red 攻击时」的分数**（`verdict` 是本轮 [:96](../src/adversarial/loop.py#L96) 攻击的产物，`prev_scores` 是上一轮攻击的产物）。

> **所以 `delta` 衡量的是「上一轮 Blue 修复带来的边际收益」**，不是「本轮修复的效果」。**这个语义是正确的**——你想知道"修了之后分有没有变好"，就得比"修前 vs 修前"（跨轮）。

**被追问「delta 是哪两轮的差」，必须立刻答出**：*"第 N 轮攻击分减去第 N−1 轮攻击分，中间隔着的是第 N−1 轮的修复动作。所以它测的是修复的边际收益，不是攻击的波动。"* **答错说明没真读过代码。**

**顺带：[:132](../src/adversarial/loop.py#L132) 的 `copy.deepcopy`** 是必需的——不深拷贝的话 `prev_scores` 会和 `verdict.dimension_scores` 指向同一对象。**和 [dag.py:91](../src/planner/dag.py#L91) 的 `dict(...)` 是同一个思路：跨轮次保存快照必须拷贝。**

### 4.3 `compute_priority` —— 决定先修哪个（[:260-276](../src/adversarial/verdict.py#L260-L276)）

```python
sw = cls.SEVERITY_WEIGHTS.get(issue.severity, 1.0)     # 10 / 5 / 1
dw = cls.DIMENSION_WEIGHTS.get(issue.dimension, 0.1)   # 0.30 ~ 0.10
fd = cls.FIX_DIFFICULTY.get(issue.fix_type, 1.0)       # 1.0 / 0.8 / 0.6
return sw * dw * fd                                     # ← 连乘
```

被 [blue_agent.py:204-208](../src/adversarial/blue_agent.py#L204-L208) 用来排序（`reverse=True`，分大优先）。

**实测取值范围（`m5_verdict_metrics.json` §5）：**

```
最低: 0.0600   (MINOR / COVERAGE / SUPPLEMENTARY)
最高: 3.0000   (CRITICAL / FACTUAL / IN_PLACE)
跨度: 50.0 倍
```

**为什么用连乘而不是相加？**

- **加性**（`sw + dw + fd`）：三个因素可以互相补偿
- **乘性**：**任一因素接近 0，整体就接近 0；三个都要高才排前面**

**乘性是正确的**，因为真实语义是「与」关系：一个 MINOR 的问题，哪怕它在最重要的维度、又快又好修，**也不该排在 CRITICAL 前面**。50 倍跨度保证这一点。

### 4.4 `to_json` / `from_json`（[:278-286](../src/adversarial/verdict.py#L278-L286)）

```python

```

**`ensure_ascii=False` 是必需的**——否则中文全部变成 `中文`。**这个参数在中文项目里极易漏**，漏了之后 round-trip 仍正常，只是存档变成天书。

### 5.2 🚨 坑 2 详解：整套审计链在运行时被丢弃（**本文最硬的发现**）

**序列化能力实现了，但没有任何代码调用它。** 这和评测层那个「`compute_composite_score` 从未被调用」是同一类缺陷。

**面试话术（这是主动坦白里最值钱的一条）：**
> "有个我自己审出来的问题：**对抗循环的每轮评分记录构造得很完整——维度分、轮间变化、修复操作、停止原因都打包了——但编排器拿到之后只用了它的长度（算轮数），记录本身没有落盘。** 配套的序列化方法我写了但从来没被调用，配置里那个 `save_logs` 开关也没有代码消费它。

>
> 修法很简单——把 history 的 `to_dict()` 写进 `memory_store` 或按 `session_id` 落盘。**我当时没做，是因为循环是先写好的、落盘是后加的，中间那条线就断在那里。**"

**为什么这条特别值钱**：它同时展示了 ① 你读过 `orchestrator` 和 `loop` 的**接缝**（不是只读单个模块）；② 你会做「配置项有没有接线」这类横向审计；③ 你能给出修法。

### 5.3 坑 3 详解：`FIX_DIFFICULTY` 名字反了，且与轮数上限有交互

[:203-208](../src/adversarial/verdict.py#L203-L208)：

```python
# fix_type → 难度系数（用于优先级计算）
FIX_DIFFICULTY: dict[FixType, float] = {
    FixType.IN_PLACE: 1.0,        # ← 最容易修，拿最高乘数
    FixType.REMOVAL: 0.8,
    FixType.SUPPLEMENTARY: 0.6,   # ← 最难（要重新检索），拿最低乘数
}
```

**名字叫「难度系数」，但值越大代表越「容易」。** `IN_PLACE = 1.0` 是**最不需要搜索、最快**的修复方式。实测确认「难度名与乘数方向相反 = True」。所以这张表实际是**「性价比系数」/「易修程度」**，命名反了。

**更重要的是它的后果。** `SUPPLEMENTARY`（乘 0.6）对应的恰恰是 [verdict.py:41](../src/adversarial/verdict.py#L41) 注释自己写的 **"unsourced claims → 触发新搜索"**——**没来源支撑的断言，也就是幻觉高发区。**

**静态优先级 × 硬轮数上限的交互：**

> **最难修、也最重要的那类问题（无来源断言）被排到最后；如果轮次预算先耗尽，它们永远修不到。**

⚠️ **【重要修正：我在对话里第一次讲这个坑时用的是函数默认值 `max_rounds=3`，那是错的】**

实测真实配置是 **10 轮**（`configs/default.yaml:168`），所以我当时说的"3 轮用完就修不到"**过强了**。准确的表述是：

| | 轮数 | 截断风险 |
|---|---|---|
| 函数默认值 | 3 | **高**——两轮修完别的就没了 |
| **工程实际值** | **10** | **中**——松得多，但实测 5 次里 **2 次跑满 10 轮**（§6.1），说明上限**确实会绑定** |

**实测支撑**：5 份真实报告的对抗轮数是 **2 / 2 / 10 / 10 / 5**——**2/5 命中上限**。

> **面试话术**："优先级是 `严重度 × 维度权重 × 修复系数` 连乘。修复系数我是为了让**快速见效的修复先做**——轮数预算有限时，同样的时间能修掉更多问题。**但代价是『需要发起新检索』那类问题被乘 0.6 排到最后，而它们恰恰是无来源断言、幻觉高发区；实测 5 次里有 2 次跑满 10 轮上限，所以这个截断是真实存在的风险，不是理论担忧。**
>
> **如果要改，我会把这个静态乘数改成『随轮次递减的惩罚』——前几轮压后，最后几轮强制前置。目前的公式是静态的，没有考虑『还剩几轮』。**"

**这个回答展示的是**：不只读懂了公式，还看到「静态优先级 + 硬轮数上限」这个组合的**交互后果**，并给出了修法方向。**面试官问"这个公式有什么问题"，就是在等这个。**

### 5.4 坑 4 详解：停止原因不可分辨

[loop.py:161-176](../src/adversarial/loop.py#L161-L176)：

```python
if round_idx >= self.max_rounds:            # ① 先判轮数
    return f"max_rounds_reached({self.max_rounds})"
if overall_score >= self.score_threshold:   # ② 再判分数
    return f"score_threshold_met(...)"
if round_idx > 1 and delta < self.delta_threshold:   # ③ 最后判变化量
    return f"delta_converged(...)"
```

**探针实测（`m5_verdict_metrics.json` §9）：**

| round | score | delta | 返回的 stop_reason |
|---|---|---|---|
| 1 | 9.6 | 0.0 | `score_threshold_met(9.60>=9.5)` |
| 2 | 9.6 | 0.05 | `score_threshold_met(9.60>=9.5)` |
| 2 | 5.0 | 0.05 | `delta_converged(0.050<0.2)` |
| 2 | 5.0 | 1.20 | `""`（继续） |
| 9 | 9.9 | 0.0 | `score_threshold_met(9.90>=9.5)` |
| **10** | **9.9** | **0.0** | **`max_rounds_reached(10)`** ← 分数达标被掩盖 |

**两个问题：**

**① 优先级顺序让「跑满轮数」在最后一轮必然覆盖其他原因。** 在第 10 轮，即使分数到了 9.9，返回的也是 `max_rounds_reached`。

**② 更实际的问题：`stop_reason` 是 `history` 里的一个字段，而 `history` 不落盘（§5.2）。所以从 `outputs/` 只能看到「轮数」，无法反推早停原因。**

**实测佐证**：5 份报告的轮数是 2 / 2 / 10 / 10 / 5。
- 轮数 **10** 的两份 → 可以确定是 `max_rounds_reached`（因为第 10 轮必然走 ①）
- 轮数 **2** 和 **5** 的三份 → 停在 `score_threshold_met` 还是 `delta_converged`？**无法区分。**

> **面试话术**："收敛判据是三选一，但**检查顺序把『轮数用尽』放在最前**，所以最后一轮的停止原因永远是 `max_rounds_reached`，会掩盖『其实分数也达标了』这个信息。更实际的问题是**停止原因存在每轮记录里、而记录不落盘**——所以事后我只能看到『跑了 2 轮』，**答不出『为什么是 2 轮』**。对调参来说这是最需要的信息。"

### 5.5 坑 5 详解：`final_score` 是**修复前**的分数

**先看执行顺序**（[loop.py:92-153](../src/adversarial/loop.py#L92-L153)）：

```
:96   verdict = await self.red_agent.attack(current)      ← ① 攻击（打分）
:118  fixed_report, operations = await blue_agent.defend(current, verdict)  ← ② 修复
:135  stop_reason = self._check_convergence(round_idx, verdict.overall_score, delta)  ← 用 ① 的分
:157  current.final_score = history[-1]["overall_score"]  ← 同样是 ① 的分
```

**`verdict` 在 `defend` 之前产生**，所以：

- 收敛判据用的是 **「本轮修复前」** 的分数
- `final_score` 也是 **「最后一轮修复前」** 的分数

**且它和 dataclass 的 docstring 矛盾：**

| 来源 | 说法 |
|---|---|
| [schemas.py:124](../src/orchestrator/schemas.py#L124) | `final_score`: 最终综合评分（**由外部评测模块写入**） |
| [loop.py:157](../src/adversarial/loop.py#L157) | `current.final_score = history[-1]["overall_score"]`（**对抗循环自己写的**） |

**实现和注释分家了。** 而且 `final_score` **不出现在交付的 .md 报告里**——实测 5 份报告全部 `final_score_是否出现在报告里 = false`（runner.py:355-375 只写 置信度/搜索轮数/重规划/对抗轮数/总耗时）。它的实际消费者是 M6 进化模块（[collector.py:57](../src/evolution/collector.py#L57)）。

> **面试话术**："`final_score` 落的是**最后一轮攻击时、修复生效前**的分数——因为再攻击一次才能拿到修复后分数，而那会多花一轮模型调用。**所以这个分是保守下界，真实交付的报告质量应该比它高。**
>
> 如果追问『那你凭什么说修复有效』，我会说：**修复效果体现在『轮间 delta』和『最后一轮比第一轮高多少』上，不是 `final_score` 的绝对值。** 另外这个字段的 docstring 说是外部评测模块写入的，实际是循环自己写的，**注释和实现不一致，这是我该修的。**"

### 5.6 坑 6 / 坑 7 详解（次要）

**坑 6：`FixOperation` 没有 `from_dict`。** 实测：

```
Issue        to_dict ✅  from_dict ✅
RedVerdict   to_dict ✅  from_dict ✅
FixOperation to_dict ✅  from_dict ❌   ← 单向
```

**后果**：轮次历史里的 `fix_operations` 只能写出、不能读回。**不支持「从存档恢复一个中断的对抗循环」（断点续跑）。**

> 话术："三个数据类里 `FixOperation` 只有单向序列化，因为**修复操作是『只写日志』语义**——我只需要事后能读，不需要程序化回放。**要支持断点续跑就得补 `from_dict`，目前不支持。**"

**坑 7：`from_dict` 无降级。** 实测三例全部抛 `ValueError`（未知 severity / 未知 dimension / 用枚举名当值）。**round-trip 场景安全，但人工编辑过的存档会直接崩。** 同 §2.1 的边界论证。
