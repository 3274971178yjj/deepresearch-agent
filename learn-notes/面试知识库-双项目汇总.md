### 项目一 · Shopping-GRPO:长程购物Agent的可复现后训练与评测系统

#### 1.1 一句话定位与三阶段流水线

**一句话定位:** 训练一个 2B 小模型(Qwen3.5-2B),用「教师示范 + 监督微调 + 强化学习」三阶段流水线,把它变成能在模拟购物网站 ShopSimulator 里完成长程购物任务(平均 10+ 步、最多 35 步工具调用)的 Agent,并建立一套可复现、可审计的评测体系。

| 阶段 | 干什么 | 为什么不能跳过 |
|---|---|---|
| ① 教师轨迹采集(DeepSeek-V4-Flash 在环境内真实执行,temp=0) | 强模型先跑通任务,把成功过程录成教材 | 基座严格成功率 0%、82% 轨迹走不到终局,直接进 RL 时每条 rollout 全负分、组内全等 → advantage 全 0 → 梯度恒为零(冷启动死局)。RL 需要"偶尔能成功"的初始策略 |
| ② 课程式 SFT(三阶段重建 LoRA) | 教 2B 模型工具协议与购物策略 | 把成功率从 0% 拉到 60.5%,GRPO 才有正负样本对比的原料;SFT 还把 Guard 非法动作从 752 次降到 52 次 |
| ③ 在线 GRPO(veRL 0.8 + 自研适配层) | 模型在环境里按 Reward v3 自我试错修正 | 补 SFT 上限:教师没教的局面(目标没货→合法替代)由模型自己探索出来(GRPO 后出现 1 条 valid_alternative) |
| ④ 冻结评测(Final-200 Clean + 双 Judge) | 同一张卷子验收三个阶段 | 环境/数据集/Judge 全冻结,分数差才能归因于训练而非"尺子变了" |

**不能"直接 SFT"的原因:** 2498 条教师轨迹只有 41% 通过验收,六成是脏的,SFT 上限=教材上限,且学不到教师没见过的局面。**不能"直接原生 veRL+GRPO"的原因(五连坑,每坑一个自研模块):** ①环境协议不通(veRL 工具抽象只有"execute 返回文本",ShopSimulator 是有租约的 HTTP 仿真服务)→ AgentLoop 适配层;②奖励太简陋 → Reward v3;③组内奖励全等 → advantage 归零、原生框架无限重采空转 → 有界动态采样;④缺训练诊断 → training_diagnostics.jsonl;⑤评测不可复现 → 数据集治理 + SHA-256 冻结 + 双 Judge。

**分界线(必被问"哪些是你做的"):** veRL 自带 = GRPO 训练循环(RayPPOTrainer)、vLLM 采样、LoRA 训练、Hydra 配置、ToolAgentLoop/BaseTool 基类;项目自研 = 工具 schema 与动作翻译、HTTP 环境客户端与租约管理、动作守卫、observation 投影与上下文压缩、终局奖励组装、有界动态采样(打补丁)、诊断日志、TRACE、评测全套;ShopSimulator 环境**只读不改**(奖励规则和商品库冻结在里面)。

#### 1.2 整体数据流

一条任务从头到尾:购物指令 → 教师模型 V4-Flash 在 ShopSimulator(HTTP :5700,租约 reset→step→release,商品库 23,421 个真实商品)内真实执行 → 每条轨迹终局由环境内 Reward v3 打分,**2498 条 → 验收合格 1026 条(41.07%)→ 重新策展成 1192 条(1073 训 / 119 验)→ 排成 A/B/C 三阶段课程** → 每阶段训练一个新 LoRA 挂在上阶段合并回基座的权重上,超长样本(>24K)整条丢弃 → stage-c/merged 作为 GRPO 唯一起点 → veRL rollout(n=4/题):模型生成工具调用 → 自研动作守卫校验 → 翻译成 `search[...]`/`click[...]` 环境动作 → HTTP step → observation 渲染+投影后回填对话;终局由环境 Reward v3 裁决、适配层三道验收后结算 → 训练侧动态采样质量门按组筛查(全等组/含无效组丢弃,最多补采 3 批,连跳 10 次熔断)→ 有效组进 GRPO 更新,全过程写 training_diagnostics.jsonl → 导出 merged LoRA → Final-200 Clean(哈希冻结、与训练 task_id 零重叠)上每题 1 次确定性 rollout → 三层评测(代码硬检查 → V4-Flash 冻结 Rubric → V4-Pro 五维盲评)→ 四面板报告 + 6 模型横向对比。

轨迹三流结构(样例 `examples/trajectories.jsonl`):messages(SFT 原材料,assistant content 为空只有 tool_calls)/ steps(逐步审计流,中间步 reward 全 0)/ terminal_result(Reward v3 裁决)。三条典型:example-gold(+1.0)/ example-wrong(-0.85,买错颜色,weighted_score 仍有 0.2 但硬门一票否决)/ example-max-steps(-0.5,重复搜索步数耗尽)。

#### 1.3 核心机制逐条

**Reward v3 确定性终局奖励** ｜ 解决:不用奖励模型(RM 有 reward hacking/训练漂移/随机性/延迟成本四宗罪;购物是可验证任务,"能验证的就不要学习"),给 RL 提供可信、可复现的唯一训练信号 ｜ 实现:规则冻结在环境 reward.py,项目侧只做结构校验不重算。①需求开跑前编译冻结(模型不能改考题);②硬门控一票否决:类目门+预算门,任一不过 → wrong_purchase **-0.85**;③软约束分级加权:品牌 0.35 / 型号 0.25 / 核心功能 0.25 / 关键规格 0.15,只考任务激活的维度,满分要求匹配分=1 且证据覆盖率=1(蒙对的不算);④终局 9 档:gold +1.0 / **valid_alternative +0.55**(硬门+全部偏好满足但非目标 ASIN,把目标从"找那个商品"改成"满足约束集")/ 部分满足 min(0.25, -0.30+0.55×S) / 合理放弃 -0.15(≥2 组结果页且 ≥2 候选且 0 个合格候选)/ 过早放弃 -0.35 / 步尽 -0.5 / 死循环 -0.65 / 买错 -0.85 / **证据不足 0 分但标 invalid**(数据问题不当模型错,训练侧隔离不进梯度)。惩罚阶梯塑造"宁谨慎放弃,不乱买"。中间步 reward 全 0,代价是奖励稀疏(TRACE 的动机)。四岔路顺序不能换:先判 unverifiable 再判 fail(证据缺失不能定罪为买错) ｜ 代码:`environments/ShopSimulator/shop_env/web_agent_site/engine/reward.py:32-53`(常量表,已核)、`reward.py:353` evaluate_purchase 四岔路、项目侧 `src/shopping_grpo/training/grpo/adapter/runtime.py:113` validate_reward(已核)与 `runtime.py:218` reward_breakdown

**有界动态采样** ｜ 解决:GRPO 同题 n=4 用组内相对分(减组均值,本项目 norm_adv_by_std_in_grpo=false 不除标准差),组内奖励全等 → advantage 全 0 → 梯度全 0;Reward v3 离散 9 档使全等高频(早期全 -0.85,后期全 +1.0);原生 veRL 遇全等组无限重采且静默 ｜ 实现:在"生成完"和"算梯度"之间插筛子,按 uid 分组逐组体检,判定基准是 terminal_utility;丢弃两类组:sampling_invalid(含 infrastructure_invalid/reward_unverifiable/overlong,**无效优先于全等**——错值有差异比没差异更危险)和 constant_reward(极差 ≤ 1e-8,浮点不能比 ==);不足则补采最多 **3 批**,仍不足跳过本次更新(写 skipped_update 日志),连续跳过 **10 次** RuntimeError 熔断停训;补丁还把 global_steps+1 挪到优化器真正更新后(step 对齐真实学习步);每步进优化器的 prompt 数严格等于 train_batch_size ｜ 代码:`src/shopping_grpo/training/grpo/dynamic_sampling.py:231` select_reward_varying_groups(已核)、`configs/grpo.yaml:106-111`(已核)

**action-only loss mask** ｜ 解决:不 mask 则 loss 被页面文本淹没、浪费 2B 容量、诱导模型幻觉补页面 ｜ 实现:labels 全置 IGNORE_INDEX=-100(CrossEntropyLoss 自动忽略),只把 assistant 回合 token 段打开算 loss;边界定位不硬编码——用 chat template 分别渲染"回合前+生成提示"和"回合前+该回合",取公共前缀确定起点,兼容模板微小格式差异;超长样本**整条丢弃绝不截断**(截断可能切断工具调用) ｜ 代码:`src/shopping_grpo/training/sft/dataset.py:56` build_supervised_example(已核),-100 定义在 dataset.py:14

**三阶段课程 SFT** ｜ 解决:一次性混训三大风险——难度失衡(梯度被简单样本主导)、学习率一刀切、能力互相干扰/灾难性遗忘 ｜ 实现:难度标签由大模型逐条打,**任务内在难度与轨迹复杂度分开打**(不能因教师跑得曲折就说任务难);按规则分三桶:simple→foundation(284 条,256 训),medium 且不需改写不需比较→constraints(603 条,543 训),其余(需改写/比较的 medium + 全部 hard)→strategy(305 条,274 训);阶段累积式:A=foundation 256 条 lr 1e-4 → B=+constraints 799 条 lr 7e-5 → C=全部 1073 条 lr 5e-5,各 1 epoch;**逐阶段重建 LoRA**:每阶段新初始化 LoRA(r=16/alpha=32)挂在上阶段 merge 回基座的新权重上——旧知识固化、容量不占、可回退;质量合同 _validate_row 六道硬门槛(含终局分数文本必须已洗净,防偷看答案) ｜ 代码:`scripts/prepare_sft_curriculum.py:13-26`(STAGE_CONFIG)、`:100-109`(_bucket)、`data/sft_curriculum/manifest.json`(冻结 task_id + 源文件 SHA-256)。**已知隐患(主动说破)**:累积课程造成隐式重加权——简单题学 3 遍/难题 1 遍,有效曝光 2128 而非 1073,难题占比 9.3%→4.7%,简单题名义 LR 总量是难题 4.4 倍;项目定性为"待验证假设,非因果结论",修法不能靠复制难题

**24K 长上下文** ｜ 解决:一条轨迹 9-12 步(最长 35 步)轻松上万 token,截断会切掉终局决策 buy_now 和支撑它的证据,模型学成"无缘无故下单" ｜ 实现:最大序列 24576;显存组合拳 = LoRA(冻结基座)+ 梯度检查点 + batch=1 + 梯度累积 8 → SFT 峰值 **89GiB**,单卡 RTX 6000 96GB 约 3 小时跑完三阶段——"整个流水线在个人可负担硬件上可复现" ｜ 代码:`scripts/run_sft_curriculum.py`(--max-length 24576)、`docs/sft.md:44-54` 配方表

**AgentLoop 适配层** ｜ 解决:veRL 原生把环境当"无状态问答工具",ShopSimulator 是有状态、要租约、环境判终局的"考场"——五个错位:状态/租约/终局/非法动作/奖励口径 ｜ 实现:**不修改 veRL,靠继承+协议接入**,在三个边界插项目逻辑:①生成前上下文预算检查与压缩(预留生成余量 512+安全边距 512,超限终止);②工具返回后 observation 投影(搜索 top20、详情按预算截断,投影失败整条轨迹判无效);③结束时统一从环境状态结算奖励,finally 里必释放租约。配套:ShopSimulatorSession 用 **ContextVar** 做轨迹级状态隔离(16 条并发 rollout 异步交错,全局变量必串线),reset 失败也要还租约、环境版本不符直接报错;ShopSimulatorTool 执行守卫→翻译→HTTP step→终局三道验收(over 且 reward 有限 / reward_version 必须 v3 / validate_reward 通过且 terminal_utility 与 reward 一致),不过标 infrastructure_invalid;**连续 3 次守卫拒绝终止轨迹**;模型一次生成多个工具调用直接终止(环境状态串行演进);`release()` 故意实现成空方法骗过 veRL"每次调用后释放"的协议,真正释放在 AgentLoop finally;gold 目标(_trace_target)绝不进模型上下文,渲染器把 goal/reward 列为 forbidden 字段 ｜ 代码:`adapter/agent_loop.py:29`(已核)、`adapter/tools.py:39`、`adapter/session.py:17`(已核)、`adapter/runtime.py`(50+ 诊断字段)

#### G+ · 专攻:"GRPO 只涨 1.5pp"的三层回答(第 11 讲,必背)

这是全项目最容易被问翻的一题,**按三层说,层层加深**:

- **第一层 · 承认数字不显著**:"SFT 121/200(60.5%)→ GRPO 124/200(62.0%),净增 3 题。但这是**配对**数据:12 道从失败变成功、9 道从成功变失败,净 +3。对 21 个不一致对做双侧 exact McNemar 检验,p≈0.664——**统计上不能区分'真实小增益'和'任务级抽样噪声'**。原因是每题只有一次确定性 rollout,没有方差估计。"
- **第二层 · 讲清"不是训练没用"**:"同一个实验里,这些指标**方向一致地改善**:平均 Reward 0.4729→0.5158、Guard 拒绝 52→38、死循环 27→25、步尽 5→3、买错 7→5,而且**出现了 1 条 `valid_alternative_purchase`**——教师数据里从没有过这种轨迹,是模型自己探索出来的新行为。所以准确表述是'**成功率没明显拉开,但行为在变好**',而不是'训练没作用'。"
- **第三层 · 给原因假设和验证方法(拉开差距的一层)**:"更可能先限制 GRPO 的是 **group 信息量**,而不是算法。每 prompt 只采 n=4,而 SFT 已有 60.5% 的单次成功率,组内很可能全对或全错——**这两种组的 advantage 都是 0,等于白采**。项目已有有界动态采样过滤这类组,但补采上限 3 批。要验证也很便宜:从已有诊断日志量三个东西——**每 step 的 zero-variance group 比例、组内 reward 的唯一值个数、同题 4 条轨迹的唯一工具序列数**。如果 zero-variance 很高,该做的是扩大同题探索(加 n 或调采样),而不是先换更复杂的算法。"

> 三层的价值:第一层证明你会看统计,第二层证明你会看全貌,第三层证明你知道**下一步该测什么**。面试官问"1.5pp"想听的就是第三层。

### 2.3 三层局限清单

### 2.2 九个状态是怎么实现的（**别答错**）

**不是 `if/elif` 链，是字典映射。** [orchestrator.py:84](../src/orchestrator/orchestrator.py#L84) 处 `self._state_handlers = {...}`，每个 handler **返回下一个状态**，主循环用返回值驱动转移。

九个状态 = **7 个正常流转 + REPLANNING + FAILED**：

```
IDLE → PLANNING → DISPATCHING → COLLECTING → SYNTHESIZING → ADVERSARIAL → DONE
                       ↑                                       
                  REPLANNING ──────────┘（回到 DISPATCHING）
任意状态 → FAILED（不可恢复错误）
```

**被追问"为什么用字典不用 if/elif"**：状态到处理器的映射是**静态的**，字典是 O(1) 查表且新增状态不用改主循环；if/elif 是 O(n) 且每加一个状态就得动那个函数。**但真正的理由是**：handler 返回 next state 让**状态转移本身变成了数据**，而不是控制流——这样 REPLANNING 这种"回边"不需要特殊处理。

### 2.3 核心机制逐条（对应简历 6 句）

#### ② 编排引擎 —— 三级降级（**这是全项目最强的部分，讲透它**）

**第一级 · 单任务超时标记继续** — [orchestrator.py:263](../src/orchestrator/orchestrator.py#L263)

```python
await asyncio.wait_for(agent.run(...), timeout=per_task_timeout)
```

超时不抛穿整层，而是记为 `TIMEOUT` 状态、**继续**。语义是"一个子任务失败不阻塞同层其他任务"。

**第二级 · 增量重规划** — 触发条件在 [orchestrator.py:332](../src/orchestrator/orchestrator.py#L332)，判定函数 [orchestrator.py:519](../src/orchestrator/orchestrator.py#L519)

精确阈值（**必背**）：

```
failure_rate > 0.5
  或
(success / total < 0.3  且  failed > 0)

→ 触发 REPLANNING，上限 3 轮
```

注意第二个条件里的 `failed > 0` 是**必要的**：没有它，`total = 0` 时 `success/total` 会除零，而且全成功时 `0 < 0.3` 也会误触发。

**重规划做的事**（[orchestrator.py:492](../src/orchestrator/orchestrator.py#L492) 附近）：

1. **保留** confidence 达标的结果（保留在 memory 中，新任务通过 `context_keys` 引用）
2. `self._results = []` —— **清空**当前结果列表
3. 重新规划剩余子任务

**"为什么清空，不是追加？"** —— 因为重规划会**重新生成任务 DAG**，旧的 DAG 已经不成立了。追加会让结果列表里混进两套任务体系的产物，去重和合成都没法做。**旧结果没有丢，它在 memory 里，通过 `context_keys` 被新任务引用**——这是"清空但不清失"。

**第三级 · 全局超时强制合成** — [orchestrator.py:125](../src/orchestrator/orchestrator.py#L125)

全局 600s 预算耗尽 → 不再跑后续状态，**直接跳 SYNTHESIZING**，用已有结果出报告。宁可要一份不完整的报告，也不要一个超时异常。

> ⚠️ **这一级有个你必须主动说破的真相，见 §2.5 陷阱 6。**

**并发的三层防护**（简历没写，但这是加分点）：

| 层 | 位置 | 作用 |
|---|---|---|
| 全局并发上限 | [orchestrator.py:238](../src/orchestrator/orchestrator.py#L238) `asyncio.Semaphore(max_concurrent)` | 建在**层循环之外** = 全局上限，不是每层重置 |
| 单任务超时 | [orchestrator.py:263](../src/orchestrator/orchestrator.py#L263) `asyncio.wait_for` | 第一道 |
| 层内异常隔离 | [orchestrator.py:286](../src/orchestrator/orchestrator.py#L286) `asyncio.gather(*coros, return_exceptions=True)` | 第二道 |
| Agent 归还 | `finally: await release_agent` | 第三道（防泄漏） |

**"`gather` 里一个任务抛异常会怎样？"** —— `return_exceptions=True` 把它**变成返回值**而不是抛出来，所以同层其他任务不受影响；异常对象在结果遍历时被识别、记为失败。**如果面试官追问"那 `return_exceptions=True` 会不会吞掉本该中断的致命错误"** —— 会，这是**有意的取舍**：研究任务里"一个子任务挂了"不该让整个研究失败，代价是无法区分"子任务失败"和"系统级故障"。

**时间用 `time.monotonic()`**（[orchestrator.py:113](../src/orchestrator/orchestrator.py#L113)），不用 `time.time()` —— 超时判定必须单调，墙上时钟会被 NTP 校时往回拨。

#### DAG 与 Kahn（两个排序的区别，容易答混）

| 方法 | 行号 | 返回 | 谁在用 |
|---|---|---|---|
| `topological_sort()` | [dag.py:85](../src/planner/dag.py#L85) | **全序**（一个平铺的列表） | 需要严格顺序时 |
| `get_parallel_groups()` | [dag.py:115](../src/planner/dag.py#L115) | **分层**（list of list） | ⭐ **orchestrator 用的是这个** |

`get_parallel_groups()` 每轮取出 `_in_degree == 0` 的节点作为一层，同时扣减后继的入度——这就是 **Kahn 算法**。

**三层保护**：

1. **环检测** — [dag.py:109-112](../src/planner/dag.py#L109-L112)：入度不为 0 的节点就是环上的节点，`DAGCycleError` **把节点名报出来**（不是只说"有环"）
2. **状态无副作用** — [dag.py:91](../src/planner/dag.py#L91) 和 [dag.py:124](../src/planner/dag.py#L124) 都用 `dict(...)` **拷贝** `_in_degree`，所以同一个 DAG 可以反复排序，不污染内部状态
3. **稳定排序** — [dag.py:130-131](../src/planner/dag.py#L130-L131) `current.sort()`：同层内按字典序排，保证**同样的输入产出同样的层序**（可复现性）

**"为什么不用 `networkx`？"** —— ⚠️ **注意：项目里 `networkx` 是依赖**，用在 [compressor/extractive.py](../src/compressor/extractive.py) 的 TextRank 上。**绝对不能说"我没用 networkx"**。正确答法见讲义 03 附加 4，四个理由：① `networkx.algorithms.dag` 报环时报的是**环上的边**，我需要的是**剩下的节点名**（好定位）② 我有邻接字典，构 `DiGraph` 是多余的搬运 ③ 我要"重复调用无副作用"，自己写反而更短 ④ `networkx` 不保证同层顺序稳定。**收尾一定要加**："纯算法层面 networkx 完全能做，我是为了报错信息和确定性排序自己写的，不是性能问题。"

- 用"负责 / 优化 / 提升"却**没有对象 + 动作 + 证据**
- 报了百分比却**说不清统计口径**（← 就是那个 85%→95%）

### 2.7 "哪些是你做的" + "代码是不是 AI 写的"

这两问在 2026 年几乎是必问，且**必须提前想好、平静讲完**。

**准备三句话，具体、不心虚、不辩解**：

1. **讲你做了什么**（用"我定的"而不是"我写的"——设计决策比敲键盘更难被质疑）：
   "架构和降级策略是我定的，代码是我用 Claude Code 辅助实现的。9 状态机的状态划分、三级降级的阈值、DAG 分层并发这几个设计取舍是我做的，实现过程我逐模块审过。"

2. **讲证据**（比任何解释都硬）：
   "我可以现场讲任意一个模块的实现细节和它的缺陷——比如全局超时是软超时、Red Agent 只读前 4000 字符、AgentPool 的类型键算错导致池化失效。这三个都是我自己找出来的。"

3. **如果问 commit 为什么不在你名下**（如实、一句话、不展开）：
   "仓库在组里统一账号下推的。" —— **然后立刻转回技术**。**不要在这个问题上多解释**，越解释越像心虚。

> **核心逻辑**：AI 辅助写代码在 2026 年不是减分项，**说不清自己代码的才是**。所以 §2.5 那 11 个陷阱是这一节的弹药——**能主动指出自己系统的缺陷，是对代码所有权最强的证明**。

### 2.9 30 秒项目总述（背这一段）

> "这是一个面向复杂研究任务的多智能体系统，用 asyncio 手写了编排引擎。核心是三层设计：
> **第一层是状态机**——9 个状态管任务生命周期，每个 handler 返回下一个状态，所以状态转移是数据不是控制流；
> **第二层是执行**——用 Kahn 算法把子任务 DAG 拓扑分层，层内并发、层间串行，全局信号量控制并发度 5；
> **第三层是容错**——三级降级：单任务超时标记继续不阻塞整层，失败率超 50% 触发增量重规划（保留高置信结果、上限 3 轮），全局超时强制用已有结果合成。
>
> 后面接 Red-Blue 对抗压幻觉、三级压缩治理上下文、SQLite 共享记忆做跨 Agent 一致，最后是带统计检验的评测体系，35 题 11 领域，Bootstrap 置信区间加 Cohen's d。
>
> 有一个我自己最清楚的设计取舍可以讲：全局超时是**软超时**，只在循环顶部检查，单个长状态拦不住——我当时选了软超时，因为研究任务更看重出结果而不是硬 SLA。"

### 2.11 主动讲出的三个架构盲区（**这是加分项，不是减分项**）

面试时如果讲到对应模块，**主动带出**这三条中的任意一条，效果远好于被问出来：

1. **全局超时是软超时** — 只检查循环顶部，长状态拦不住
2. **Red Agent 只读前 4000 字符** — 五维里来源可信度实际失明；同模式在 judge / compressor 也有
3. **AgentPool 池化失效** — 类型键算错，`_idle["analyze"]` 永远空

**为什么主动说是加分**：它证明 ① 你真读过每一行 ② 你能识别自己的失败模式 ③ 你知道正确的修法。**没有任何一个面试官会因为候选人指出自己系统的缺陷而扣分。**
