| 语法 | 例子 | 人话 |
|---|---|---|
| `@trace_chain(name=..., tags=[...])` | `@trace_chain(name="compressor.compress", tags=["m3"])` | **带参数的装饰器**。注意它比普通装饰器多一层:外层先收 `name/tags`,返回一个"真正的装饰器",再由那个装饰器包住函数。**这不是语法糖,是一个会立刻执行的函数调用**——本讲第 5.5 节会看到它正是"import 就崩"的原因 |
| `@staticmethod` | `ContextCompressor._to_norm_vec(v)` | 不碰 `self`、也不碰 `cls` 的方法。**放在类里只是为了归类**,和写成一个普通函数没区别。对比 `@classmethod`(第 1 包讲过,第一个参数是 `cls`) |
| `np.array(x, dtype=np.float32)` | `np.array(emb, dtype=np.float32)` | 把 Python 列表变成**向量**。`dtype` 指定精度:float32 占 4 字节,float64 占 8 字节。embedding 用 float32 是业界习惯 |
| `np.linalg.norm(v)` | `norm = np.linalg.norm(vec)` | **向量的长度**(模)。`norm(v) == 0` 表示零向量,不能拿去做除法 |
| `axis=1, keepdims=True` | `np.linalg.norm(m, axis=1, keepdims=True)` | `axis=1` = **按行**算(每一行得到一个长度);`keepdims=True` = 结果保持 `(n,1)` 形状而不是 `(n,)`。**没它就没法广播**,这是 numpy 最容易踩的一脚 |
| `A.dot(B)` / `A.T` | `normalized.dot(normalized.T)` | **矩阵乘法** / **转置**。`(n,d)·(d,n) → (n,n)`,一行算出**所有句子两两之间的相似度** |
| `max(lo, min(hi, x))` | `max(0.15, min(0.40, 0.50 - r * 0.35))` | **夹逼(clamp)**:把 `x` 限制在 `[lo, hi]` 区间内。**顺序不能反**——写成 `min(0.40, max(0.15, ...))` 结果一样,但 `min(0.15, max(0.40, ...))` 就永远是 0.15 |
| `sum(1 for e in es if e in t)` | `sum(1 for e in entities if e in comp_text)` | **生成器表达式 + 计数**。等价于"数一数有多少个实体在文本里出现过"。比先建 list 再 `len()` 省内存 |

### 补充:三个本讲会用到但容易看错的写法

```python
# 1. 用 None 当"自动"哨兵
def compress(self, texts, query="", level: Optional[int] = None, system_prompt_tokens=0):
    if level is None:          # ← None 不是"没有级别",而是"你自己判断"
        ...
#   ^ 这里 None 有业务含义,不是"缺省所以空"。面试讲"自动分级 vs 手动指定"就在这一行

# 2. 只取前 N 个字符来"加速"
text_emb = self.embedder.encode(text[:1000])   # 只取前 1000 字符加速
#   ^ 这是有代价的优化:第 1001 字符之后的内容对 L1 的相关性打分完全没贡献

# 3. 幂等收敛判据(数学写法,不是语法)
if np.linalg.norm(new_scores - scores) < tol:
    break
#   ^ "新旧两轮的差小于阈值就停"。这就是所有迭代算法里"收敛"的标准写法
```

> 💡 **一句话记住 `keepdims=True` 的价值**:`(n,d) / (n,1)` 能广播成"每一行除以自己的长度"(归一化);写成 `(n,d) / (n,)` 在 numpy 里会广播成"按列除",结果全错但**不报错**。这是静默错误,最危险的一种。

### 1.2 三条路:截断、抽取、生成

上下文快满了,你只有三条路:

| 思路 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **截断**(truncate) | 从最旧的消息开始整条扔掉 | 零成本、零延迟、不会引入错误信息 | **信息直接没了**。而且丢的可能是唯一那条关键证据 |
| **抽取**(extractive) | 从原文里**挑句子**保留,不新写一个字 | 不会产生幻觉(**输出的每个字都来自原文**)、不需要调 LLM(便宜、快) | 挑得准不准完全取决于打分函数;句子被抽出来会**失去上下文**,读起来断断续续 |
| **生成**(abstractive) | 让 LLM 用自己的话重写一遍摘要 | 压缩率最高、可读性最好 | **会幻觉**——数字、来源都可能被模型改写;每次压缩都要调 LLM(贵、慢) |

**这个项目的三级压缩,就是按"代价从低到高"排的:**

```
L1 向量粗筛  → 抽取式(整篇丢弃)   ← 最便宜,先做
L2 关键句提取 → 抽取式(句子级保留) ← 还是抽取,不产生新字
L3 LLM 摘要   → 生成式             ← 最贵,留到最后
```

👉 **本地阅读代码**:[compressor.py:92-168 compress()](../src/compressor/compressor.py#L92-L168) · [compressor.py:40-46 类与职责](../src/compressor/compressor.py#L40-L46)

> **面试怎么讲这个排序(这一段值得背)**:
> "我把三级按**信息损失风险和成本**排的:**前两级都是抽取式,输出的每个字都来自原文,所以不会引入幻觉**;只有到第三级才让模型重写,因为它最贵、也唯一有幻觉风险。**先做便宜的、无损的;实在不够再上贵的、有损的**——这个顺序本身就是设计决策,不是随手排的。"
>
> ⚠️ 这样讲**同时回答了"为什么不用 LLM 一步到位做摘要"**——那是很多人的第一反应,也是最贵的方案。

## 第 2 步 · 三个阈值到底是什么(本讲第一个纠正)

### 2.1 先看常量

👉 **本地阅读代码**:[compressor.py:30-37 阈值与换算常量](../src/compressor/compressor.py#L30-L37)

```python
# 压缩级别触发阈值
_L1_THRESHOLD = 0.60
_L2_THRESHOLD = 0.80
_L3_THRESHOLD = 0.95

# token 估算参数
_CHARS_PER_TOKEN = 3.5
_OUTPUT_RESERVE = 2048  # 为 LLM 输出预留的 token 数
```

变量名里有个陷阱:**`_L1_THRESHOLD` 里的 `L1` 是"第一级压缩",不是"第一层相似度"**。名字长得像相似度阈值,实际完全不是。

### 2.2 它们是怎么被用的

👉 **本地阅读代码**:[compressor.py:114-134 分级判定](../src/compressor/compressor.py#L114-L134)

```python
actual_budget = self.available_budget - system_prompt_tokens   # 扣掉 system prompt 占的
if actual_budget <= 0:
    logger.warning("Actual budget <= 0 after system prompt, forcing max compression.")
    actual_budget = self.available_budget // 2                 # 兜底:对半砍

current_tokens = self.calculate_tokens(texts)                  # 当前文本占多少 token
usage_ratio = current_tokens / max(actual_budget, 1)           # ← 占用率

if level is None:                                              # 没手动指定就自动判断
    if usage_ratio > _L3_THRESHOLD:      level = 3             # >95% → 三级全上
    elif usage_ratio > _L2_THRESHOLD:    level = 2             # >80% → L1+L2
    elif usage_ratio > _L1_THRESHOLD:    level = 1             # >60% → 只 L1
    else:
        self._record_stats(texts, texts, 0, current_tokens)    # ← 记一笔"没压缩"
        return texts                                           # ← 原样返回
```

**【人话翻译】**

- `usage_ratio` 是**"现在用了百分之多少的预算"**。它是**分子是文本大小、分母是预算**的一个比值,和"这段文字和问题像不像"**一点关系都没有**。
- 三个 `if/elif` 是从**高到低**判的,所以是"叠加式":到 95% 时,`level = 3`,后面 `level >= 1 / >= 2 / >= 3` 三个都会执行 → **L1、L2、L3 全上**。
- `else` 分支很关键:`level` 保持 `None`,**但 `if level >= 1` 会这样比**——下一节讲这个坑。
- 注意用的都是 `>` 不是 `>=`,所以"正好 60%"不触发。

### 2.3 ⚠️ `level = None` 那一路是怎么"不压缩"的

`else` 分支里 `level` 是 `None`,然后代码继续往下走到:

```python
if level >= 1:      # None >= 1 会怎样?
```

**这是本讲第一个 Python 陷阱:**`None >= 1` 在 Python 3 里**不会抛异常**,而是直接抛 `TypeError`——

```
TypeError: '>=' not supported between instances of 'NoneType' and 'int'
```

等一下,那代码不是会崩吗?**不会崩**,因为 `else` 分支里 `return texts` 了——**函数直接返回,根本走不到下面**。

👉 **本地阅读代码**:[compressor.py:131-134 提前 return](../src/compressor/compressor.py#L131-L134)

**【人话翻译】** 这个 `return` 是**必需的**。如果哪天有人把这个 `return` 删掉(比如为了"记完统计继续往下走"),代码会在 `if level >= 1` 那一行对所有输入抛 `TypeError`。**这是"隐式依赖 return 拦截"的写法**:危险不在于现在错,而在于它看起来很安全。

> 💡 **这一条面试可以主动提**(属于"我知道自己代码的脆弱点"):
> "自动分级那条路是靠 `return` 提前退出的,如果那块逻辑被改动、`return` 没了,下面 `level >= 1` 会因为 `level` 还是 `None` 直接抛 `TypeError`。**更稳的写法是给 `level` 一个默认值 0**,让"不压缩"成为一条正常路径而不是"靠提前返回"。"
>
> 这句话显示的是**代码健壮性意识**,不是挑自己毛病。

**实际代码里,`0.60 / 0.80 / 0.95` 是"预算占用率门槛"。**

👉 **本地阅读代码**:[compressor.py:30-33](../src/compressor/compressor.py#L30-L33) 与 [compressor.py:121-130](../src/compressor/compressor.py#L121-L130) 对照看

| | README / 配置注释的说法 | 代码的真实语义 |
|---|---|---|
| `0.60` | L1 的**相似度**门槛:cosine < 0.6 就丢弃 | **预算占用率**:用满 60% 才启动 L1 |
| `0.80` | L2 的**相似度**门槛:中等相似度进候选池 | **预算占用率**:用满 80% 追加 L2 |
| `0.95` | L3 的**保留**门槛:> 0.95 完整保留原文 | **预算占用率**:用满 95% 追加 L3 |
| L3 干什么 | "高度相关内容**保留原文**" | **调 LLM 做层级摘要**(生成式,不是保留) |
| 那三个 YAML 键 | 看起来在驱动上面的行为 | **全仓零读取点,是死配置**(见第 7.5 节) |

**为什么会错成这样?** 这是"文档按直觉写、代码按工程写"的典型。写 README 的人(可能就是当时的你)脑子里想的是"embedding 相似度过滤",于是把三个数字按"相似度"讲了一遍;而写代码时又需要三个**预算水位线**,顺手**复用了同一组数字**。两边各自自洽,合起来就矛盾了。

**"L3 原文保留"这个说法在逻辑上自相矛盾**:如果 L3 是"保留原文",那它就不是压缩,而是**不压缩**。

> **面试怎么讲(必须主动亮,不要等被问)**:
> "这里有个我自己发现并对齐过的文档与实现冲突:**README 和配置注释把 `0.6/0.8/0.95` 写成了相似度阈值,实际代码里它们是预算占用率的三个水位线**——用满 60% 启 L1、80% 追加 L2、95% 追加 L3。另外 README 写的'L3 保留原文'也不对,`L3` 是调 LLM 做层级摘要。
> **那三个 YAML 键(`l1_threshold`/`l2_threshold`/`l3_threshold`)在代码里一个读取点都没有**,是死配置——**看起来能调、实际调不动**,这比文档写错更危险,因为改配置的人会以为自己改生效了。"
>
> 这样讲有三个好处:①证明你真的读过自己的代码;②显示出**"配置项存在 ≠ 配置项生效"**这种工程直觉;③把一个"文档错字"升级成了"配置治理"的话题。

### 2.5 把门槛换算成"需要多少字"

光知道 60% 没感觉。换成字符数就直观了。换算链是(实测,来自 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 1 节):

```

                 = 16000 - 2048 = 13952 token          ← 可用预算
实际字符预算      = 13952 × 3.5 = 48,832 字符
```

| 级别 | 水位线 | 需要多少 token | 需要多少字符 |
|---|---|---|---|
| **L1** | 60% | 8,371 | **29,299** |
| **L2** | 80% | 11,162 | **39,066** |
| **L3** | 95% | 13,254 | **46,390** |

**记这三个数:`2.9 万 / 3.9 万 / 4.6 万` 字符。** 第 7 步要用它们和第 7.1 节的闸门做对比。

> 💡 `_CHARS_PER_TOKEN = 3.5` 这个数是**中文混合文本的经验折算**——中文一个字大约 1~1.5 token,英文一个词约 1.3 token,混起来差不多 1 token ≈ 3.5 字符。

## 第 3 步 · L1 向量粗筛(含一个方向反了的循环)

### 3.1 逐行带读

👉 **本地阅读代码**:[compressor.py:170-218 _l1_filter()](../src/compressor/compressor.py#L170-L218)

```python
def _l1_filter(self, texts: list[str], query: str, budget: int) -> list[str]:
    """L1 相关性过滤：embedding cosine similarity 评分，自适应阈值。"""
    if not query or not query.strip():
        return texts                                    # ① 没有 query 就不过滤

    query_emb = self.embedder.encode(query)
    query_vec = self._to_norm_vec(query_emb)            # ② query 转单位向量

    scored: list[tuple[str, float]] = []
    for text in texts:
        text_emb = self.embedder.encode(text[:1000])    # ③ 只取前 1000 字符加速
        text_vec = self._to_norm_vec(text_emb)
        sim = float(query_vec.dot(text_vec)) if text_vec is not None else 0.0
        scored.append((text, sim))                      # ④ 每个文档配一个相似度分

    best_result: list[str] = []
    for threshold in [0.25, 0.20, 0.15]:                # ⑤ 自适应阈值
        filtered = [t for t, s in scored if s >= threshold]
        tokens = self.calculate_tokens(filtered)
        if tokens <= budget * 0.8:
            best_result = filtered
            break
        if threshold == 0.15:
            best_result = filtered                      # ⑥ 最后一轮无条件收下

    if not best_result and texts:                       # ⑦ 保底:至少留 1 篇
        best_text = max(scored, key=lambda x: x[1])[0]
        best_result = [best_text]
        logger.info(f"[L1] Fallback: kept top-1 similar doc.")

    return best_result
```

**【人话翻译】**

- **① 没有 query 就不过滤。** 合理:L1 的全部本事就是拿 query 去比相似度,没有 query 无从比。
- **②③④:把"每段文本和 query 有多像"算出来,形成一个分数列表。** 这里 `_to_norm_vec` 干的是**把向量长度归一化成 1**,这样两个单位向量一**点积**就等于余弦相似度——**不用再除以长度**。这是手写 cosine 的标准简写。
- **⑤ 自适应阈值:先试 0.25(最严),不够便宜就放宽到 0.20、0.15(最松)。** 逻辑上是"**先狠心筛,还是太大就手软**"。
- **⑥ 到 0.15 是最后一档,无条件收下**,不管超不超预算。**因为再往下削就不是"过滤"而是"直接丢光"了**。
- **⑦ 保底:如果一片都没过阈值,至少留相似度最高的那 1 篇。** 防的是"筛完啥也不剩,模型没东西可写"。

👉 **本地阅读代码**:[compressor.py:285-293 _to_norm_vec()](../src/compressor/compressor.py#L285-L293)

```python
@staticmethod
def _to_norm_vec(embedding: list[float]) -> Optional[Any]:
    import numpy as np
    vec = np.array(embedding, dtype=np.float32)
    norm = float(np.linalg.norm(vec))
    if norm < 1e-9:
        return None          # ← 零向量:返回 None,调用方要用 None 判断
    return vec / norm
```

**【人话翻译】** 返回 `None` 而不是抛异常,是**防御式写法**。但代价是**调用方必须记得判 `None`**——`_l1_filter` 里确实判了(`if text_vec is not None else 0.0`),不过它把"向量坏了"当成"相似度 = 0"处理,**这等于把一篇文档静默判成"完全不相关"**,然后被阈值筛掉。这是个**静默降级**(和 [embedder.py:27-35](../src/memory/embedder.py#L27-L35) 的随机向量是同一类毛病)。

### 3.2 ⚠️ 本讲第二个发现:这个"自适应"循环不会自适应

代码注释和 docstring 都说:**"若过滤后仍然超 budget,逐步降低到 0.15"**([compressor.py:181](../src/compressor/compressor.py#L181))。

**但实测下来,最常见的失败路径上它一步都不降。** 我用一个"能精确控制相似度"的桩 embedder 把两个分支都逼了出来(实测,见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 5b 节):

| 场景 | 输入 | 实测结果 |
|---|---|---|
| **A. 全部相似度 0.10**(一片都过不了 0.25) | 30 篇 × 200 字符 | 保留 **1/30** 篇(走了保底 top-1) |
| **B. 全部相似度 0.90**(全都过得去) | 30 篇 × 200 字符 | 保留 **30/30** 篇(0.15 收下全部) |

**A 场景才是关键。机理是这样的:**

```
threshold = 0.25 → filtered = []        ← 一片都没过
tokens = calculate_tokens([]) = 0
if 0 <= budget * 0.8:                   ← 0 当然小于任何正数,条件成立!
    break                               ← 循环在这里 break 了
```

**"滤得太狠"产生了一个空集,而空集的 token 数是 0——循环把这个 0 误读成了"已经够省了"。** 于是:

1. `0.20` 和 `0.15` **永远不会被尝试**;
2. `best_result` 是空的;
3. 接着走到 ⑦ 的保底,**把 30 篇砍成 top-1 篇**。

**结论:这个循环的设计意图(嫌大就放宽)和它的实际行为(嫌小就收工)方向正好相反。** 它只有在"**过了 0.25、但总量仍超 80% 预算**"这一条窄路上才会真的降阈值(B 场景就是),而那恰恰不是最需要它的场景。

> 💡 **为什么"滤成空集"在真实环境里很容易发生?** 因为阈值 `[0.25, 0.20, 0.15]` 是给**真 embedding 模型**定的经验值;而本机 **`sentence-transformers` 没装**时,`Embedder` 会静默降级成**确定性随机向量**(👉 [embedder.py:27-35](../src/memory/embedder.py#L27-L35))。实测两句话的余弦相似度:
>
> | 对比 | 余弦 |
> |---|---|
> | "大模型Agent市场规模在2025年快速增长" vs "2025年大模型Agent赛道规模显著增长"(语义相近) | **+0.0779** |
> | "大模型Agent市场规模在2025年快速增长" vs "今天天气不错,适合出门散步"(完全无关) | **+0.0203** |
> | 差值 | **+0.0577**(判据要求 ≥ 0.10 才算有语义信号) |
>
> **相近的两句并不比无关的两句更相似。** 在这种向量上,0.25 这个阈值等于**随机一刀切**,绝大多数文本会被砍掉 → 直接走进 A 场景的保底 top-1。
> ⚠️ **这是环境事实(本机未装模型),不是代码 bug。** 但它决定了:**凡是在本机复现出来的 L1 数字,都不能当作"语义过滤效果"来报**。

> **面试怎么讲(这条主动讲,含金量最高)**:
> "L1 的自适应阈值循环有个逻辑问题,我实测复现过:**它是想'嫌大就放宽阈值',但判断条件是'过滤后的 token 数 ≤ 预算 80%'。当阈值太严、结果被滤成空集时,空集的 token 数是 0,这个条件反而成立,循环立刻 break——所以 0.20 和 0.15 根本不会被尝试,而保底逻辑会把 N 篇砍成 top-1 篇。**
> **修法**:判断条件应该改成"结果非空 **且** 不超预算",或者干脆在保底之前再跑一轮降阈值。"

### 3.3 那 1000 字符截断值得说一句

```python
text_emb = self.embedder.encode(text[:1000])   # 只取前 1000 字符加速
```

这是一处**速度与准确度的交换**:一段 5,000 字符的文档,只有前 1,000 字符参与相关性打分,后 4,000 字符对 L1 的判定**没有贡献**。

**但它是对的取舍**:L1 是粗筛,它的任务不是"精确判断",而是"把明显不相关的丢掉"。用前 1,000 字符(通常已经包含标题、导语、核心结论)足以完成粗筛,而把 encode 的耗时降低到 1/5。

| | 全量 encode | 前 1000 字符 |
|---|---|---|
| 准确度 | 更高 | 略低(只看开头) |
| 单篇耗时 | 与长度成正比 | **上界固定** |
| 用在 | L2(要精确排序句子的) | **L1(粗筛)** ✅ |

> 💡 这个"**按阶段的精度要求分配计算量**"的思路,和 L1/L2/L3 三级本身是同一个设计哲学。面试讲 L1 时顺带提一句"粗筛阶段我主动砍掉长尾内容来换速度",比只说"我用了 embedding"高一档。

### 4.1 分句:先有"句子"这个概念

👉 **本地阅读代码**:[extractive.py:26-40 分句正则与过滤](../src/compressor/extractive.py#L26-L40)

```python
_SENTENCE_PATTERN = re.compile(r'[^.!?。！？\n]+[.!?。！？\n]*')

def _tokenize_sentences(text: str) -> list[str]:

    sentences = [s.strip() for s in raw if len(s.strip()) > 8]

```

**【人话翻译】**

- 正则的意思是:"**一串"非句末标点"的字符 + 后面的句末标点**"。中英文的句号问号感叹号和换行都算句末。
- **`len(s.strip()) > 8`:太短的句子直接扔掉。** 防的是"#"、"1."、"---"这种 markdown 碎片变成假句子。**这个 8 是有讲究的**:中文标题往往很短,但标题恰好是高信息量的——所以 8 是一个"宁可漏掉短标题,也不让碎屑污染图"的取舍。
- 实测:一份 25,185 字符的真实报告分出 **570 句**;而 200 字符的碎片分出 **4 句**(见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 5 节)。

**三个因子,各自的职责:**

| 因子 | 在问什么 | 取值范围 | 技术上叫什么 |
|---|---|---|---|
| `textrank` | **这句话在全文里"重要"吗?**(和很多句子都相关的句子,往往是核心句) | 约 0~1,总和为 1 | 图算法 / PageRank |
| `query_sims` | **这句话和用户问题相关吗?** | -1~1 | query bias / 偏置 |
| `value_bonus` | **这句话含数字/来源/结论词吗?** | 1.0 或 1.2 | 规则加权 / 特征叠加 |

**【为什么要相乘而不是相加?】** 相乘意味着**一票否决**:任何一项接近 0,总分就接近 0。效果是"**既重要、又相关、还含硬信息**"三者**都满足**的句子才排得上来。相加则会让"特别重要但完全不相关"的句子靠单科高分挤进榜单。

**这是可讲的取舍**:相乘更严格(句子数少、精度高),相加更宽松(召回高、噪音多)。压缩场景下**宁缺毋滥**,所以选相乘。

> ⚠️ **注意 `query_sims` 可能为负。** 负相关句相乘后得到负数,`argsort` 升序排完再 `[::-1]`,负数排在最后 → 安全。但如果 query 向量退化(`q_norm < 1e-9`),代码走的是 `query_emb = query_emb`(**保持原样,没做归一化**),接下来 `query_sims` 的量纲就错了。这是**只在 query 是空字符串时才可能发生**的边角路径,而 `_l1_filter` 会先拦住空 query,**`_l2_extract` 不会**——两条路的空值防御不一致(分析)。


**这条正则在抓六类"信息密度高"的句子:**

| 模式 | 抓什么 | 例子 |
|---|---|---|
| `\d+[\d,]*\.?\d*\s*%?` | **数字和百分比** | `12.5%`、`1,200` |
| `\d{4}-\d{2}-\d{2}` | **日期** | `2025-03-01` |
| `https?://` / `www\.` | **URL** | `https://idc.com/...` |
| `\[[\d\w]+\]` | **引用角标** | `[1]`、`[IDC]` |
| `according to`/`cited`/`reported`/`found that` | **英文归因** | `according to Gartner` |
| `结论`/`结果表明`/`数据显示` | **中文归因与结论** | `数据显示` |

**【人话翻译】** 这六类是一份研究报告里**最不能丢的东西**:数字被丢掉,报告就变成空话;来源被丢掉,就变成不可验证的断言。

**为什么是 ×1.2 而不是 ×2?** 因为这是个**加分项,不是决定项**。1.2 足够在"两句话 otherwise 打平"时把含数字那句顶上去,又不足以让一句含数字但和问题无关的废话挤掉真正切题的句子。**这个 1.2 是手工调的粗调,不是调参调出来的**(诚实说明:仓库里没有调参记录,属于推断)。

### 4.4 TextRank 的实现:自己写的 PageRank 幂迭代

这是**整个模块最"技术"的一段**,也是面试最容易被追问"你是不是调库"的地方。

👉 **本地阅读代码**:[extractive.py:43-57 余弦相似度矩阵](../src/compressor/extractive.py#L43-L57) · [extractive.py:60-91 幂迭代](../src/compressor/extractive.py#L60-L91)

```python
def _cosine_similarity_matrix(vectors: np.ndarray) -> np.ndarray:
    """计算向量矩阵的余弦相似度矩阵。"""
    norms = np.linalg.norm(vectors, axis=1, keepdims=True)   # 每行的长度
    norms[norms < 1e-9] = 1.0                                # 防 0 除
    normalized = vectors / norms                             # 归一化
    return normalized.dot(normalized.T)                      # (n,d)·(d,n) → (n,n)


def _textrank_scores(sim_matrix, damping=0.85, max_iter=30, tol=1e-4):
    n = sim_matrix.shape[0]
    if n == 0:
        return np.array([])

    adj = sim_matrix.copy()          # ← 关键:先复制,不改原矩阵
    adj[adj < 0.1] = 0.0             # ← 稀疏化:相似度太低的边直接切断
    row_sums = adj.sum(axis=1, keepdims=True)
    row_sums[row_sums < 1e-9] = 1.0  # 防 0 除
    transition = adj / row_sums      # ← 行归一化:每行的出边权重和为 1

    scores = np.ones(n) / n          # ← 初始:所有句子均分
    for _ in range(max_iter):
        new_scores = (1 - damping) / n + damping * transition.T.dot(scores)
        if np.linalg.norm(new_scores - scores) < tol:
            break                    # ← 收敛了就提前退出
        scores = new_scores
    return scores
```

**【人话翻译,一步步来】**

**第一步:把句子变成一个"图"。** 每个句子是一个**节点**;任意两句之间的余弦相似度,就是那条**边的粗细**。一句话如果和很多别的话都相似,它在图里就连着很多粗边。

**第二步:切掉太细的边。** `adj[adj < 0.1] = 0.0`——相似度不到 0.1 的就当没关系。**这是降噪**:两个句子碰巧都用到了"数据"这个词,不代表它们相关。

**第三步:行归一化。** 让每个节点的"出边权重总和 = 1"。这样下一步做加权平均时,量纲才一致。

**第四步:幂迭代(这就是 PageRank)。**

```
new_scores = (1 - damping) / n + damping * transition.T.dot(scores)
             └──── 基础分 ────┘   └──── 从邻居那里"传"过来的分 ────┘
```

- `damping = 0.85`:**阻尼系数**,表示"85% 的分数来自邻居,15% 凭空均分"。
- `transition.T.dot(scores)`:每个节点的新分数 = **所有"指向它的"节点的分数加权和**(权重就是边粗细)。
- **为什么能收敛?** 因为这是一个**压缩映射**:每一轮都在做"加权平均 + 一点常数",分数不会发散。迭代到变化量小于 `tol = 1e-4` 就停。
- `max_iter = 30` 是**保险丝**:万一不收敛(某些矩阵结构下可能震荡),30 轮后强制停,不会死循环。

**用一句话总结 TextRank:**"**重要的句子,是那些和很多其他重要句子都相似的句子。**"——这句话自己引用自己(所以是迭代),PageRank 就是让它收敛的数学工具。

> **面试怎么讲(这段背下来,直接回答"TextRank 怎么实现的")**:
> "我自己写的,没调库。三步:①把每个句子当节点、句子两两之间的余弦相似度当边权,切掉 0.1 以下的弱边降噪;②对邻接矩阵做行归一化,得到转移概率矩阵;③用 **PageRank 的幂迭代**求解,阻尼系数 0.85,收敛阈值 1e-4,最多 30 轮。**收敛判据是前后两轮分数向量的 L2 距离小于阈值**。
> 然后我把它和**句子与问题的相关性**、**含数字/来源的规则加分**三样**相乘**融合,相乘是为了'一票否决'——三个条件都得满足才排得上来。
> **没用 `sumy`/`gensim` 的原因是我要加 query 偏置和规则加权,那两样库不直接给;而且零新增依赖**。"

> ⚠️ **一个必须提前想好的追问**:"**你为什么用 embedding 余弦建图,而不用论文里 TextRank 原始的共现窗口?**"
> **正解(原型是这么做的)**:原始 TextRank 用"滑动窗口内共现"建边,是因为它是 2004 年的论文,那时没有句向量。用句向量算相似度是**现代做法**,语义上更准(同义不同词也能连上边)。
> **代价(必须说出来)**:embedding 建图是 **O(n²)** 的相似度计算——570 句话就是 324,900 个相似度。**n 再大就要上稀疏化或分块**,这里的 0.1 阈值截断也算一种粗糙的稀疏化。

### 4.5 保留句数:`k = max(1, int(n * top_ratio))`

```python
k = max(1, int(n * top_ratio))
top_indices = set(np.argsort(combined)[::-1][:k].tolist())
result = [s for i, s in enumerate(sentences) if i in top_indices]   # ← 恢复原文顺序
```

**【人话翻译】** 两个细节:

1. **`int()` 是截断不是四舍五入**:`int(8 × 0.22) = int(1.76) = 1`。
2. **最后一行在恢复原文顺序。** 这是**抽取式摘要的必需步骤**:你是按"分数高到低"选出来的句子,但**读的时候必须按原文顺序**——否则摘要会语序错乱、逻辑跳跃。**实现方式是用 `set` 存下标,再按原顺序遍历一遍原文。** 这个"用集合存下标 + 顺序遍历"是个值得记住的小技巧。

**`top_ratio` 从哪来?** 来自 `_l2_extract` 的动态计算:

👉 **本地阅读代码**:[compressor.py:233-235 动态保留比例](../src/compressor/compressor.py#L233-L235)

```python
current_tokens = self.calculate_tokens(texts)
# 目标比例：线性映射，预算用满 80% 时保留 30%，用满 100% 时保留 15%
target_ratio = max(0.15, min(0.40, 0.50 - (current_tokens / max(budget, 1)) * 0.35))
```

**设计意图**:预算越紧,保留比例越低——用满 57% 的时候留 30%,用满 100% 的时候留 15%。**这是一个线性衰减,夹在 [0.15, 0.40] 之间。**

### 4.6 ⚠️ 本讲第三个发现:那行注释算错了

**注释说的是"用满 80% 保留 30%、用满 100% 保留 15%"。代进公式算一遍**(实测,见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 4 节):

| 占用率 | 公式算出的 `target_ratio` | 注释声称 |
|---|---|---|
| 60% | 0.290 | — |
| 70% | 0.255 | — |
| **80%** | **0.220** | **30%** ❌ |
| 90% | 0.185 | — |
| **100%** | **0.150** | **15%** ✅(这一处恰好对) |
| **57.1%** | **0.300** | ← 注释里的"30%"实际出现在这里 |

**反解一下更清楚:**

- 想让 `target_ratio = 0.30`,需要 `0.50 - occ × 0.35 = 0.30`,解得 **`occ = 57.1%`**;
- 想让 `target_ratio = 0.15`,需要 `occ = 100%`——**正好卡在下限上**。也就是说 **0.15 这个下限实际要到占用率超过 100% 才会真正生效**,100% 时公式自己就能算出 0.15。

**结论:注释里那两个数("80%→30%")是错的,应该是"57%→30%"。** 代码是对的,注释是顺手写的近似。

> 💡 **这个坑的价值不在数字本身,而在"你怎么发现的"**:
> **面试可以这么讲**:"我核对自己注释的时候发现一处对不上——L2 的保留比例注释写的是'预算用满 80% 保留 30%',把公式代进去实际是 **0.22**,0.30 对应的是 **57%**。代码是对的,注释是近似写歪了。**这类'注释与公式不符'在长项目里很常见,我的做法是把公式和注释放在同一行旁边,让人一眼能验算。**"
>

### 4.7 L2 作用在不同规模文本上的实测

| 输入 | 分句数 | `ratio=0.40` 保留 | `ratio=0.22` 保留 | `ratio=0.15` 保留 |
|---|---|---|---|---|
| 200 字符碎片(调用点喂进来的形状) | 4 | 1 句 | **1 句** | 1 句 |
| 整份报告(25,185 字符) | 570 | 228 句 | 125 句 | **85 句** |

**两个结论:**

1. **`extractive.compress()` 有个"太短不压缩"的提前返回**([extractive.py:128-130](../src/compressor/extractive.py#L128-L130)):`len(sentences) <= 3` 就原样返回。**实测 200 字符的中文碎片能分出 4 句,刚好越过 3 这个门槛**——所以它**没有**走提前返回,而是被压到 1 句。
2. **`k = max(1, ...)` 意味着碎片最少也留 1 句。** 一篇 200 字符的碎片被 L2 处理后剩 1 句(约 20~60 字符),**压缩比看起来非常漂亮(0.1 量级),但信息也几乎被抽干**。这是"**压缩比高 ≠ 压缩得好**"的典型例子,面试被问"你的压缩比是多少"时**必须一起说保留率**。

> ⚠️ **`len(sentences) <= 3` 这个提前返回是个静默短路**:它不记日志、不改状态、直接返回原文。所以从 `compression_ratio` 上看不出"这条根本没被压"和"这条压了但压不动"的区别。**这是"静默降级"的第三处**(前两处:`_to_norm_vec` 返回 None、`Embedder` 随机回退)。

## 第 5 步 · L3 LLM 层级摘要

### 5.1 为什么是"两层"而不是"一次搞定"

👉 **本地阅读代码**:[compressor.py:249-283 _l3_summarize()](../src/compressor/compressor.py#L249-L283)

```python
current_tokens = self.calculate_tokens(texts)
per_doc_max = max(200, budget // max(len(texts), 1))     # 单篇摘要的长度上限
summaries = []
for text in texts:
    summary = self.summarizer.summarize_document(text, query, max_length=per_doc_max)
    summaries.append(summary)

aggregate_max = max(400, budget // 2)                    # 聚合摘要的长度上限
aggregate = self.summarizer.summarize_documents(summaries, query, max_length=aggregate_max)

return [aggregate]                                        # ← 注意:返回单元素列表
```

**【人话翻译】** 这里的关键决策是**"均分预算再做聚合"**:

- `per_doc_max = budget // len(texts)`:把总预算**平均分给每篇文档**。这样 N 篇文档的摘要加起来大致就是总预算,**不会因为文档多而爆炸**。
- `max(200, ...)` 是**下限保险**:文档特别多时(比如 100 篇),`budget // 100` 会很小,摘要短到没意义,所以强制每篇至少 200。
- 然后再把 N 份小摘要**聚合成一份综述**,上限 `budget // 2`(留一半余量)。

**为什么不能一次把所有文档丢给 LLM 做摘要?** 因为**那正是我们想避免的事**——输入本来就太长,一次丢进去要么超限、要么模型"看不过来"(长输入下摘要质量普遍下降,关键信息容易漏)。**分而治之,每篇先压到可控长度,再合并**,是标准的 Map-Reduce 式摘要。

👉 **本地阅读代码**:[summarizer.py:103-154 summarize_documents()](../src/compressor/summarizer.py#L103-L154)

### 5.2 Prompt 里的四条要求,和它们各自防什么

👉 **本地阅读代码**:[summarizer.py:19-29 单文档摘要 prompt](../src/compressor/summarizer.py#L19-L29) · [summarizer.py:32-46 聚合摘要 prompt](../src/compressor/summarizer.py#L32-L46)

```
1. 保留所有关键数字、日期、统计数据        ← 防"数字被四舍五入掉"
2. 保留来源引用和作者信息                  ← 防"变成不可验证的断言"
3. 保留不确定性表述（如"约""可能""据报道"） ← 防"把'可能'写成'就是'"
4. 摘要长度不超过 {max_length} 字
5. 使用中文输出
```

**第 3 条是最有含金量的一条,值得单独讲。** LLM 做摘要时有个非常危险的倾向:**把模糊表述"硬化"**。原文是"初步结果显示,该比例**可能**上升",摘要成"该比例上升"——**事实强度被悄悄改写了**。这是幻觉的一种隐蔽形式:**它不编造新事实,只是把不确定的变成了确定的**。

聚合 prompt 里还多了一条:

```
5. 若文档间存在矛盾，请分别列出不同观点并标注来源
```

**这一条和整个项目的第二主题(跨 Agent 结论打架)呼应**:如果两篇文档给出了矛盾的数字,摘要**不应该**"和稀泥"地取平均或只留一个,而应该**把矛盾原样保留下来**。

> **面试怎么讲(这句很加分)**:
> "摘要 prompt 里我特别强调了**保留不确定性表述**——因为 LLM 做摘要最容易出的问题不是编造新事实,而是**把'可能'写成'就是'**,把原文的置信度悄悄抬高。这是最隐蔽的一类失真。**聚合阶段我还要求它遇到矛盾不要合并、要分别列出并标注来源。**"
>
> ⚠️ 但要诚实:**prompt 要求 ≠ 模型一定会照做**。这是"约束"不是"保证",没有做校验。

### 5.3 两条兜底:空响应和异常

👉 **本地阅读代码**:[summarizer.py:91-101 单文档兜底](../src/compressor/summarizer.py#L91-L101)

```python
try:
    resp = self.llm_policy([{"role": "user", "content": prompt}])
    summary = str(resp.content or "").strip()
    if not summary:
        logger.warning("LLM returned empty summary, returning truncated original.")
        return doc[:max_length] + "\n[TRUNCATED]"        # ← 空响应 → 硬截断
    return summary
except Exception as e:
    logger.error(f"LLM summarize_document failed: {e}")
    return doc[:max_length] + "\n[TRUNCATED]"            # ← 异常 → 同一条兜底
```

**【人话翻译】** 这里体现的是"**降级方向的选择**":

- **失败时退回"硬截断原文"**,而不是"返回空字符串"或"抛出异常"。
- **为什么?** 因为**截断的原文至少还是原文**——里面的数字、来源都是真的,只是可能被切掉一半;而返回空字符串会让下游拿到"空上下文",模型只能凭空编。**在所有坏选项里,"有损但真实"优于"干净但空洞"。**
- `[TRUNCATED]` 标记是**给人看的**:让下游(或调试的你)一眼看出这段是降级产物,而不是正常摘要。

👉 **本地阅读代码**:[summarizer.py:145-154 聚合兜底](../src/compressor/summarizer.py#L145-L154)

聚合失败时退到 **`"\n\n".join(single_summaries)`**——**返回 N 份小摘要的拼接**。同样是"有损但真实":不算是一份连贯综述,但每一句都是模型基于原文写的。

> **面试怎么讲**:"L3 的兜底我做了两层:**LLM 返回空**和**LLM 抛异常**都退回**硬截断原文**,聚合失败就退回**拼接各篇小摘要**。选择逻辑是——**降级产物宁可'有损但真实',也不要'干净但空洞'**,因为下游拿不到内容就会开始编。"

### 5.4 ⚠️ `return [aggregate]` 的后果:文档边界消失了

注意最后一行:**不管输入多少篇文档,L3 都返回一个只有 1 个元素的列表。**

**这是个真实的信息结构损失:**

| 阶段 | 列表长度 | 还知道"哪句话来自哪篇文档"吗 |
|---|---|---|
| 调用 `compress()` 前 | N | ✅ 知道 |
| 过 L1 后 | ≤ N(筛掉一些) | ✅ 知道 |
| 过 L2 后 | 同 L1 | ✅ 知道(句子还是原来那些) |
| **过 L3 后** | **1** | ❌ **全被合并成一份综述了** |

**后果**:如果 `compress()` 的调用方依赖"一篇文档一个元素"这个结构(比如把每个元素渲染成一个引用块、或者按元素分配引用编号),**过了 L3 之后这个结构就没了**。

**这是有意的设计**(聚合摘要的定义就是"合并成一份综述"),**但它和上游的假设不一致**。这是一个典型的**接口契约问题**:`compress()` 的入参是 `list[str]`(N 篇),出参**在 L1/L2 下是"N 篇的子集"、在 L3 下是"1 篇综述"**——**同一个函数的返回结构随 level 变化**。

> 💡 **这属于"接口设计"层面的批评,面试讲出来是很高的段位**:
> "`compress()` 在 L1/L2 下返回的是'文档列表的子集',到 L3 会塌缩成单个元素。**同一个函数的返回结构随内部等级变化,调用方就没法写稳定代码**。更清楚的契约是让 L3 也返回同样长度的列表,或者干脆分成两个函数(`compress_extractive` / `compress_abstractive`),把结构变化放到类型上显式表达。"

### 6.1 触发条件与实现

**【人话翻译】** 三级都压过了还是超预算,就上**最粗暴的那一招**:把文本转成"消息格式",交给滑动窗口**整条丢弃**,再转回来。

**注意这里有一次"格式往返"**:`list[str]` → `list[dict]` → 截断 → `list[str]`。之所以要绕这一圈,是因为 `SlidingWindowCompressor` 的接口是**按消息列表设计的**(它要识别 `role`、要单独保留 `system`),而 `compress()` 的接口是**纯文本列表**。**这是两个模块接口不一致导致的适配成本。**

👉 **本地阅读代码**:[sliding_window.py:65-153 _truncate_messages()](../src/compressor/sliding_window.py#L65-L153)

```python
system_msgs = [m for m in messages if ... m.get("role") == "system"]     # ① system 单独拿出来
other_msgs  = [m for m in messages if not (... m.get("role") == "system")]

before_chars = self._count_chars(messages)
if before_chars <= max_chars:
    ... return messages                    # ② 没超限就原样返回

kept = list(other_msgs)
removed_count = 0
while len(kept) > self.min_recent_turns:   # ③ 至少保留 3 条,别全丢光
    removed = kept.pop(0)                  # ← 从最旧的一条开始丢
    removed_count += 1
    after_chars = self._count_chars(system_msgs + kept)
    if after_chars <= max_chars:
        ... return system_msgs + kept      # ④ 够省了就停
```

**【人话翻译】**

- **① `system` 消息被单独拎出来,永远不参与丢弃。** 因为 system prompt 是"角色设定 + 输出规范",丢了模型就不知道自己要干嘛。
- **③ `min_recent_turns = 3`**:至少留 3 条非 system 消息。**防的是"预算特别紧时把历史全丢光,模型完全失忆"**。
- **`pop(0)` 是从**最旧**的一条开始丢**(FIFO)。这是有意的:**近期的上下文比久远的更重要**。
- **注意 `while` 的条件是 `len(kept) > self.min_recent_turns`**:循环结束后 `kept` 至少有 `min_recent_turns` 条。

### 6.2 极端情况:连"只留 system + 最后 3 条"都超预算

👉 **本地阅读代码**:[sliding_window.py:122-145 内容级截断](../src/compressor/sliding_window.py#L122-L145)

```python
if after_chars > max_chars and kept:
    last_msg = kept[-1]
    excess = after_chars - max_chars
    content = str(last_msg.get("content", ""))
    new_len = max(len(content) - excess - 100, self.min_last_msg_chars)
    if new_len < len(content):
        last_msg["content"] = content[:new_len] + "\n[CONTENT_TRUNCATED]"
```

**【人话翻译】** 连"只留 system + 最后 3 条"都还是超,就**对最后一条消息做内容级截断**:

- `excess` = 超出多少字符;`- 100` 是**多砍 100 字符的余量**(防止临界值反复);
- **`max(..., min_last_msg_chars)`**:不管怎么砍,**最后一条至少保留 500 字符**。

**为什么"至少留 500 字符"很重要?** 因为最后一条消息通常是**当前正在处理的任务**,砍光了模型就无事可做。**"宁可超一点预算,也不能让模型没有输入"**——这是取舍。

> ⚠️ **注意 `last_msg["content"] = ...` 是原地修改!** `kept[-1]` 是**调用方传进来的那个 dict 对象**,不是副本。所以**这个函数会修改调用方的数据结构**——调用完之后,原来那个消息列表里的最后一条**也变了**。
> 这是**函数式纯洁性的破坏**:一个叫 `compress`(听着像"读取并返回处理结果")的函数,偷偷改了入参。**面试可以主动提**:"这里我改的是入参对象本身,不是副本,这是个副作用;`compressor.py` 的 L1/L2 都用 `list(texts)` 做了拷贝,只有这一处没有。"

### 6.3 ⚠️ 本讲第四个发现:滑窗会切出"孤儿 tool 消息"

**实测**(见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 9 节),构造一段含工具调用的真实形状消息:

```
输入 roles = ['system', 'assistant', 'tool', 'assistant', 'tool', 'user']   ← 1852 字符
```

| `max_tokens` | 输出 roles | 孤儿 tool 消息? |
|---|---|---|
| 400 | `['system', 'assistant', 'tool', 'user']` | **是** ⚠️ |
| 200 | `['system', 'tool', 'user']` | **是** ⚠️ |

**什么叫"孤儿 tool 消息"?** 在 OpenAI 的消息协议里,一次工具调用是**两条配对的消息**:

```
{"role": "assistant", "tool_calls": [{"id": "call_1", ...}]}   ← 说要调工具
{"role": "tool", "tool_call_id": "call_1", "content": "..."}   ← 工具返回结果
```

**这两条必须成对出现。** 而滑窗的丢弃逻辑是"**按字符预算,从最旧一条开始 pop,够省就停**"——它**完全不认识这个配对语义**。所以它完全可能:

- pop 掉 `assistant(tool_calls)` 那条,却**留下了对应的 `tool` 结果**;
- 或者 pop 到一半在配对中间停住。

**实测两种配置下都出现了孤儿 tool 消息。** 后果:**多数 OpenAI 兼容后端遇到"没有对应 tool_call 的 tool 消息"会直接返回 400 错误。** 也就是说,**这个"兜底"策略自己可能成为一次故障的来源**。

**正确做法是"按轮次丢弃"**:丢弃时以"一次完整的工具调用(assistant + tool)"为单位,而不是以单条消息为单位。

> **面试怎么讲(这条要主动讲,展示你对协议的理解)**:
> "滑窗兜底我实测发现一个副作用:**它是按字符预算逐条 pop 的,不认'工具调用'是 assistant + tool 两条配对消息**。所以它可能丢掉 assistant 那条、留下 tool 的结果,产生一个**没有对应 tool_call 的孤儿消息**——多数兼容后端会直接报 400。**正确的粒度应该是'按一次完整的工具调用成对丢弃'。**"
>
> 这个回答同时证明了三件事:①你知道工具调用的消息协议;②你会实测而不只看代码;③你能把"截断策略"和"协议合法性"这两件看似无关的事连起来。

### 6.4 还有一个小副作用:system 消息被重排

截断分支的返回值是 **`system_msgs + kept`**(三处:[sliding_window.py:120](../src/compressor/sliding_window.py#L120)、[:145](../src/compressor/sliding_window.py#L145)、[:153](../src/compressor/sliding_window.py#L153))。

**这意味着所有 `system` 消息会被集中搬到列表最前面。** 原列表里如果有一条 `system` 消息插在中间(比如"用户中途改了要求"这种注入式 system),它的**位置就变了**。

在 OpenAI 的协议里,消息顺序是有语义的。**不过在这个项目里影响不大**——因为正常的会话里 `system` 本来就只有开头一条。**但在通用压缩器上这是个隐患**,也是"把 `system_msgs + kept` 当作返回结构"这个实现的代价。

### 7.1 唯一的接入点长什么样

👉 **本地阅读代码**:[orchestrator.py:548-588 _build_memory_context()](../src/orchestrator/orchestrator.py#L548-L588)

```python
def _build_memory_context(self) -> str:
    """构建给 planner 的上下文摘要。"""
    # M4: 语义检索相关记忆
    if self.memory_store is not None:
        try:
            ctx = self.memory_store.get_context_for_query(self._query, max_tokens=2000)
            if ctx:
                print(f"[M4] Retrieved {len(ctx)} chars of semantic memory context")
                return ctx                                  # ← ① 早返回:正常路径在这里就结束了
        except Exception as e:
            print(f"[M4] Semantic memory query failed: {e}, falling back to dict")

    # 回退：运行时 dict 遍历                              ← ② 只有上面没返回才会走到这
    parts = []
    for key, value in self._memory_store.items():
        if key.startswith("result:"):
            continue
        parts.append(f"{key}: {str(value)[:200]}")           # ← ③ 每条截到 200 字符

    # M3: 如果上下文过长，启用压缩
    if self.compressor is not None and parts:
        total_chars = sum(len(p) for p in parts)
        if total_chars > 6000:      # 约 2000 tokens 的启发式阈值   ← ④ 闸门
            compressed = self.compressor.compress(
                texts=parts, query=self._query, system_prompt_tokens=0,
            )
            print(f"[M3] Context compressed: {total_chars} → {sum(len(c) for c in compressed)} chars")
            return "\n".join(compressed)
    return "\n".join(parts) if parts else ""
```

**这里有三个必须看出来的事实:**

| # | 事实 | 后果 |
|---|---|---|
| ① | **压缩在"回退分支"上** | `memory_store.get_context_for_query()` 只要返回**非空**字符串就早返回了。而它的语义是"**没有相关记忆时返回空字符串**"([memory_store.py:328-361](../src/memory/memory_store.py#L328-L361),门槛 `min_sim=0.55`)。**所以只有"记忆库里没有相关记忆"时,压缩才有机会被调用** |
| ② | **喂进去的每条已经被截到 200 字符** | 压缩器的输入**不是原始文档,而是每条 200 字符的碎片**。TextRank 分句、LLM 摘要作用在这些碎片上 |
| ③ | **闸门是 6000 字符** | 但 L1 的门槛是**29,299 字符**(见 2.5 节) |

**而且这个接入点服务的对象是 Planner,不是 ResearchAgent。** `_build_memory_context()` 是给规划器构建"背景知识"用的。**真正会爆上下文的 `ResearcherAgent` 多轮循环(max_turns=10,每轮 append 工具结果)完全没有接压缩。**

### 7.2 闸门和级别门槛差了 4.9 倍

把两边的数字摆在一起(实测,见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 2 节):

```
调用点闸门:  total_chars > 6000
             → 6000 / 3.5 = 1,714 token
             → 占用率 = 1714 / 13952 = 12.3%

L1 门槛:     usage_ratio > 0.60

差距:        0.60 / 0.1229 = 4.9 倍
```

**换句话说:能通过调用点闸门的输入,占用率只有 12.3%,离启动 L1 需要的 60% 差了近 5 倍。**

**那需要多少条才能触发?** 每条被截到 200 字符、加上 key 大约 210 字符:

| 级别 | 需要字符 | 需要 `_memory_store` 里至少多少条 |
|---|---|---|
| L1 | 29,299 | **140 条** |
| L2 | 39,066 | **187 条** |
| L3 | 46,390 | **221 条** |

### 7.3 实跑证明:返回原样,而且日志会撒谎

我按**调用点的真实输入形状**(30 条 × 200 字符 = 6,000 字符,刚好过闸门)实跑了一遍 `compress()`(见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 3 节):

```
输入: 30 条, 共 6000 字符
输出: 30 条, 共 6000 字符
输出 == 输入（原样返回）: True
get_stats().level_distribution = {0: 1, 1: 0, 2: 0, 3: 0}
```

**一个字都没动。** 而且注意 orchestrator 在调用后打印的那行:

```python
print(f"[M3] Context compressed: {total_chars} → {sum(len(c) for c in compressed)} chars")
```

**实测打印结果是:`[M3] Context compressed: 6000 → 6000 chars`。**

**两个数字一模一样。** 这行日志的措辞是"Context **compressed**",但**压缩根本没发生**——`compress()` 走进了 `else` 分支,`_record_stats` 记了一笔"level=0",然后原样返回。

> ⚠️ **这就是"日志撒谎"最典型的形态**:它没有报错、没有 warning,只是**打印了一句听起来成功的话**。如果只看日志,你会以为压缩在工作。
> **面试可以主动讲**:"我在核对的时候发现调用点那行 `[M3] Context compressed: X → Y chars` 会在没有压缩时也打印,而且 X 和 Y 相同。**这类日志比不打印更危险**,因为它会让人误以为功能在生效。我改成只在真的压缩了才打,或者把 level 一起打出来。"

**对照实验(证明这套逻辑本身是好的):** 同一批输入,只要把预算从 16,000 调到 3,000:

```
available_budget = 952 tokens → 占用率 = 1.80
输出 1 条, 54 字符, 原样返回=False
level_distribution = {0: 0, 1: 0, 2: 0, 3: 1}     ← L3 正常触发了
```

**分级逻辑是对的。问题纯粹出在"调用点的闸门"和"级别的门槛"这两个数字不在同一个量级上。**

### 7.4 端到端实测:三级各自压成什么样

把一份**真实报告**(25,185 字符)切成 30 条 × 200 字符,分别**强制指定** level=1/2/3 跑一遍(见 [scripts/measure_compressor.py](../scripts/measure_compressor.py) 第 5c 节):

| 强制级别 | 输出条数 | 输出字符 | 压缩比 | 信息保留率 |
|---|---|---|---|---|
| L1 | 1 | 200 | **0.033** | **0.097** |
| L2 | 1 | 68 | **0.011** | **0.000** |
| L3 | 1 | 68 | **0.011** | **0.000** |

> ⚠️ **证据档位:实测,但必须带两条限制。**
> ① **本机没装 `sentence-transformers`**,`Embedder` 走确定性随机回退 → **"筛得准不准"完全不可信**(见 3.2 节)。L1 之所以把 30 条砍到 1 条,是因为随机向量过不了 0.25 阈值触发了保底 top-1。
> ② **信息保留率是 `_estimate_retention` 的启发式口径**(见 7.6 节),它只统计**数字实体和英文专有名词**的出现比例,`0.000` 意味着"原碎片里的数字/专有名词在输出里一个都没留下"。
>
> **所以这张表能说明的只有一件事:压缩比可以做得极其漂亮(0.011),同时信息保留率可以是 0。** 这正是"**压缩比高 ≠ 压缩得好**"的实证。

**面试被问"你的压缩比能达到多少"时的正确答法:**

> "压缩比我能做到 0.01~0.03 量级,但**这个数字单独看没有意义**——同一套参数下我把信息保留率实测到过 0.0。**压缩类工作必须同时报两个数:压掉了多少、留住了多少。** 只看压缩比会奖励'把内容全删掉'这种最差的方案。"

### 7.6 那句"量化评测接口"没有接线

👉 **本地阅读代码**:[compressor.py:42-46 类 docstring](../src/compressor/compressor.py#L42-L46) · [compressor.py:342-377 get_stats()](../src/compressor/compressor.py#L342-L377)

类 docstring 写着:

> 对外暴露 compress() 接口,自动判断压缩级别并执行渐进式压缩。**同时提供量化评测接口,用于 ablation 实验。**

模块 docstring 也写着([compressor.py:11](../src/compressor/compressor.py#L11) 附近):

> **量化评测接口**:compression_ratio + information_retention

**实测:`get_stats` 在 `src/` + `evaluation/` 里被调用的总次数 = 0。**

项目里一共有 **5 个类**各自定义了同名 `get_stats`(`ContextCompressor`、`ExtractiveCompressor`、`SlidingWindowCompressor`、`LLMSummarizer`、`experience_memory`),**全项目没有任何一处调用 `get_stats()`**。

**所以 `compression_ratio` 和 `information_retention` 这两个指标是"算得出来,但没人看"。** 这和 M5 的 `to_json`/`from_json`(零调用点)、评测层的 `compute_composite_score` 是**同一类问题:接口写好了,评测没接上**。

> ⚠️ **这是"简历句 vs 代码"风险最高的一处组合**。你的 v5 简历第 ④ 句没有出现"压缩比"这个词,**这是对的**;但如果面试官追问"**你压缩前后的效果怎么衡量?**",标准答案必须是:
>
> "我实现了一套量化接口——**压缩比**和**信息保留率**——但坦白讲**它没有接进评测流程,是待办**。而且我现在会重新设计那两个指标:**保留率用的是启发式口径**(统计数字实体和英文专有名词的出现比例,见 [compressor.py:315-340](../src/compressor/compressor.py#L315-L340)),**它只覆盖'硬信息',抓不到论点和逻辑关系的丢失**。更好的做法是加一个**下游任务指标**:同一道题,用压缩前和压缩后的上下文各跑一遍,比最终答案质量。"
>
> **三句话:承认现状 → 说清口径的局限 → 给出更好的方案。** 这比硬说"我做过压缩效果评测"安全一万倍。

```
消融开关      ✅ 写进配置    →    no_compressor 臂不生效(无消费点)
```

**一句话总结这个模块的处境:代码是对的,接线是不通的。**

> **面试时的黄金答法(把这一整步浓缩成一段)**:
> "这个模块**算法部分是完整且正确的**——分级逻辑、TextRank、三级兜底我都实测过。但**接线有问题**:它唯一的调用点在'记忆语义检索返回空'的回退分支上,而且闸门是 6000 字符,可 L1 的启动门槛是预算的 60%(约 2.9 万字符),**两个数字差了近 5 倍**,所以**在真实运行里它几乎总是算出一级都不压、原样返回**。
> **我实测过这个:输入 6000 字符,输出还是 6000 字符,而那行日志还会打印'compressed'。**
> **修法很清楚**:把闸门从'固定 6000 字符'改成'占预算比例'(和内部门槛用同一个口径),并且**优先接到多轮研究循环上——那里才是上下文真正涨得快的地方**。"

## 第 11 步 · 本篇小结

**这一讲要带走三件事:**

1. **三组阈值 + 两个常量**:占用率门槛 `60%/80%/95%`、换算常量 `3.5 字符/token` 和 `2048 token 输出预留`、对应字符数 `2.9万/3.9万/4.6万`。**它们必须能脱口而出,因为第 7 步的"闸门错配"就是靠这几个数推出来的。**
2. **三级的技术栈与取舍**:向量粗筛 → TextRank 图算法 → LLM 摘要;**前两级抽取式(无幻觉风险、便宜)、第三级生成式(有幻觉风险、贵)**。这个排序本身就是设计决策,是这一条里最值得讲的东西。
3. **一个必须承认的现实**:这个模块**算法是对的、接线是不通的**。诚实说清"它在真实运行里几乎不触发",比含糊其辞安全得多——**而且能顺势讲出"该接在多轮研究循环上",展示你知道瓶颈在哪。**
