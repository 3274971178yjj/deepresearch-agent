> 第 1 包(枚举、`@classmethod`、`dict[...]` 注解、`copy.deepcopy`、集合 `&`、f-string `.2f`、`np.argsort()[::-1]`)见 [02 第 0 步](02-核心模块细节笔记.md)。
> 本包是**并发那一套**。看不懂这 8 个,第 3、4 步的代码就会卡住。

| 语法 | 例子 | 人话 |
|---|---|---|
| `asyncio.Semaphore(n)` | `sem = asyncio.Semaphore(5)` | **停车场闸机**。一共 5 个车位,第 6 辆车必须在门口等着 |
| `async with` | `async with sem:` | **自动闸机**。进去刷一次卡占位,出来自动抬杆,不用手写"释放" |
| `asyncio.wait_for(x, timeout=N)` | `await asyncio.wait_for(f(), timeout=300)` | **沙漏**。300 秒没跑完就掐断,抛 `asyncio.TimeoutError` |
| `asyncio.gather(*任务, return_exceptions=True)` | `await asyncio.gather(*coros, return_exceptions=True)` | **一起等**。`return_exceptions=True` 让"报错"也当成一个正常结果收回来,而不是把整队掀翻 |
| `deque` + `popleft()` | `q = deque([1,2]); q.popleft()` | **双端队列,左端出队是 O(1)**。用它做 Kahn 算法的"待处理队列"比 list 快 |
| `defaultdict(list)` | `d = defaultdict(list); d["x"].append(1)` | **缺键自动建空列表**。不用先 `if key not in d` |
| `raise X from e` | `raise PlanParseError(...) from e` | **异常链**。抛新错误但保留原始错误,报错时两个都看得到 |
| `field(default_factory=list)` | `deps: list[str] = field(default_factory=list)` | **dataclass 的可变默认值**。不能写 `= []`,那样所有实例会共用同一个列表 |

> 💡 **一句话记住 `async with sem` 的价值**:它保证**异常路径也会释放**。如果手写 `sem.release()`,中间抛异常就永远漏掉一个车位,跑久了并发度会悄悄掉到 0。

## 第 1 步 · 大白话:为什么需要一个"编排引擎"

先讲问题。

假设你要做一个深度研究 Agent,用户问"对比 GPT-4o、Claude 3.5 和 DeepSeek-V3 的推理能力"。这一句话要拆成好几件事:

- 查三家的官方 benchmark 数字
- 查三家的定价和上下文长度
- 查第三方评测(比如 LMSYS 榜单)
- 把上面三块拼成对比结论

**这四件事里,前三件互不依赖,可以同时做;第四件必须等前三件都完成。**

朴素写法是这样:

```python
r1 = await do_task_1()
r2 = await do_task_2()
r3 = await do_task_3()
r4 = await do_task_4(r1, r2, r3)
```

问题在哪?**`r1` 花 3 分钟,`r2` 花 1 分钟,但这 3 分钟里 `r2` 干等着。** 总耗时 = 3+1+1+2 = 7 分钟,而理论最短是 3+2 = 5 分钟。

改成一起发:

```python
r1, r2, r3 = await asyncio.gather(do_task_1(), do_task_2(), do_task_3())
r4 = await do_task_4(r1, r2, r3)
```

耗时降到 5 分钟。**但新问题来了:**

1. `gather` 里 `do_task_2()` 抛异常,会怎样?→ 默认**整个 `gather` 一起炸**,`r1` 和 `r3` 白跑
2. 其中一个卡住 20 分钟不返回呢?→ **无限等下去**
3. 题目复杂到拆出 30 个子任务,**同时发 30 个请求会不会把 API 打爆 / 超配额**?
4. 有的任务依赖前置结果,**"哪些能同时发"这件事本身需要算**
5. 跑挂了之后,已经拿到的结果**要不要扔掉重来**?

**编排引擎就是回答这五个问题的。**

这个项目给的五条答案,一一对应:

| 问题 | 答案 | 在哪 |
|---|---|---|
| 1. 一个炸了全炸 | `gather(..., return_exceptions=True)` + 任务内部自己消化异常 | [orchestrator.py:286](../src/orchestrator/orchestrator.py#L286) |
| 2. 卡住不返回 | `asyncio.wait_for` 给每个任务单独设超时 | [orchestrator.py:263-266](../src/orchestrator/orchestrator.py#L263-L266) |
| 3. 打爆 API | `asyncio.Semaphore(5)` 限流 | [orchestrator.py:238](../src/orchestrator/orchestrator.py#L238) |
| 4. 哪些能同时发 | DAG + Kahn 算法分层 | [dag.py:115-149](../src/planner/dag.py#L115-L149) |
| 5. 挂了要不要重来 | 三级降级 + 增量重规划 | [orchestrator.py:519-537](../src/orchestrator/orchestrator.py#L519-L537) |

**记住这张表,它就是"为什么需要编排引擎"的标准答案。** 面试问"你为什么要自研而不用 LangGraph",就可以从这五个问题切入——不是因为 LangGraph 不能做,而是**这五个决策点你自己定过,所以每一处为什么这么选你答得出来**。

## 第 2 步 · 九个状态分别是哪九个

### 2.1 状态定义

👉 **本地阅读代码**:[schemas.py:29-45 OrchestratorState(九状态枚举)](../src/orchestrator/schemas.py#L29-L45)

```python
class OrchestratorState(Enum):
    """M1 编排层 9 状态状态机。

    正常流: IDLE → PLANNING → DISPATCHING → COLLECTING → SYNTHESIZING → ADVERSARIAL → DONE
    异常流:
      - 局部失败 → REPLANNING (增量重规划) → DISPATCHING
      - 全局失败 / 超过最大重规划次数 → FAILED
    """
    IDLE = "idle"
    PLANNING = "planning"
    DISPATCHING = "dispatching"
    COLLECTING = "collecting"
    SYNTHESIZING = "synthesizing"
    ADVERSARIAL = "adversarial"
    REPLANNING = "replanning"
    DONE = "done"
    FAILED = "failed"
```

**【人话翻译】** 把一次研究运行想象成**做一顿饭**:

| 状态 | 中文 | 在做的事 | 代码入口 |
|---|---|---|---|
| `IDLE` | 待命 | 还没开始 | [orchestrator.py:194](../src/orchestrator/orchestrator.py#L194) |
| `PLANNING` | 备菜 | 把大问题拆成子任务,排好依赖关系 | [orchestrator.py:198](../src/orchestrator/orchestrator.py#L198) |
| `DISPATCHING` | 下锅 | 按"能同时做的就同时做"的原则并发执行 | [orchestrator.py:226](../src/orchestrator/orchestrator.py#L226) |
| `COLLECTING` | 收菜 | 清点哪些成功哪些失败,**判断要不要重做** | [orchestrator.py:303](../src/orchestrator/orchestrator.py#L303) |
| `SYNTHESIZING` | 装盘 | 把结果合成一份完整报告 | [orchestrator.py:371](../src/orchestrator/orchestrator.py#L371) |
| `ADVERSARIAL` | 尝咸淡 | 让"找茬 Agent"挑毛病、"修补 Agent"改 | [orchestrator.py:435](../src/orchestrator/orchestrator.py#L435) |
| `REPLANNING` | 重开菜单 | 失败的菜太多,重新规划 | [orchestrator.py:465](../src/orchestrator/orchestrator.py#L465) |
| `DONE` | 上桌 | 终态 | [orchestrator.py:507](../src/orchestrator/orchestrator.py#L507) |
| `FAILED` | 弃疗 | 终态 | [orchestrator.py:511](../src/orchestrator/orchestrator.py#L511) |

### 2.2 状态转移图

```text
                    ┌──────────────────────────────────────────┐
                    ↓                                          │
   IDLE → PLANNING → DISPATCHING → COLLECTING → SYNTHESIZING → ADVERSARIAL → DONE
                  ↑                    │                                    
                  │                    │ 失败率>50% 且 replan<3 次           
                  └──── REPLANNING ←───┘

   全局超时(状态下在 COLLECTING/SYNTHESIZING/ADVERSARIAL) ───────→ SYNTHESIZING
   全局超时(其他状态) ──────────────────────────────────────────→ FAILED      
```

### 2.3 状态机是怎么实现的:**字典映射,不是 if/elif**

👉 **本地阅读代码**:[orchestrator.py:84-94 状态处理函数表](../src/orchestrator/orchestrator.py#L84-L94)

```python
# 状态机处理器映射
self._state_handlers: dict[OrchestratorState, Callable[[], asyncio.Future[OrchestratorState]]] = {
    OrchestratorState.IDLE: self._on_idle,
    OrchestratorState.PLANNING: self._do_planning,
    OrchestratorState.DISPATCHING: self._do_dispatching,
    OrchestratorState.COLLECTING: self._do_collecting,
    OrchestratorState.SYNTHESIZING: self._do_synthesizing,
    OrchestratorState.ADVERSARIAL: self._do_adversarial,
    OrchestratorState.REPLANNING: self._do_replanning,
    OrchestratorState.DONE: self._on_done,
    OrchestratorState.FAILED: self._on_failed,
}
```

**【人话翻译】** 每个状态配一个"处理函数",函数**返回下一个状态**。

这比写一长串 `if state == "idle": ... elif state == "planning": ...` 好在哪?

1. **加一个状态只需要加一行映射**,不用改任何分支逻辑
2. **每个处理函数的返回值就是唯一的转移声明**,状态图是"可枚举"的——你甚至能自动生成上面那张转移图
3. 主循环只有一处 `await handler()`,**所有状态共享同一套超时/日志/异常处理**

这是"状态机"和"状态枚举 + if-else"的本质区别。面试被问"你的状态机是怎么实现的",答"**字典映射 + 每个处理函数返回下一状态**",比答"我用了 Enum"高一个层次。

## 第 3 步 · 带读代码:主循环（**本讲核心**）

### 3.1 先看代码

👉 **本地阅读代码**:[orchestrator.py:100-144 run()(主入口 + 状态机主循环)](../src/orchestrator/orchestrator.py#L100-L144)

拆成三段看。

**第一段:每次运行前的状态重置**（[orchestrator.py:111-120](../src/orchestrator/orchestrator.py#L111-L120)）

```python
self._query = query
self._config = config or RunConfig()
self._start_time = time.monotonic()      # ← 注意:用 monotonic,不是 time.time()
self._replan_count = 0
self._adversarial_count = 0
self._memory_store.clear()
self._results.clear()
self._dag = None
self._task_map.clear()
self._current_state = OrchestratorState.IDLE
```

**【人话翻译】** 这是**关键的工程细节**:`_start_time` 用 `time.monotonic()` 而不是 `time.time()`。

为什么?因为 `time.time()` 读的是**墙上时钟**,用户改系统时间、NTP 校时、夏令时切换都会让它跳变。`time.monotonic()` 是**单调递增**的,只保证"一直往前走",专门用来算"过了多久"。**用 `time.time()` 算耗时,可能算出负数。**

> 💡 这个小点**面试价值很高**。被问"你怎么算耗时的",答"用 `monotonic` 而不是 `time.time`,因为后者会受系统时钟调整影响",直接体现工程素养。

**第二段:主循环 + 全局超时检查**（[orchestrator.py:123-135](../src/orchestrator/orchestrator.py#L123-L135)）

```python
# 状态机主循环
while self._current_state not in (OrchestratorState.DONE, OrchestratorState.FAILED):
    # 全局超时检查
    if self._is_global_timeout():
        if self._current_state in (
            OrchestratorState.COLLECTING,
            OrchestratorState.SYNTHESIZING,
            OrchestratorState.ADVERSARIAL,
        ):
            # 强制合成：用已有结果生成报告
            self._current_state = OrchestratorState.SYNTHESIZING
        else:
            self._current_state = OrchestratorState.FAILED
        break
```

**【人话翻译】** 循环条件写的是**"只要还没到终态就继续转"**——`DONE` 和 `FAILED` 是仅有的两个出口。

超时后的分支是个**白名单**:只有当前在 `COLLECTING` / `SYNTHESIZING` / `ADVERSARIAL` 这三个状态,才"抢救一下,拿已有结果强制合成";其他状态直接判死。

**为什么是这三个状态?** 因为走到这三个状态时,**结果已经在手上了**——`COLLECTING` 说明调度已经跑完、`SYNTHESIZING` 说明正在合成、`ADVERSARIAL` 说明报告已经出来了。这时候超时,丢掉太可惜。

反过来如果在 `PLANNING`(还没拆题)或 `REPLANNING`(连计划都没有)超时,**手上什么都没有**,强行合成就只能产出空报告,不如老实报告失败。

**第三段:取处理函数并执行**（[orchestrator.py:137-142](../src/orchestrator/orchestrator.py#L137-L142)）

```python
handler = self._state_handlers.get(self._current_state)
if handler is None:
    raise RuntimeError(f"Unknown state: {self._current_state}")

next_state = await handler()
self._current_state = next_state

print(f"[Orchestrator] State transition: {self._current_state.value}")
```

**【人话翻译】** 三件事:**查表 → 执行 → 把返回值当成新状态**。

`handler is None` 那两行是**防御性编程**:理论上枚举里的每个值都在映射表里,但万一以后有人加了新状态忘了注册,这里会立刻炸一个明确的错误,而不是默默死循环。

`print` 那一行是**可观测性**——因为这个项目没有日志框架统一接管编排器的状态流转,用的是 `print`。**这是个可讲的改进点**:应该换成 `logging` 并带上 `session_id`。

### 3.2 ⚠️ 本讲第一个重要发现:全局超时是"**软超时**"

这是读代码才能发现的真相,面试官很可能会追。

看这一行:

```python
next_state = await handler()      # ← 这一行没有外层 timeout
```

`handler()` 里可能是 `_do_dispatching()`,而它内部会跑完**所有**并行层才返回。**这个 `await` 没有任何外层超时保护。**

再看 `_is_global_timeout()`:

👉 **本地阅读代码**:[orchestrator.py:543-546 _is_global_timeout()](../src/orchestrator/orchestrator.py#L543-L546)

```python
def _is_global_timeout(self) -> bool:
    """检查是否超过全局超时。"""
    elapsed = time.monotonic() - self._start_time
    return elapsed > self._config.global_timeout_seconds
```

**它只在循环顶部被调用一次。** 于是:

> **600 秒的全局超时,不是硬约束,而是"状态切换间隙的软检查"。**

具体后果:

| 场景 | 实际行为 |
|---|---|
| `DISPATCHING` 跑了 40 分钟 | **不会被打断**。40 分钟后它返回,进入 `COLLECTING`,此时循环顶部才发现超时 → 转 `SYNTHESIZING` 抢救 |
| `PLANNING` 卡住 20 分钟 | 同理,不会被中断;返回后循环顶部发现超时,因为状态是 `COLLECTING`(规划成功后转的),**反而会走抢救分支** |
| 想靠 600 秒兜住"整次运行的上限" | **做不到**。真正兜住的是每个子任务的 `SubTask.timeout_seconds`(默认 300 秒)和 TCP/HTTP 超时 |

**所以 165 次实验跑 12 小时、平均单次 4.4 分钟,并不矛盾——** 单次运行的实际耗时由"子任务超时 × 层数"决定,600 秒只是一个"别再继续烧钱"的软闸门。

**【面试怎么答这个问题】**

> "这是个我知道的设计局限。600 秒的全局超时是**状态切换之间的检查**,不是硬中断。因为每个状态处理函数是一个大的 `await`,外面没套 `wait_for`,所以它只在状态返回之后才生效。
>
> 影响是:**单次运行的实际上限由子任务超时决定,不是 600 秒**。要真正硬约束,应该把主循环体包一层 `asyncio.wait_for`,或者给每个状态处理函数单独设预算。
>
> 当时没这么做,是因为超时后还要**优雅降级**(拿已有结果合成)而不是直接取消——直接 `cancel()` 会把 `finally` 里的 Agent 归还逻辑打断,池子会漏。"

**注意这个回答的结构**:承认局限 → 说清影响 → 给正确方案 → **解释当时为什么不这么做**。最后一步是绝大多数候选人答不出来的,而它恰好证明你**真的理解自己的代码**。

## 第 4 步 · 带读代码:并发调度（Semaphore + gather + wait_for）

### 4.1 三层结构

👉 **本地阅读代码**:[orchestrator.py:226-301 _do_dispatching()](../src/orchestrator/orchestrator.py#L226-L301)

```
for 每一层 (拓扑层):
    ├─ 构建本层所有任务的协程
    ├─ 每个协程内部: 抢信号量 → 执行 → 归还 Agent
    └─ asyncio.gather 一起等
```

### 4.2 第一层:信号量建在**层循环之外**

👉 **本地阅读代码**:[orchestrator.py:238-243](../src/orchestrator/orchestrator.py#L238-L243)

```python
semaphore = asyncio.Semaphore(self._config.max_concurrent)
parallel_groups = self._dag.get_parallel_groups()
all_results: list[AgentResult] = []

for layer_idx, group in enumerate(parallel_groups):
    print(f"[Dispatch] ▶ Layer {layer_idx + 1}/{len(parallel_groups)}: {group} (并行执行)")
```

**【人话翻译】** 注意 `semaphore` 是在 `for` **外面**建的。

**这个位置很重要**:如果建在循环内部,每层都会有独立的 5 个名额——但层与层之间其实是串行的(下一层依赖上层),所以那样写看起来没区别、实际也一样。**但建在外面表达的是"整次运行的全局并发上限是 5"这个语义**,而且为将来"层间流水线"留了口子。

`max_concurrent` 来自配置,**默认 5**。

### 4.3 第二层:单个任务怎么跑——**三层异常防护**

这是本讲最需要逐行读的一段。

👉 **本地阅读代码**:[orchestrator.py:246-282 _run_one(单任务执行 + 三层防护)](../src/orchestrator/orchestrator.py#L246-L282)

```python
async def _run_one(task_id: str) -> AgentResult:
    async with semaphore:                      # ① 抢车位
        subtask = self._task_map.get(task_id)
        if subtask is None:
            return AgentResult(
                task_id=task_id,
                status=AgentStatus.FAILED,
                output=f"SubTask '{task_id}' not found in task_map",
            )

        # 准备上下文：先执行依赖任务的结果
        context = self._build_task_context(subtask)

        # 获取 Agent
        agent = await self.agent_pool.get_agent(subtask.task_type)
        try:
            # 设置单任务超时
            result = await asyncio.wait_for(     # ② 沙漏
                agent.run(subtask, context),
                timeout=subtask.timeout_seconds,
            )
        except asyncio.TimeoutError:             # ③ 超时 → 标记,不抛
            result = AgentResult(
                task_id=task_id,
                status=AgentStatus.TIMEOUT,
                output=f"Task timed out after {subtask.timeout_seconds}s",
            )
        except Exception as e:                   # ④ 其他异常 → 标记,不抛
            result = AgentResult(
                task_id=task_id,
                status=AgentStatus.FAILED,
                output=f"Exception: {type(e).__name__}: {e}",
            )
        finally:
            await self.agent_pool.release_agent(agent)   # ⑤ 无论成败都归还

        return result
```

**【人话翻译】** 逐层拆:

**① `async with semaphore`** —— 抢车位。`async with` 保证**离开时自动释放**,哪怕是异常路径。

**② `asyncio.wait_for(..., timeout=subtask.timeout_seconds)`** —— 给这一个任务套沙漏。默认 `SubTask.timeout_seconds = 300`（见 [schemas.py:86](../src/orchestrator/schemas.py#L86)）。

**③④ 两个 `except`——关键在这里。**

注意:**超时和异常都被"接住"了,变成了 `AgentResult` 对象返回,而不是继续往外抛。**

> **这就是"单任务超时标记继续,不阻塞整层"的全部秘密。**
>
> 因为异常在 `_run_one` **内部**就被消化成了返回值,所以外面 `gather` 拿到的东西**永远是 `AgentResult`,不是异常**。

**⑤ `finally: await ...release_agent(agent)`** —— **无论成功、超时还是异常,Agent 都会归还池子。** 少了这一句,每失败一次就漏一个 Agent,跑久了池子枯竭。

### 4.4 第三层:gather 与"第二道保险"

👉 **本地阅读代码**:[orchestrator.py:284-298](../src/orchestrator/orchestrator.py#L284-L298)

```python
# 并发执行本层
coros = [_run_one(tid) for tid in group]
layer_results = await asyncio.gather(*coros, return_exceptions=True)

for lr in layer_results:
    if isinstance(lr, Exception):
        # 将异常包装为 FAILED 结果
        # 这种情况理论上不会发生（_run_one 内部已捕获），但保险起见
        all_results.append(AgentResult(
            task_id="unknown",
            status=AgentStatus.FAILED,
            output=f"Dispatch exception: {lr}",
        ))
    else:
        all_results.append(lr)
```

**【人话翻译】** `isinstance(lr, Exception)` 这个判断——**代码注释自己写了"理论上不会发生"**。

那为什么还留着?

因为 `_run_one` 里接住的是 `agent.run()` 的异常。但如果异常发生在 `agent.run()` **之外**——比如 `self.agent_pool.get_agent()` 抛了(池子创建 Agent 时内存不足)、或者 `self._build_task_context()` 抛了——**那些不在 try 块里,会真的抛出去**。这时候 `return_exceptions=True` 就是唯一的防线。

**这是一个"纵深防御"的典型样例**:一层不够就加第二层,而且第二层要能容忍"第一层理论上不会漏"。

**面试价值**:被问"`return_exceptions=True` 是干嘛的",很多人答"防止一个失败全挂"。你可以答得更准:

> "它是**第二道保险**。第一道在任务函数内部——超时和异常都被转成了结果对象,所以正常情况下 `gather` 拿不到异常。但上下文构建、Agent 取用这些地方不在 try 块里,那些位置抛的异常会漏出来,`return_exceptions=True` 兜住它们。代码注释里也写了'理论上不会发生,但保险起见'。"

### 4.5 一句话总结这一节

> **`Semaphore` 限并发、`wait_for` 限时长、`gather` 收异常、`finally` 保归还 —— 四个机制合起来,才叫"单任务失败不阻塞整层"。**

面试口播版（内部名词已下沉）:

> "并发是三层防护叠出来的:任务内部把超时和异常都转换成结果对象;每个任务有独立超时;最后再让并发收集器把兜底的异常也收成结果。所以任何单个子任务出问题,都只是变成一条'失败记录',不会影响同一层的其他任务。"

## 第 5 步 · 带读代码:三级降级，逐级落地

简历第 ② 句的后半句就是三级降级。**这三级要能分别指出代码位置,且阈值要背准。**

### 5.1 三级总览

| 级别 | 触发条件 | 动作 | 代码位置 |
|---|---|---|---|
| **第一级** | 单个子任务超时或异常 | 标记 `TIMEOUT`/`FAILED`,**继续跑同层其他任务** | [orchestrator.py:267-278](../src/orchestrator/orchestrator.py#L267-L278) |
| **第二级** | 失败率 **> 50%**,或 成功率 **< 30%** 且有失败 | 进入增量重规划,上限 **3 轮** | [orchestrator.py:519-537](../src/orchestrator/orchestrator.py#L519-L537) |
| **第三级** | 全局耗时 **> 600 秒** | 强制合成(仅限三个状态);否则判失败 | [orchestrator.py:124-135](../src/orchestrator/orchestrator.py#L124-L135) |

**这三级的划分逻辑是"失败归因"**:
- 第一级 = **单点故障**（一个任务的问题,不该拖累别人）
- 第二级 = **计划失效**（失败的太多,说明拆题方式本身有问题,要重拆）
- 第三级 = **预算超支**（钱/时间花完了,拿现有产出收尾）

**记住这个"单点故障 / 计划失效 / 预算超支"的三分法**,这是简历里的原话,也是最好记的锚点。

### 5.2 第二级的精确阈值（**必背**）

👉 **本地阅读代码**:[orchestrator.py:519-537 _should_replan()](../src/orchestrator/orchestrator.py#L519-L537)

```python
def _should_replan(self, results: list[AgentResult]) -> bool:
    """判断是否需要重规划。

    策略:
      - 失败率 > 50% 时触发
      - 或存在任何 TIMEOUT 且成功结果不足 30%
    """
    if not results:
        return False
    total = len(results)
    failed = sum(1 for r in results if r.status in (AgentStatus.FAILED, AgentStatus.TIMEOUT))
    success = sum(1 for r in results if r.status == AgentStatus.SUCCESS)

    failure_rate = failed / total
    if failure_rate > 0.5:
        return True
    if success / total < 0.3 and failed > 0:
        return True
    return False
```

**【人话翻译】** 三个必须说清的细节:

**细节 1:`failed` 同时包含 `FAILED` 和 `TIMEOUT`。** "失败率"不是只算报错的,超时也算。

**细节 2:第二个条件的 `and failed > 0` 是防呆。**

看这个反例:如果 `results` 是**空列表**,`_should_replan` 在开头就 `return False` 了,没问题。
但如果 **`success/total < 0.3` 而 `failed == 0`**——数学上可能吗?
`success + failed = total`,所以 `failed == 0` 意味着 `success == total`,即 `success/total == 1.0`,`< 0.3` 不成立。

**所以 `and failed > 0` 在数学上是冗余的。** 那为什么写?**因为它是"意图声明"**:作者想表达的是"**有失败**且**成功的太少**才重规划",而不是"成功率低就重规划"。同时它也防住了未来引入第三种 `AgentStatus` 时的不变式被破坏。

**这是一个很好的"我读过自己的代码"的细节**——被问"这两个条件的优先级",能顺口讲出这个冗余判断的用意。

**细节 3:这里是"全局失败率",不是"本层失败率"。**

`_do_collecting` 是在**所有层跑完之后**才被调用的,传进去的 `self._results` 是**所有层累积的结果**（见 [orchestrator.py:300](../src/orchestrator/orchestrator.py#L300)）。

所以判定的是**整次运行的失败比例**,不是某一层。**这点如果答错("每层检查一次")就露馅了。**

### 5.3 第二级的轮数上限与"重规划后清空"

👉 **本地阅读代码**:[orchestrator.py:331-340](../src/orchestrator/orchestrator.py#L331-L340)

```python
# 检查是否需要重规划

    if self._replan_count < self._config.max_replan_rounds:
        self._replan_count += 1
        return OrchestratorState.REPLANNING
    else:
        print("[Collect] Max replan rounds reached, proceeding with partial results")
        # 超过最大重规划次数，继续合成（用已有结果）
```

**【人话翻译】** 超过 3 轮就**不再重规划,带着残缺结果去合成**。

这是"降级"的精髓:**宁可交一份不完整的报告,也不能无限重试**。因为重试本身也在烧 token,而且**重试失败的最常见原因(题目太难/LM 不稳定)不会因为多试一次而改变**。

**注意 `else` 分支没有 `return`,所以会继续往下走到 `return OrchestratorState.SYNTHESIZING`** —— 这就是"proceeding with partial results"的实现。**如果这里写成 `return FAILED`,整次研究就白跑了。**

### 5.4 重规划真的做了什么

👉 **本地阅读代码**:[orchestrator.py:465-505 _do_replanning()](../src/orchestrator/orchestrator.py#L465-L505)


真正做过滤的是规划器：

**【人话翻译】** 分工是这样的:

| 谁 | 负责什么 |

⚠️ **顺带一个诚实提醒**:`_do_replanning` 的 docstring 与实现**分家了**——docstring 描述的过滤逻辑实际在 planner 里。这种"注释说 A 处做了 X,实际 B 处做的"是**读代码时最容易上当的地方**。

> **这个细节面试价值极高**。被问"你的增量重规划是怎么实现的",答:
> "分两半。编排器负责识别失败任务并给出失败原因;规划器负责把'成功且置信度 0.6 以上'的结果摘要出来,连同失败清单一起交给模型,让它只规划新任务、不要重复已完成的部分。**这个拆分是因为'什么值得保留'是规划策略,不是调度策略。**"

### 5.6 重规划后为什么要清空结果

👉 **本地阅读代码**:[orchestrator.py:487-492](../src/orchestrator/orchestrator.py#L487-L492)

**【人话翻译】** 新计划只包含"重做的任务",所以旧结果列表要清掉——**否则下一轮 `_should_replan` 会把上一轮的失败又数一遍,永远触发重规划,直到耗尽 3 轮。**

旧结果并没有丢:`_memory_store` 里有 `result:{task_id}` 的副本（[orchestrator.py:312-313](../src/orchestrator/orchestrator.py#L312-L313)）,新任务可以通过 `context_keys` 引用它们。

## 第 6 步 · DAG 与 Kahn 算法

### 6.1 为什么需要 DAG

子任务之间有依赖:

```text
  t1 查A家benchmark ──┐
  t2 查B家benchmark ──┼──→ t4 三方对比 ──→ t5 写结论
  t3 查C家benchmark ──┘
```

`t1/t2/t3` 可以同时做;`t4` 必须等三个都完成;`t5` 等 `t4`。

这个结构就是**有向无环图**(DAG):箭头有方向(依赖关系),"无环"保证不会出现"A 等 B、B 等 A"的死锁。

### 6.2 两种排序的**区别**（容易答混）

👉 **本地阅读代码**:[dag.py:85-113 topological_sort()(Kahn 全序)](../src/planner/dag.py#L85-L113) · [dag.py:115-149 get_parallel_groups()(分层并发)](../src/planner/dag.py#L115-L149)

| 方法 | 返回 | 用途 |
|---|---|---|
| `topological_sort()` | `["t1","t2","t3","t4","t5"]` | **一个全序**。每个任务只出现一次,保证"依赖的一定排在前面" |
| `get_parallel_groups()` | `[["t1","t2","t3"], ["t4"], ["t5"]]` | **按层分组**。同层之间无依赖,可以并发 |

**编排器实际用的是 `get_parallel_groups()`**（[orchestrator.py:239](../src/orchestrator/orchestrator.py#L239)）,因为要的是"哪些能一起发",不是一个一个发。

**`topological_sort()` 在编排器里没被调用**——它存在是因为 DAG 是个通用数据结构,规划器解析时也会用到。

> ⚠️ **面试如果问"你是怎么用拓扑排序的",别笼统答"拓扑排序"。** 要答:
> "我用的是**拓扑排序的分层版本**——不是排出一个线性顺序,而是按执行层分组,同层无依赖可并发。这是 Kahn 算法的一个变体,入度归零的节点在每一轮同时出队,而不是一个一个出。"

### 6.3 Kahn 算法的三层保护

**保护 1:自环在建边时就拦掉**（[dag.py:43-55](../src/planner/dag.py#L43-L55)）

```python
def add_edge(self, from_node: str, to_node: str) -> None:
    """添加有向边 from_node -> to_node (to_node 依赖 from_node)。"""
    if from_node == to_node:
        raise DAGCycleError(f"自环不允许: {from_node}")
    ...
```

**保护 2:入度表用拷贝,不污染原图**（[dag.py:124](../src/planner/dag.py#L124) 和 [dag.py:91](../src/planner/dag.py#L91)）

```python
in_deg = dict(self._in_degree)      # ← 拷贝!
```

**【人话翻译】** Kahn 算法要不断减入度。如果直接改 `self._in_degree`,**跑完一次图就废了**——第二次调用会得到错误结果。

`dict(...)` 这一句让方法**可重复调用、无副作用**。这是"纯函数"思维的体现,**面试官如果注意到这一行会加分**。

**保护 3:有环时明确报错并给出排查信息**（[dag.py:107-112](../src/planner/dag.py#L107-L112)）

```python
if len(result) != len(self._nodes):
    # 找出环上的节点，便于调试
    remaining = self._nodes - set(result)
    raise DAGCycleError(
        f"DAG 中存在环，无法完成拓扑排序。剩余节点: {sorted(remaining)}"
    )
```

**【人话翻译】** Kahn 算法检测环的原理很优雅:**如果图里有环,环上的节点入度永远降不到 0,所以永远进不了结果列表。** 最后 `len(result) != len(self._nodes)` 就说明有环。

更漂亮的是它**顺手把环上的节点算出来了**(做集合差)。**报错信息里直接告诉你是哪几个节点成环**,省掉一轮调试。

### 6.4 一个可复现性细节:稳定排序

👉 **本地阅读代码**:[dag.py:129-143](../src/planner/dag.py#L129-L143)

```python
current: list[str] = [n for n in self._nodes if in_deg.get(n, 0) == 0]
# 按字典序稳定排序，保证确定性
current.sort()
```

**【人话翻译】** 注释写得很直白:**"保证确定性"**。

因为底层 `self._nodes` 是 `set`,**Python 的 set 遍历顺序不稳定**(尤其是字符串 hash 会随进程随机化)。如果不排序,同样一个 DAG**每次跑出来的层内顺序都可能不同**。

而层内顺序会影响:
- 信号量的抢位顺序 → 哪个任务先跑
- 日志顺序
- 结果列表顺序 → 影响 `_should_replan` 无关,但影响**可复现性**

**对"可复现评测"这个卖点来说,这一行是必需的。** 面试被问"你怎么保证实验可复现",除了"固定随机种子",还可以答:

> "还有几个容易被忽略的点:比如拓扑分层时对同层节点做了稳定排序,因为底层用的是 set,遍历顺序不稳定,会影响子任务的调度顺序。"

## 第 7 步 · AgentPool:对象池，以及它的两个问题

### 7.1 对象池在做什么

👉 **本地阅读代码**:[agent_pool.py:58-86 get_agent()](../src/orchestrator/agent_pool.py#L58-L86) · [agent_pool.py:88-109 release_agent()](../src/orchestrator/agent_pool.py#L88-L109)

```python
async def get_agent(self, task_type: "TaskType") -> BaseAgent:
    type_key = task_type.value
    ...
    # 尝试复用空闲 Agent
    while self._idle[type_key]:
        agent = self._idle[type_key].pop()
        # 简单健康检查：若 Agent 内部 policy 被标记为截断/污染，则丢弃
        if hasattr(agent, "policy") and getattr(agent.policy, "was_truncated", False):
            self._degraded_count[type_key] += 1
            continue  # 丢弃，尝试下一个
        self._active_count[type_key] += 1
        return agent

    # 新建 Agent
    agent = self._create_agent(type_key)
    self._created_count[type_key] += 1
    self._active_count[type_key] += 1
    return agent
```

**【人话翻译】**

- **"取"的逻辑**:池里有空闲就复用,没有就新建
- **`while` 不是 `if`**:因为要支持"跳过若干个不健康的 Agent"
- **健康检查看 `policy.was_truncated`**:如果这个 Agent 上次的输出被截断了,**不回收也不复用**——因为 `AgentPool` 认为"被截断过的 Agent 状态是被污染的"
- **`max_idle=3`**:每类型最多留 3 个空闲,防止内存膨胀

**这个设计的面试价值**在于它体现了一个真实工程问题:**LLM Agent 是有状态的**(它持有 policy、tools、可能的对话历史),**不能像无状态函数那样随便复用**。所以池化的时候必须加健康检查。"用完就扔"浪费连接和初始化开销,"一直复用"会串味,池化 + 健康检查是折中。

### 7.2 ⚠️ 发现 A:三种任务类型**造出来的是同一个类**

👉 **本地阅读代码**:[agent_pool.py:127-147 _create_agent()](../src/orchestrator/agent_pool.py#L127-L147)

```python
def _create_agent(self, type_key: str) -> "BaseAgent":
    """根据类型键创建对应的 Agent 实例。"""
    policy = self.policy_factory()
    tools = self.tools_factory() if self.tools_factory else []

    from ..agents.researcher import ResearcherAgent
    from ..agents.summarizer import SummarizerAgent
    from .schemas import TaskType

    if type_key == TaskType.SEARCH.value:
        return ResearcherAgent(name=f"researcher_{type_key}", policy=policy, tools=tools)
    elif type_key == TaskType.ANALYZE.value:
        return ResearcherAgent(name=f"analyzer_{type_key}", policy=policy, tools=tools)
    elif type_key == TaskType.VERIFY.value:
        return ResearcherAgent(name=f"verifier_{type_key}", policy=policy, tools=tools)
    elif type_key == "synthesize":
        return SummarizerAgent(name="summarizer", policy=policy, tools=tools)
    else:
        # 默认降级为 Researcher
        return ResearcherAgent(name=f"researcher_default", policy=policy, tools=tools)
```

**【人话翻译】** 看仔细:前三个分支(`SEARCH` / `ANALYZE` / `VERIFY`)**返回的都是 `ResearcherAgent`**,只有 `name` 不一样。

**所以"按任务类型路由到不同 Agent 实现"这个说法**是偏乐观的**。准确说法是:**

> "三种子任务类型目前**共用同一个研究 Agent 实现**,靠不同的 `name` 和不同的 prompt 上下文区分。这是有意为之的简化——事实检索、分析、验证的**工具集是一样的**(都要搜索、读网页),差别在**指令**而不是**能力**。如果将来验证任务要用不同的工具组合(比如专门的 NLI 模型),再拆成独立类。"

**这个回答的技巧**:不否认事实(确实是同一个类),而是解释**为什么这是一个合理的设计决策**,并给出**什么时候该拆**。这比硬说"我有三个 Agent"安全得多。

### 7.3 ⚠️ 发现 B:归还时类型键算错，池化对 2/3 的任务失效

👉 **本地阅读代码**:[agent_pool.py:149-157 _infer_type_key()](../src/orchestrator/agent_pool.py#L149-L157)

```python
def _infer_type_key(self, agent: "BaseAgent") -> str:
    """从 Agent 实例推断其类型键。"""
    # 简单启发式：通过类名推断
    cls_name = agent.__class__.__name__
    if "Summarizer" in cls_name:
        return "synthesize"
    # ResearcherAgent 用于 search/analyze/verify，统一归到 search
    from .schemas import TaskType
    return TaskType.SEARCH.value          # ← 一律归到 "search"
```

**【人话翻译】** 这里有个**真实的类型键不一致**:

| 环节 | `type_key` |
|---|---|
| `get_agent(ANALYZE)` 取出时 | `"analyze"` |
| `release_agent()` 归还时 | `"search"`（因为 `_infer_type_key` 一律返回 search） |

**后果链条:**

1. 一个 `ANALYZE` 任务结束,Agent 被塞进 `_idle["search"]`
2. 下一个 `ANALYZE` 任务来,查 `_idle["analyze"]` → **空的** → 新建一个 Agent
3. **所以 `ANALYZE` 和 `VERIFY` 类型完全享受不到池化复用**,每次都新建
4. 而 `_active_count["analyze"]` **只增不减**（`release` 减的是 `_active_count["search"]`,那个会**减成负数**后被 `max(0, ...)` 夹住）

**这是 bug 吗?** 严格说是**两部分**:
- **功能上无害**:`_active_count` 只被 `get_stats()` 用于监控,不参与任何调度决策（代码注释也写了"非精确对象追踪"）
- **统计上是错的**:`get_stats()` 返回的 active 数字不可信

**面试怎么处理这个?** 这是**最好的那类"主动坦白"素材**,因为它证明你真的读过每一行:

> "这里有个我知道的小问题:Agent 归还池子的时候,类型是根据类名反推的——而三种研究任务用的是同一个类,所以归还时全部落进了 `search` 池。结果是分析和验证类型的 Agent 实际上没有复用,而且监控计数器会漂移。
>
> 功能上没影响,因为那个计数器不参与调度。但这是**类型键不统一**的典型症状——正确做法是让 Agent 自己记住创建时的类型,或者用 `dict` 做 `id(agent) -> type_key` 的映射,而不是靠类名反推。"

**顺带说一个更值钱的点**:`_infer_type_key` 用**类名反推类型**本身就是脆弱设计——它是"字符串启发式",而不是类型系统保证的。这类代码在重构时最容易悄悄失效。

### 8.2 ⚠️ 发现 D:对抗不是无条件跑的

👉 **本地阅读代码**:[orchestrator.py:435-452 _do_adversarial() 的置信度门](../src/orchestrator/orchestrator.py#L435-L452)

```python
async def _do_adversarial(self) -> OrchestratorState:
    report = self._memory_store.get("final_report")
    if report is None:
        return OrchestratorState.DONE

    # 置信度足够高时跳过对抗
    if report.confidence >= 0.8:
        print("[Adversarial] ✓ 报告置信度已达标 (≥0.8)，跳过对抗优化")
        return OrchestratorState.DONE

    if self.adversarial_loop is None:
        print("[Adversarial] AdversarialLoop 未配置，跳过")
        return OrchestratorState.DONE
```

**【人话翻译】** 对抗循环有**三道门**,任何一道不通过就直接跳到 `DONE`:

1. 报告对象缺失 → 跳过
2. **置信度 ≥ 0.8 → 跳过**
3. 对抗循环未配置 → 跳过

**第 2 道门很关键**:它意味着**"对抗模块"不是每次运行都会执行的**。如果你要跑"完整 vs 关掉对抗"的消融实验,得注意:两组都可能在置信度达标时跳过对抗,那这个对比就不纯粹了。

> 💡 **这条对"要不要跑消融"这件事是有实际影响的信息**——如果真跑,得先把 `0.8` 这个门处理掉,否则对照组的差异会被稀释。

| Technical | 为什么不直接用 LangGraph? | 因为核心决策点我需要自己定。比如全局超时到底是硬中断还是软检查、子任务超时该设多少、重规划时哪些结果值得保留——这些在框架里是配置项或黑盒,自己写才能把每个 trade-off 讲清楚。**⚠️ 这题有两个陷阱,完整答法见文末【附加题】**（一是你其实用了 LangSmith,二是 networkx 有个 `topological_generations` 能做同样的事）。 |
| Technical | 一个子任务挂了会怎样? | 三层保护。任务函数内部把超时和异常都转成"失败记录"而不是往上抛;每个任务有独立超时;最后并发收集器还把兜底的异常也收成结果。所以任何单个任务出问题,只是少一条结果,不影响同层其他任务。 |
| Technical | 三级降级是什么? | 按失败归因分三级:①单点故障——单个任务超时或报错,标记后继续,不阻塞整层;②计划失效——失败率超 50%,或成功率不足 30% 且有失败,触发重规划,最多 3 轮;③预算超支——全局超时,拿已有结果强制合成。 |
| Technical | 重规划为什么是"增量"的? | 因为重跑全部太贵。编排器负责挑出失败的任务并说明失败原因,规划器负责把"成功且置信度 0.6 以上"的结果摘要出来一起交给模型,让它只规划新任务、不重复已完成的部分。 |
| Technical | 并发度怎么控制的? | 信号量。它建在层循环外面,所以是整个运行的全局上限,不是每层各 5 个。 |
| Technical | 任务数量上限怎么控制的? | ⚠️ **如实说**:"这里我要承认一个缺陷——我配了一个子任务数量上限的参数,从配置文件读进了运行时配置,但**没有任何逻辑消费它**。真正决定拆几个子任务的是规划提示词里的硬编码区间。这是典型的配置项存在但未接线。" |
| Technical | "哪些任务能同时跑"怎么算的? | 用一个无环有向图表示依赖,然后做**拓扑排序的分层版本**——不是排出一个线性顺序,而是按执行层分组,入度归零的节点每一轮同时出队,同层之间无依赖可并发。图里有环会直接报错并指出是哪几个节点成环。 |
| Technical | 怎么保证实验可复现? | 除了固定随机种子,还有几个容易漏的点。比如拓扑分层时对同层节点做了稳定排序——因为底层用的是集合,遍历顺序不稳定,会影响子任务的调度顺序。另外算耗时用单调时钟而不是墙上时钟,后者会受系统时间调整影响。 |
| **Architecture** | **这个模块有什么局限?** | ⭐ **主动讲**:三个。①**全局超时是状态切换之间的软检查,不是硬中断**——状态处理函数是个大 await,外面没套超时,所以单次运行的实际上限由子任务超时决定。要真硬约束得再包一层。②**Agent 池的类型键不统一**——归还时按类名反推类型,而三种任务共用一个类,所以归还时都落进了同一个池,分析和验证类型实际没享受到复用。功能无影响,但监控计数不准。③**对抗有置信度门**——报告置信度到 0.8 就跳过对抗,所以它不是每次运行都执行。 |
| Architecture | 如果重做会怎么改? | 三个优先级:①给状态处理函数加独立时间预算,让全局超时变成真硬约束;②编排器改成可恢复的——现在纯内存状态,批量跑挂一次就得从头,应该做断点续跑;③把"可观测性"做起来——现在是散落的 print,应该统一结构化日志并带上会话 ID。 |

## 本篇小结

- **九个状态**:7 个正常 + `REPLANNING` + `FAILED`。**状态机是字典映射,处理函数返回下一状态。**
- **主循环**:唯一出口是 `DONE`/`FAILED`;**全局超时是软检查**,只在状态切换间隙生效——这是本讲最值钱的发现。
- **并发三件套**:`Semaphore`(限并发,建在层外) + `wait_for`(限时长) + `gather(return_exceptions=True)`(兜异常),再加 `finally` 保 Agent 归还。
- **三级降级**:单点故障 → 计划失效(>50%,或 <30% 且有失败,上限 3 轮) → 预算超支(600 秒强制合成)。**"保留高置信"的过滤在规划器,不在编排器。**
- **DAG**:用的是**拓扑排序的分层版本**,不是全序。入度表用拷贝所以方法无副作用;同层做稳定排序保证可复现。
- **四处实现真相**:软超时、池化类型键不统一、`max_sub_questions` 死配置、对抗有置信度门。**这四条要主动讲。**
- **附加题 · 自研 vs LangGraph**:① 你**用了 LangSmith**（tracing，非编排），但**没用** LangGraph/LangChain 原语——这句区别必须能当场说清;② 别贬低 LangGraph，它**能**做状态图和 fan-out;③ 正面答案是"六个我需要自己定的决策点"（见附加 3 的表）;④ 更难的一问是"**你依赖了 networkx，为什么还自己写 Kahn**"，诚实答案是成环诊断信息 + 无副作用重复调用,并用"如果重做我会评估直接用它的"收口。

**一句话记住这一讲**:*编排引擎的价值不在"我用了状态机",而在"我能说出每个降级阈值为什么是这个数,以及我在哪一处做了简化、代价是什么"。*

### 附加 4 · 还有一道更刁的:**"你依赖了 networkx,为什么还自己写 Kahn?"**

⚠️ **这题比 LangGraph 那题更难,而且更可能被问** —— 因为它是从你自己的依赖文件里长出来的。

事实:`networkx` 已经在你的依赖里（[requirements.txt](../requirements.txt) 里写着
`networkx>=3.0 # 图算法（M3 TextRank 关键句提取）`）。
而 networkx 有一个 **`topological_generations(G)`**,返回的就是**分层的拓扑序** ——
和你的 `get_parallel_groups()`（[dag.py:115](../src/planner/dag.py#L115)）**干的是同一件事**。

**所以"我自己实现了 Kahn"这句话,会立刻招来这一问。** 诚实答案有三条,而且三条都是真的:

1. **我要的异常信息更具体。** 成环时我要报**剩余未排序的节点名**,好直接定位规划器哪里输出了环 ——
   见 [dag.py:109-112](../src/planner/dag.py#L109-L112) 的 `remaining = self._nodes - set(result)`。
   networkx 抛的是泛化的 `NetworkXUnfeasible`,拿不到你真正关心的拓扑残留信息。
2. **我的图是 `dict[str, list[str]]` 邻接表,直接来自规划器的 JSON。**
   转成 `nx.DiGraph` 再转回来是纯开销;而且我另外还要 `to_dict()` 序列化给日志
   （[dag.py:151-156](../src/planner/dag.py#L151-L156)）。
3. **我必须能在同一个对象上反复调用两个方法而不互相污染。**
   `topological_sort()` 和 `get_parallel_groups()` 都要能调,两者都靠
   `dict(self._in_degree)` 做拷贝来保证无副作用（[dag.py:91](../src/planner/dag.py#L91)、
   [:124](../src/planner/dag.py#L124)）。用 networkx 反而要额外写适配层来保证这一点。
4. **顺带一个可复现性理由**:同层节点做 `sort()` 保证确定性（[dag.py:130-131](../src/planner/dag.py#L130-L131)）,
   因为底层用的是 `set`,遍历顺序不稳定。这是我自己踩过才加的。

⚠️ **绝对不要说的两句话:**

| 不能说 | 为什么 |
|---|---|
| "networkx 性能差" | **没有任何 benchmark**,说了就会被要求给数据 |
| "networkx 不支持分层拓扑排序" | **事实错误**,`topological_generations` 就是干这个的 |

**加分收尾（这句会让你显得不是"为了自研而自研"）:**

> **"如果重做,在 networkx 已经是依赖的前提下,我会评估直接用 `topological_generations` 加一层薄封装 —— 手写的 30 行和薄封装 10 行的差别,不足以支撑一个长期的维护负担。当时手写主要是为了成环诊断信息,那个理由现在看仍然成立,但它只值那 10 行,不值 30 行。"**
