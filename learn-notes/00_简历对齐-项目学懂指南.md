## 一、这个项目到底在干什么

**一句话**：用户给一个复杂研究问题（如"对比 2024-2025 大模型 Agent 技术与后端开发的发展"），系统自动拆解问题、并发检索多个信息源、压缩整理上下文、用"攻击-修复"对抗循环打磨报告，最终输出一份带引用、带置信度的 Markdown 研究报告。

**它解决什么问题**（面试开场白，背下来）：

大模型直接回答复杂研究问题有三大痛点：
1. **信息过载与上下文遗忘**——检索回来的长文本把关键信息淹没，模型记不住前面的内容；
2. **幻觉与事实漂移**——多轮推理中模型倾向于编造未经验证的事实；
3. **缺乏系统性评估**——"深度研究报告"这种输出形态没有现成的端到端评测方法。

对应的三层解法：**多智能体编排**（拆解+并发+记忆）解决第一个，**Red-Blue 对抗循环**解决第二个，**三层评测体系**解决第三个。

**系统全链路**（一次请求的完整旅程）：

```
用户 Query
  ↓ M2 Planner：LLM 把问题拆成 3~10 个子任务的 DAG（谁依赖谁）
  ↓ M1 Orchestrator：9状态状态机接管
      ├─ Kahn 算法把 DAG 分成"执行层"，同层无依赖 → 可并行
      ├─ Semaphore(5) 限流，asyncio.gather 并发派发给子 Agent
      ├─ 每个子 Agent 拿着工具（搜索/arXiv/浏览器/计算器…）干活
      ├─ 干完的结果写入 M4 共享记忆（去重、矛盾检测）
      └─ 失败了？三级降级：超时标记继续 / 失败率>50% 重规划 / 全局超时强制合成
  ↓ Summarizer：把所有子结果合成完整报告
  ↓ M5 对抗循环（报告置信度 <0.8 时触发）：
      Red Agent 五维打分找问题 → Blue Agent 按优先级修复 → 直到收敛/震荡
  ↓ 输出报告（带置信度、搜索轮数、重规划次数、对抗轮数、参考来源）
```

## 二、逐条拆解简历

简历五条 bullet，每条按"它说的是什么 → 代码在哪 → 术语逐个解释 → 为什么这么设计"来讲。

### 2.1 项目介绍

> 面向深度研究任务中信息过载与幻觉漂移的问题，基于 asyncio 自研多 Agent 编排引擎，搭建规划→并发执行→对抗降噪→报告合成全链路流水线，并配套可复现评测体系。

这条是总纲。"自研"的含义：**不依赖 LangGraph / AutoGen / CrewAI 等编排框架**，编排逻辑全部手写（`src/orchestrator/orchestrator.py`，646 行）。面试官问"为什么不用现成框架"，标准答案：

1. 深度研究任务的调度逻辑需要**完全可控**：三级降级、按失败率触发重规划、全局超时强制合成，这些细粒度策略在通用框架里要么改起来别扭，要么被框架抽象挡住；
2. 框架本身有学习成本和版本风险，而这里需要的核心原语只有三个：拓扑分层、Semaphore 限流、wait_for 超时——asyncio 原生就够；
3. 自己写一遍才能真正掌握调度细节（对面试也有价值）。

### 2.2 编排引擎（第一条 bullet）

> 针对长链路单点故障与失败归因问题，基于 asyncio+Semaphore 自研：9状态状态机管理任务生命周期，Kahn 算法对子任务 DAG 拓扑分层并发(并发度5)；设计三级降级——单任务超时标记继续不阻塞整层、失败率超50%触发增量重规划(保留高置信结果,上限3轮)、全局超时强制以已有结果合成。

**代码位置**：`src/orchestrator/orchestrator.py` + `src/planner/dag.py` + `src/planner/planner.py`

#### ① 9 状态状态机

`orchestrator.py:84-94`，用字典映射实现：

| 状态 | 干什么 | 下一步去哪 |
|------|--------|-----------|
| IDLE | 入口，清空运行时状态 | → PLANNING |
| PLANNING | 调 Planner 生成 DAG | 成功→DISPATCHING；解析失败→FAILED |
| DISPATCHING | 按层并发执行子任务 | → COLLECTING |
| COLLECTING | 收结果、写记忆、判断要不要重规划 | → REPLANNING 或 SYNTHESIZING |
| SYNTHESIZING | 合成报告 | → ADVERSARIAL（若开启）或 DONE |
| ADVERSARIAL | Red-Blue 打磨报告 | → DONE |
| REPLANNING | 增量重规划（只改失败任务） | → DISPATCHING（循环回去） |
| DONE / FAILED | 终态 | — |

主循环就是 `while state not in (DONE, FAILED): state = await handlers[state]()`（`orchestrator.py:123-144`）。**为什么用状态机而不是顺序写一个 async 函数**：因为 REPLANNING 会把流程"跳回"DISPATCHING 形成循环，顺序代码会写成 spaghetti 的 while 嵌套；状态机把每个阶段的入口/出口、异常转换显式化，加新状态（比如以后加"人工审核中"）只需注册一个 handler。

#### ② Kahn 算法拓扑分层

`dag.py:85-149`。Kahn 算法：反复取**入度为 0** 的节点（没有未完成依赖的任务），移除它并把它指向的后继节点入度减一。O(V+E)。

关键改进是 `get_parallel_groups()`（`dag.py:115-149`）：不是返回一条拓扑序，而是**按层分组**——第 0 层是所有初始入度为 0 的节点，它们互不依赖所以可以并行；它们完成后入度归零的节点构成第 1 层，以此类推。每层内按字典序排序保证确定性（`dag.py:131`），最终还做安全检查：分组总数 ≠ 节点总数说明图里有环，抛 `DAGCycleError`。

为什么分层而不是逐个调度：**分层让"最大可并行度"变得显然**——同层任务 gather 一起跑，层与层之间天然同步（后面层的依赖全在前面的层里），不需要手动管理复杂的依赖等待逻辑。图里有环时 Planner 侧也会在 `_parse_plan` 里先跑一次拓扑排序做校验（`planner.py:317-320`），环直接判解析失败。

#### ③ 并发度 5 = Semaphore

`orchestrator.py:238`：`semaphore = asyncio.Semaphore(self._config.max_concurrent)`，配置在 `configs/default.yaml:112` 是 `max_concurrent: 5`。每个子任务先 `async with semaphore` 拿到名额才能执行——即使某一层有 10 个任务，同时最多 5 个在跑。**为什么要限流**：每个子 Agent 都会调 LLM API 和搜索 API，不限流会撞 API 并发上限 / 触发限速，也会让单任务延迟不可控。

#### ④ 三级降级（面试必问，按严重程度递进）

| 级别 | 触发条件 | 行为 | 代码 |
|------|---------|------|------|
| 一级 | 单任务超时（`asyncio.wait_for`，默认每个子任务 120s） | 标记为 TIMEOUT，**不影响同层其他任务**，继续走 | `orchestrator.py:263-272` |
| 二级 | 失败率 >50%，或成功率 <30% 且有失败 | 进 REPLANNING：只重新规划失败任务，**保留 confidence≥0.6 的成功结果**，最多 3 轮 | 判定 `orchestrator.py:519-537`；保留逻辑 `planner.py:178-186` |
| 三级 | 全局超时（默认 600s） | 若已有部分结果 → 强制跳到 SYNTHESIZING 用现有材料合成；否则 FAILED | `orchestrator.py:125-135` |

**为什么"保留高置信结果"**：重规划不是为了推倒重来，是因为部分子任务失败了导致证据链有缺口。已经成功且置信度高的结果重跑一遍纯粹浪费 token 和时间，所以 replan 的 prompt 里把成功结果作为"要保留的上下文"喂给 Planner（`planner.py:78-106` 的 REPLAN_PROMPT），新计划只需要补缺口。

**失败归因**：`_build_failure_reason`（`orchestrator.py:601-610`）统计超时数和失败数生成原因描述（"2 tasks timed out (may need simpler queries or longer timeout)"），喂给 replanner——这就是简历里"失败归因"四个字的具体含义。

#### ⑤ 为什么 asyncio 不是多线程

整个流程是 **I/O 密集**（等 LLM 响应、等搜索 API），不是 CPU 密集。asyncio 单线程事件循环处理并发 I/O：没有 GIL 问题、没有锁竞争（记忆存储那把锁是防御性的）、协程切换开销远小于线程。Python 里这是标准答案。

### 2.3 对抗降噪（第二条 bullet）

> 针对长文幻觉漂移与来源不可信，设计 Red-Blue 对抗循环：RedAgent 从事实核查/幻觉检测/逻辑一致性/来源可信度/覆盖完整度五维评分，BlueAgent 执行就地修正/补充检索/整段移除；以收敛与震荡双重刹车终止，输出经多级 JSON 兜底、失败降级为保守分，保证循环不中断。

**代码位置**：`src/adversarial/`（loop.py 主控 / red_agent.py 攻击 / blue_agent.py 修复 / verdict.py 数据结构与评分引擎）

设计灵感可以直说：**GAN 的对抗思想迁移到文本质量**——生成方（报告）和审查方（Red）持续博弈，报告质量在博弈中上升。但要强调与 GAN 的区别：这里是**推理时优化**，不训练任何参数。

#### ① Red Agent 五维攻击（red_agent.py）

五个维度，每个维度**独立的一次 LLM 调用、独立 prompt**（`red_agent.py:238-244` 的 DIMENSION_PROMPTS）：

| 维度 | 枚举值 | 检查什么 | 权重 |
|------|--------|---------|------|
| 事实核查 | fact_check | 数字/日期/人名/机构是否有来源支撑且一致 | **0.30** |
| 幻觉检测 | hallucination | 无来源陈述、编造的具体数字/引语/因果 | **0.25** |
| 逻辑一致性 | logical | 前后矛盾、因果倒置、以偏概全 | **0.20** |
| 来源可信度 | source_credibility | 域名权威性(.gov/.edu vs 自媒体)、时效性、一手/二手 | **0.15** |
| 覆盖完整度 | coverage | query 的子话题是否覆盖、正反方是否均衡、是否跑题 | **0.10** |

（权重在 `verdict.py:188-194`，总和 1.0；事实+幻觉占 55%，因为这是项目的核心痛点。）

每个维度的 prompt 都给了 0-10 分的**分档评分标准**（例如事实核查 10 分=所有可验证事实有可靠来源；4-6 分=有明显事实错误但核心论点成立），并要求输出结构化 JSON：`{"score": float, "issues": [{severity, description, location, fix_type, evidence}]}`。

为什么每维独立调用而不是一个 prompt 评五个维度：**单条 prompt 太长会导致注意力分散**，五个维度挤在一个输出里每个都评得粗糙；独立调用让每个维度有自己的详细评分标准和检查清单（`red_agent.py:8` 明确写了这个设计决策）。代价是 5 倍调用成本，换来评分质量和可维护性。

综合分 = 加权平均 `compute_overall`（`verdict.py:210-230`），缺失维度时按已有权重重新归一化，越界分数 clamp 到 [0,10]。

#### ② Blue Agent 修复（blue_agent.py）

拿到 issues 后先按**优先级排序**再逐条修（`blue_agent.py:203-208`）：

```
priority = severity权重 × dimension权重 × 修复难度系数
```
severity: critical=10 / major=5 / minor=1；难度: 就地修正 1.0 > 移除 0.8 > 补充检索 0.6（`verdict.py:196-208`）。含义：**critical 的事实问题最先修，且"能直接改"的优先于"要花钱搜索"的**。

三种修复操作对应 Red 输出的 fix_type：

| FixType | 做什么 | prompt 要求 |
|---------|--------|------------|
| IN_PLACE 就地修正 | 数字/日期/名字与来源不一致 → 直接替换 | 只改事实性内容，保持结构风格，不引入新信息 |
| SUPPLEMENTARY 补充检索 | 无来源支撑的 claim → 调搜索工具找证据 | 找到→补引用；找不到→删除或标注"未经证实" |
| REMOVAL 整段移除 | 高置信幻觉段落 → 删除 | 删后保证上下文连贯，必要时加过渡句 |

每修完一条 issue 做一次 **self_verify**（`blue_agent.py:214-227`）：把"原始报告 vs 修复后报告 vs 已做的修复"给 LLM，问是否引入了新矛盾。发现新问题会记录（追加一条 failed 的 FixOperation），但**继续修而不是回滚**——避免修复和回滚之间死锁。

#### ③ 双重刹车：收敛 + 震荡（loop.py，面试最爱问）

**收敛刹车**（三选一即停，`loop.py:161-176`）：
1. 轮数达上限（config 里 `max_rounds: 10`，注意 runner 兜底默认是 3）；
2. 综合分 ≥ 阈值（`score_threshold: 9.5`）——质量够了；
3. Δ < 阈值（`delta_threshold: 0.2`）——**修复已经不产生增益**，继续烧钱没意义。

Δ 的计算不是简单总分相减，是**五维分数向量的欧氏距离** `compute_delta`（`verdict.py:232-258`）——总分不变但维度间此消彼长（比如事实分涨了、覆盖分跌了）也能被捕捉到。这是个能体现细节的加分点。

**震荡刹车**（`loop.py:102-115`）：维护一个 `resolved_issues` 集合（Issue 实现了基于核心字段的 `__hash__`/`__eq__`，`verdict.py:98-111`，所以能进 set）。每轮 Red 攻击完，如果发现**之前修好的 issue 原样重新出现**——说明 Blue 的修复在"改回来改过去"——立即终止，保留当前版本。防止无限拉扯浪费预算。

诚实细节（被追问时说出来反而加分）：震荡检测是**精确匹配**（hash 基于 severity+dimension+description+location+fix_type），Red 两轮对同一问题的措辞稍有不同就检测不到。改进方向：用 embedding 相似度做模糊匹配。

#### ④ 多级 JSON 兜底 + 保守分（red_agent.py:356-437）

LLM 输出 JSON 的解析是四级瀑布：
1. 直接 `json.loads` 整个输出；
2. 失败 → 正则提取 ```json 代码块；
3. 还失败 → 正则提取第一个 `{...}` 块；
4. 还失败 → 修复常见错误后重试（去 // 注释、单引号换双引号、去尾随逗号）；
5. 全失败 → **该维度记保守分 5.0、issues 为空**，绝不抛异常。

"保守分 5.0"的含义：既不是 0（那样会冤枉一份其实不错的报告、触发过度修复）也不是高分（那会漏掉真问题），5.0 是"我不确定，当中等"的中性值。**它保证的是：任何单点解析失败都不会打断对抗循环**——这就是简历"保证循环不中断"的意思。

#### ⑤ 触发条件（容易忽略的省钱设计）

`orchestrator.py:446-448`：**报告置信度 ≥0.8 时直接跳过对抗循环**。对抗是贵的（每轮 5 次 Red 调用 + N 次 Blue 调用），好报告不需要打磨。

### 2.4 上下文治理（第三条 bullet）

> 针对上下文膨胀与跨 Agent 结论打架，按预算占用率分级触发三级压缩(向量粗筛→TextRank关键句抽取→LLM摘要,超限由滑动窗口兜底)，前两级为抽取式；以 SQLite+NumPy 向量检索构建共享记忆，写入前做语义去重与矛盾检测，冲突由多数投票/来源权重/LLM裁定消解。

**代码位置**：`src/compressor/compressor.py` + `src/memory/memory_store.py`

#### ① 三级压缩，按预算占用率自动触发（compressor.py:121-135）

预算模型：`available = budget(16000) - output_reserve(2048) = 13952 tokens`，token 数按字符数 ÷3.5 估算（中英混合经验值）。

| 占用率 | 触发 | 手段 | 类型 |
|--------|------|------|------|
| ≤60% | 不压缩 | 原样返回 | — |
| >60% | L1 | 向量粗筛：每段文本与 query 算 embedding cosine，自适应阈值 0.25→0.20→0.15 逐级放宽，直到塞得下预算的 80% | **抽取式** |
| >80% | L1+L2 | TextRank 关键句抽取（query-biased），保留比例按占用率线性映射：占用越满留得越少，公式 `max(0.15, min(0.40, 0.50 - 占用率×0.35))` | **抽取式** |
| >95% | L1+L2+L3 | LLM 层级摘要：先逐文档摘要，再把所有摘要聚合成一段综述 | 生成式 |
| 压完仍超限 | 兜底 | 滑动窗口截断（保最近的，丢最老的） | 硬截断 |

面试三个关键问答：

**Q: 为什么前两级用抽取式而不是直接 LLM 摘要？**
A: 三点。(1) 抽取式**不引入新信息**——从原文里挑句子不可能捏造事实，LLM 摘要有幻觉风险，压缩环节引入幻觉等于治聋反致哑；(2) 免费、快，不需要 LLM 调用；(3) 可复现（TextRank 是确定性的）。LLM 摘要留到 95% 以上极端情况才用，且作为最后手段。这也是为什么简历专门写了"前两级为抽取式"——这是设计上有意的安全取舍。

**Q: TextRank 是什么？**
A: 把文章的句子建图：句子是节点，两句相似度（如词重叠）作为边权，跑 PageRank，每个句子的得分反映它对全文的"代表性"；query-biased 是在边权或排序时额外加上与 query 的相似度，让抽出的句子既代表原文又贴着问题。

**Q: 为什么还要滑动窗口兜底？**
A: L1/L2/L3 每一级的效果都依赖启发式假设（相似度阈值、保留比例），极端输入下可能压完仍超预算。滑动窗口是数学上必然能把长度压到预算内的最终保险——先保证"塞得进上下文"，再谈质量。

补充一个量化接口的亮点：压缩器每次记录 `compression_ratio` 和 `information_retention`（信息保留率=原文中的数字实体和英文专名在压缩后还剩多少，`compressor.py:315-340`），供消融实验量化压缩质量——不是拍脑袋说"压缩效果好"。

#### ② 共享记忆（memory_store.py，593 行）

架构：**SQLite 做持久层 + 内存里维护归一化后的 numpy 向量矩阵做检索层**（`memory_store.py:128-134`）。为什么不用 faiss/Milvus：数据量级（万条以内，配置 `max_entries: 10000`）numpy 矩阵点积就是暴力检索也毫秒级，引外部依赖纯属过度设计。这个"为什么不"面试要会。

**写入路径**（`put()`，`memory_store.py:211-261`），每一步都有明确动机：

1. **质量过滤**：claim 长度 <30 字、confidence <0.3、命中垃圾模式（"您好""I'm ready to help"、报错信息）→ 直接拒收，防止子 Agent 的寒暄和报错污染记忆库；
2. **语义去重**：与库内最高相似条目 cosine >0.92 → 判定为同一事实。合并策略：保留 confidence 更高的版本（新条目更可信就更新，否则忽略），避免同一事实被反复写入；
3. **矛盾检测**：0.65 < cosine < 0.92（"说的是相近话题但不完全相同"）**且**启发式语义对立判定为真 → 记 ConflictRecord。语义对立判定（`memory_store.py:62-98`）：(a) 一方含否定词另一方不含、去掉否定词后词集 Jaccard >0.5（"X 增长" vs "X 不增长"）；(b) 命中人工维护的反义词对表（增加/减少、支持/反对、高/低…）；
4. 持久化到 SQLite 并追加进内存向量索引。

**为什么去重阈值 0.92、矛盾下界 0.65**：语义上"几乎相同"（>0.92）是重复；"话题相近但表述不同"（0.65~0.92）才有可能是同一问题的两种矛盾说法；低于 0.65 大概率是别的话题，不构成矛盾。阈值是经验值，配置文件里可调（`similarity_threshold_dup: 0.92` / `similarity_threshold_conflict: 0.65`）。

**矛盾消解三策略**（`memory_store.py:387-493`，resolve_conflict）：

| 策略 | 逻辑 | 适用 |
|------|------|------|
| majority_vote | 同 topic 下多数 Agent 支持的 claim 胜出 | 多个独立子 Agent 检索同一话题，少数服从多数 |
| source_weight | evidence_type 权重（一手 1.0 / 二手 0.8 / 推断 0.6）× confidence 加权 | 来源质量差异大时，官方数据 > 自媒体转述 |
| llm_judge | 调 LLM 做仲裁（失败时降级到 source_weight） | 前两者无法裁决的复杂情况 |

**淘汰策略**：评分 = confidence × evidence权重 × 时间新近度 × 冲突加成，定期淘汰低分条目；不同 session 的记忆物理隔离（session_id 过滤），用户 A 的研究不会串进用户 B 的上下文。

### 2.5 评测体系（第四条 bullet）

> 针对"提升是真实还是波动"的问题，自建 ResearchBench(11领域/35题)与 HotpotQA 变体；三层指标由规则指标(事实准确率/幻觉率/引用覆盖率/逻辑一致性/完备性)、LLM-as-Judge 评分与统计检验(Bootstrap 95% CI、Cohen's d)构成，配一键消融脚本。

**代码位置**：`evaluation/`（metrics/rule_based.py、metrics/stats.py、benchmarks/research_bench.py、benchmarks/hotpotqa.py）+ `scripts/run_ablation.py`

核心思想一句话：**任何"X 比Y 好"的结论必须同时过三层检验——规则层证明存在差异，Judge 层证明差异被认可，统计层证明差异不是随机波动。**

#### 第一层：规则指标（免费、可复现、CI 可跑）

`rule_based.py`，纯 Python 启发式，零 API 成本：

- **事实准确率**：两个口径。字符串版=ground_truth 关键短语在报告中的命中率；**语义版**（加分点）=把 ground_truth 条目和报告句子分别 embedding，算最大 cosine，超 0.65 才算覆盖——避免"GPT-4o 是 Google 发布的"这种关键词命中但语义错误的假阳性；
- **幻觉率**：启发式找可疑模式——无引用的数值声明、绝对化表述（"毫无疑问"）、"研究表明"却无具体引用（`rule_based.py:111-119`）；
- **引用覆盖率**：报告中的引用标记（Result N / [N] / http 链接）覆盖段落的比例；
- **逻辑一致性**：矛盾词对检测（"是/不是"、"可以/不可以"共现于一句）；
- **完备性**：expected_topics 的覆盖率（ResearchBench 每题自带期望覆盖的子话题）。

#### 第二层：LLM-as-Judge

小米 MiMo 当评委，五维 0-10 深度评分（与 Red Agent 的五维对应）。用与被评系统**不同的模型**当评委，缓解自评偏置。局限要主动说：Judge 有自身偏差（偏长回答、位置偏差），所以它和规则层互补而不是替代。

#### 第三层：统计检验（`stats.py`）

- **Bootstrap 95% CI**（`bootstrap_ci_paired`，10000 次重采样）：对"完整系统 vs 消融版"的逐题配对分差做自助采样，算均值的置信区间。**判定标准：CI 下界 >0 才算显著**（区间完全落在 0 右侧）；
- **Cohen's d**：效应量，说明差异是大是小（不只统计上显著）；
- **配对 t 检验**：参数方法对照。

**为什么小样本必须 Bootstrap**：消融实验每档 12 题，正态假设不可靠；Bootstrap 是非参数方法，对样本分布无假设，12 个样本也能给出可信的区间。

#### 评测集

- **ResearchBench**（自建）：11 个领域 ×35 题，每题带 `expected_topics`（该覆盖哪些子话题）和 `ground_truth`（关键事实字典）；
- **HotpotQA 变体**：多跳 QA 改造成深度研究任务，用它的标准答案算事实准确率，新增语义覆盖度指标。

#### 一键消融（`scripts/run_ablation.py` + `run_all_experiments.py`）

模块消融（关掉 M3/M4/M5 各跑一遍对比完整版）+ 轮数消融（对抗循环 1/2/3 轮）+ Agent vs 单轮 LLM 的 head-to-head，全量约 165 次独立运行，overnight 跑完。

#### "5 项指标区分度校验"是什么（简历最后一句话，别被自己问倒）

outputs/ 下的 5 个 JSON（report_metrics / extra_metrics / compressor_metrics / eval_layer_metrics / m5_verdict_metrics）——它们**评的不是系统，是指标本身**，即"指标区分度校验"：

- compressor_metrics：验证压缩阈值的真实语义（占用率 60%/80%/95% 对应多少字符）、并**诚实记录了编排器触发门与压缩器阈值不一致的问题**（见 4.2 节）；
- m5_verdict_metrics：验证评分引擎的性质——权重和=1.0、越界分数被 clamp、Δ 的量纲（每维各涨 0.1 时 Δ=0.224）、Issue 相等性机制；
- eval_layer_metrics：验证同一个 composite_score 在三个调用方口径下天花板上限不同（A=1.00 / B=0.75 / C=0.80），防止跨口径比较出错误结论；
- report_metrics / extra_metrics：5 份真实报告的幻觉率、引用密度、章节完备性等。

一句话：**先证明尺子是准的，再用尺子量东西。**

### 3.0 开场必问

**Q: 用两分钟介绍这个项目。**
（按第一节的一句话 + 三痛点 + 三解法 + 数据流图讲，最后甩成果数字：1.4 万行、5 份报告平均 2.1 万字、规则口径幻觉率 3.34%。）

**Q: 你在这个项目里具体做了什么？**
逐模块讲自己实现的顺序与取舍：先写 DAG+状态机把链路跑通（M1/M2），发现上下文爆了写压缩（M3），发现子 Agent 结论打架写记忆（M4），发现报告有幻觉写对抗（M5），最后发现"好不好说不清"写评测。**按问题驱动讲演进，而不是报菜名。**

**Q: 为什么不用 LangGraph / AutoGen？**（见 2.2 开头，三点：可控性、原语简单、无框架锁定。）

**Q: 整个系统最耗时的环节是哪？怎么优化的？**
LLM 调用是绝对大头（每轮研究约 10~20 次调用：规划 1 + 每子任务 2~5 + 合成 1 + 对抗每轮 5+）。优化手段：并发（分层 gather+Semaphore(5)）；模型分工省钱（重活 DeepSeek、评审类轻活 MiMo，`backend_mapping`）；跳过不必要的对抗（置信度 ≥0.8 直接 DONE）；缓存与去重减少重复检索（记忆库去重）。

### 3.1 编排引擎

**Q: 状态机为什么是 9 个状态？少几个行不行？**
IDLE/PLANNING/DISPATCHING/COLLECTING/SYNTHESIZING/DONE/FAILED 是主干；REPLANNING 是为了把"失败率过高→重新规划→再执行"的循环显式化；ADVERSARIAL 独立成状态是因为它有自己的启停条件（置信度门槛）和独立的计费口径（对抗轮数）。合并当然能跑，但每个阶段的入口出口、监控指标、失败转换就糊在一起了。

**Q: Kahn 算法的时间复杂度？如果 LLM 生成的 DAG 有环怎么办？**
O(V+E)。环在两处被拦：Planner 解析时先跑拓扑排序，有环抛 PlanParseError → 判规划失败；DAG 的 get_parallel_groups 分组后做数量校验兜底。**追问"规划失败怎么办"**：初始规划失败直接 FAILED（没有可执行计划）；重规划失败但已有部分成功结果 → 降级直接合成。

**Q: Semaphore(5) 的 5 是怎么定的？**
经验值，受两个约束：LLM API 的并发/速率限制，和单任务的延迟要求（并发太高所有任务都慢）。5 在 DeepSeek API 限速内且能保证单层 8 个任务时延迟可控。这是可配置项，换后端只需改 YAML。

**Q: 单任务超时了，它的下游依赖任务怎么办？**
超时任务标记 TIMEOUT 继续走。下游任务拿到的是空的依赖上下文，可能产出低质量结果——这个缺陷由收集阶段兜底：失败率 >50% 触发 replan，把整条失效链路重新规划。也就是说**容忍局部缺失，靠全局降级策略补偿**。

**Q: asyncio.wait_for 超时后任务真的停了吗？**
wait_for 会 cancel 内部协程。但注意被取消时若 LLM 请求已在途，HTTP 层面的取消依赖 aiohttp/openai SDK 的实现——这是已知的边角，工程上可以接受（最坏情况是浪费一次调用，不影响正确性）。

**Q（刁钻）：全局超时强制合成，此时记忆里只有部分结果，报告质量必然差，这不算掩盖问题吗？**
算 trade-off 不算掩盖。报告元信息里如实记录了 num_searches、num_replan、置信度——降级合成的报告置信度会反映真实状态，下游（用户或对抗循环）能看到。**系统承诺的是"永远给一个尽可能好的答案+真实的元信息"，不是"永远完美"。**

### 3.2 对抗降噪

**Q: Red 和 Blue 用同一个模型会怎样？**
会有"自己检查自己"的盲区重合。所以配置里 Red/Blue/Judge 走 MiMo、solver 走 DeepSeek——生成和审查分离。当然 Red 和 Blue 之间同模型也有局限（彼此思维方式太熟），更理想是三模型制，成本约束下先做了两模型分工。

**Q: 收敛条件为什么是"三选一"而不是单一条件？**
三个条件分别对应三种终止场景：分数达标（质量已够，别过度打磨）、Δ 收敛（投入产出比归零，继续是浪费）、轮数上限（前两者都没触发时的硬保险）。缺任何一个都会出问题：只有轮数上限→达标了还在烧钱；只有分数→永远到不了 9.5 时死循环；只有 Δ→震荡初期 Δ 可能很小但方向是错的。

**Q: Δ 为什么用欧氏距离不是总分差？**
总分是五维加权的标量，五维此消彼长时总分可能不动——比如事实 8→9、覆盖 7→6，总分持平但报告内部结构在变。欧氏距离对每个维度的变化都敏感。实测每维各涨 0.1 时 Δ≈0.224（m5_verdict_metrics 里有这张表）。

**Q: 震荡检测怎么实现的？误报/漏报怎么办？**
精确 hash 匹配（Issue 的五个核心字段），Red 重新报出**一字不差**的 issue 才触发。所以漏报是主要风险（措辞变了就检测不到），误报几乎为零。改进方向：对 issue description 做 embedding，相似度 >0.9 判定同一 issue。

**Q: Blue 修复是让 LLM 输出整篇 fixed_content，会不会越修越丢内容？**
会，这是该设计的真实风险——LLM 重写全文时可能悄悄丢段落。缓解：(1) prompt 明确要求"保持原文结构"；(2) 每次修复后 self_verify 比对原文与修改稿，发现新问题记录在 FixOperation 里；(3) 对抗循环的 Δ 刹车兜底——如果修复在净伤害报告，覆盖维度分数会掉，Δ 会异常，循环会被终止。彻底的解法是改成 span-level 编辑（定位原文片段做替换），这是明确的改进项。

**Q: Red 每轮攻击的报告是截断到 4000 字符的（red_agent.py:289），长报告后半部分岂不是没人管？**
对，这是诚实的已知局限。当时取舍是全量报告会让单维 prompt 超 16K 预算且评分质量下降。改进方向：分段攻击再聚合，或按维度做注意力引导（事实核查维度只看含数字的段落）。

**Q: 对抗循环平均带来多少提升？**（如果没跑过消融，诚实说）消融框架已就位（run_ablation.py 支持 enable_adversarial 开关），完整 165 次运行的成本约束下，跑通了对抗轮数消融的小规模版本。**千万不要编一个没跑过的提升数字。**

### 3.3 上下文治理

**Q: 压缩的触发为什么不放在每次写入后，而是按预算占用率？**
事件驱动（每写一次压一次）在小上下文时浪费（还没到瓶颈就压，白白丢信息）；占用率阈值是"到痛点才动手"，且级别随紧张程度递进——60% 只做便宜的过滤，95% 才动用 LLM 摘要。**成本和信息损失都跟着压力走。**

**Q: embedding 模型是什么？多语料时效果如何？**
sentence-transformers 的 all-MiniLM-L6-v2（384 维）。局限：对中文语义的区分度一般——改进方向是换 bge-small-zh 之类的中文模型，接口已抽象（Embedder 类），换模型零改动。

**Q: 为什么 SQLite + numpy 而不是 faiss/Milvus/Chroma？**
量级决定：max_entries=10000，归一化后一次矩阵点积就是全库检索，numpy 在这个量级是微秒~毫秒级，外部向量数据库引入的是部署成本、运维成本和数据同步复杂度。**架构选型的第一原则是量级匹配**，真到百万级再换 faiss 也不迟——检索层已经被隔离在 `_find_duplicate`/`get_context_for_query` 这几个方法内部，替换成本很低。

**Q: 矛盾检测的启发式听起来很弱（反义词表+否定词），为什么不用 LLM 判矛盾？**
成本和延迟。写路径是高频操作（每个子任务结果都写），每次都调 LLM 判矛盾会把写入变成瓶颈。启发式是**漏报型**的（只抓最典型的对立模式），宁可漏掉一些矛盾，也不误伤正常写入；漏掉的矛盾还有两道后续防线：对抗循环的 Red Agent 会从报告层面找矛盾，LLM Judge 消解策略兜底处理已检测到的冲突。

**Q: 记忆的 session 隔离怎么做的？**
写入时打 session_id，加载索引时按 session 过滤，物理上不同用户的记忆互相不可见。跨 session 的场景（同一用户连续多次研究同一话题）通过显式指定 session 继承实现（REPL 的 sessions 命令）。

### 3.4 评测

**Q: 幻觉率 3.34% 怎么算的？可信吗？**
五份报告各自的规则幻觉率（无引用数值声明 + 绝对化表述 + 无引用"研究表明"模式的占比）取平均：(1.45+2.58+11.71+0+0.97)/5=3.34%。它是**规则口径**的下界估计（启发式只能抓模式化幻觉），不是人工标注真值。可信的部分：可复现、零成本、可进 CI；不可信的部分：对"高级"幻觉（语法通顺但事实编造）无能为力——所以才有第二层 LLM Judge 和语义版指标互补。

**Q: 怎么保证 LLM-as-Judge 本身是公平的？**
四个手段：评委与被评系统不同模型（避免自评偏置）；低温度采样（judge temperature 0.1，配置里明确写了"评分标准必须一致，避免漂移"）；详细的分档评分标准（和 Red Agent 同款设计）；以及统计层把 Judge 分数当样本做显著性检验，单次 Judge 的偏差被 CI 稀释。

**Q: 12 题一档的消融，Bootstrap 真的有意义吗？**
有的——Bootstrap 对样本分布无参数假设，12 个配对差值的重采样分布足以给出稳健的 CI；但效应量解释要保守（小样本下 Cohen's d 的估计本身方差大）。诚实说法：统计层的作用是**排除明显的随机波动**，不是宣称精确的效应大小。

**Q: composite score 三个口径不一样（1.0/0.75/0.80）是怎么回事？**
这是指标区分度校验里主动发现的问题：run_ablation、research_bench、rule_based 三个调用方各自拼 composite，键集不同导致同分不同义（比如 research_bench 产出 factual_accuracy_sem/str 两个变体但权重表只认一个，权重静默归零）。处理：文档化口径差异，跨口径不做直接比较。这题答出来是"评测意识"的强加分项。

### 3.5 项目级刁钻问题

**Q: 这个项目最大的缺陷是什么？**（必问，准备一个诚实的）
推荐答法（挑两个讲深）：
1. **压缩触发门与阈值不匹配**：编排器给压缩的触发门是 6000 字符（≈1714 token，仅 12% 占用率），而压缩器自己的阈值是 60% 起跳——意味着从编排器这条路进来时压缩几乎必然触发 L3 或走到滑动窗口兜底，60%/80% 的分级没有真正生效。这是指标校验（compressor_metrics.json 的 gate_incompatibility 项）主动发现并文档化的问题，修复方向是统一以 token 预算为单一事实源。
2. **逻辑一致性指标过弱**：五份报告的逻辑一致性全是 1.0（满分），因为矛盾词对（"是/不是"共现）在真实报告里几乎不触发——指标没有区分度等于没有指标。改进方向：基于 NLI 模型做句对蕴含检测。

**Q: 如果流量放大 100 倍，架构哪里先崩？**
SQLite 单写者锁先崩（写路径串行化）；其次是内存向量索引全量重建的启动延迟。演进：SQLite→PostgreSQL，向量检索→独立检索服务（量级到了换 faiss），编排器天然无状态可以水平扩，LLM 调用加全局速率治理。

**Q: GRPO/自进化（M6）为什么是预留的？**
诚实版答案：完整的在线 GRPO 需要 veRL 训练 infra、多卡资源和持续的训练数据回流，超出这个阶段项目的资源边界。当前完成了：进化引擎的代码骨架（engine.py 的 run_round、experience_memory、symbolic_learning）、配置项与接口占位。**面试时明确说"预留接口、未训练"，反而比含糊说"做了 GRPO"安全一万倍**——追问一层就穿帮的事情不要做。

**关于 GRPO 的最小知识包**（既然简历提了 M6 相关的进化，至少要能讲清原理）：GRPO（Group Relative Policy Optimization）是 PPO 的变体，去掉 value 网络——对同一个 query 采样一组（group_size=8）回答，用**组内相对排名**（每个回答的 reward 减组均值除组标准差）作为优势估计，配合 KL 惩罚防漂移。优点：省一个 value 网络的训练开销，且天然适合"多份报告比好坏"这种可排序的 reward 场景——这正是本项目报告质量优化问题的形状。项目 config 里 group_size: 8、kl_coef: 0.01、lora_rank: 16 就是按这个方案配的。
